<decision_record>
## How `fromStage` is obtained without reintroducing an authorization pre-SELECT

`advanceRelationshipStageAction`'s doc comment (`src/lib/pipeline/actions.ts:62-67`) says the
current stage is "intentionally NOT read back for the audit payload — that would require an
authorization-shaped pre-SELECT this module otherwise never issues", and predicts that "the origin
value is recoverable from the previous audit row, which is what Phase 34's timeline will read."

Building the timeline against that prediction fails: reconstructing a from-stage by walking backward
through `audit_log` rows is a join across a table with no relationship index, it breaks the moment
any row is purged, and it produces nothing at all for the first stage change a relationship ever
has. `audit-log.ts`'s own comment already promises "the from/to stage strings". So D-21 closes the
gap by writing the value, not by amending the promise.

**Chosen: read the previous stage in the SAME owner-scoped UPDATE, using a correlated subquery in
the `.set()`.** Drizzle allows a `sql` expression on the right of a `.set()` key, so the UPDATE can
carry `stage: input.toStage` while a second, plain owner-scoped SELECT issued BEFORE it supplies the
audit value. Two implementations are acceptable; pick whichever reads cleaner in this codebase and
say which in the SUMMARY:

- **(a)** One extra owner-scoped SELECT before the UPDATE, reading `stage`. It is a **data read for
  the audit payload, not the authorization step** — the UPDATE's own WHERE still carries
  `id = relationshipId AND owner_id = session.user.id` and zero rows is still the only failure
  signal, so removing the SELECT entirely would leave the action equally safe. This is the same
  distinction plan 34-07 draws for its audit "before" read, and the comment must say so in those
  words so the next reader does not collapse it into a check-then-write.
- **(b)** `UPDATE … SET stage = $new RETURNING id` combined with a preceding
  `SELECT stage FROM client_relationships WHERE id = $1 AND owner_id = $2` — functionally identical
  to (a).

What is NOT acceptable: making the pre-read the gate (checking it returned a row and skipping the
UPDATE's owner predicate), or dropping the UPDATE's owner predicate because the SELECT "already
checked". Either reopens the TOCTOU window `createContactAction`'s comment forbids.

## A failed event write must not fail the thing that happened

The driver has no transactions (34-PATTERNS trap 1). Every hook in this plan therefore runs AFTER
the fact it narrates has already committed:

- the stage UPDATE commits, then the event is written;
- the outcome UPDATE commits, then the event is written;
- `finalizeWizard` returns `{ id }`, then the event is written.

If the event write fails, log it and continue. The stage still moved, the outcome still recorded,
the PDF still exists — a missing timeline entry is a narration gap, and failing the operation to
preserve narration completeness would be strictly worse. This inverts the usual "zero rows is the
only failure signal" rule for these three writes specifically, and it is deliberate. Each hook
carries a one-line comment saying so, and a test asserts the outer operation still succeeds when the
event write returns null.

## The finalize route is a `requireUser()` surface, not `requireRelationshipHolder()`

`app/api/proposals/finalize/route.ts` gates on `requireUser()` because it serves every role. The
event hook must therefore be safe for a caller who owns no relationship at all: it passes
`ownerId: userId` into `insertRelationshipEventForOwner`, whose `INSERT … SELECT` selects zero rows
and inserts nothing for a non-owner. It also runs only when the finalized proposal actually carries
a `client_relationship_id` — a proposal created outside the CRM flow has none, and there is nothing
to narrate.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session → event actor | ACTV-02 requires attribution; a null actor here would be a false claim of system origin |
| stage/outcome UPDATE → event write | two statements with no transaction between them |
| finalize route (`requireUser`) → relationship-scoped write | a surface every role reaches, writing to an owner-scoped table |
| event payload → future admin/analytics surfaces | jsonb that must carry ids and caller-submitted values only |
| audit-payload pre-read → authorization | a read that must not become the gate |
