Apply migration `0010_phase34_fiche_client` to the Neon **development** branch through the gated
GitHub Actions workflow, and record the run.

from `src/db/schema.ts`, **not** from the live database — so all of them pass whether or not the

runs before it.

Output: no source files. A SUMMARY recording the workflow run and the live-schema confirmation.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration file → production database | DDL executed with elevated privileges |
| workflow_dispatch input → shell | operator-supplied `branch`/`confirm` values |
| local developer machine → shared Neon branch | an ad-hoc connection that would bypass the gated path |
| verification query output → the SUMMARY | a place a connection string could accidentally be recorded |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-34-04-01 | Tampering | the migration reaching a database out of band | mitigate | The only sanctioned path is `db-migrate.yml`; `scripts/check-no-drizzle-push.sh` blocks the `push` alternative in CI, and this task's acceptance criteria require a workflow run URL as evidence rather than a local command transcript. |
| T-34-04-02 | Elevation of Privilege | an unintended apply against the `main` (production) Neon branch | mitigate | The task explicitly targets `development`; the workflow independently requires a typed `MIGRATE PROD` confirmation plus a GitHub Environment reviewer for `main`. An acceptance criterion asserts no `main` run occurred. |
| T-34-04-03 | Tampering | command injection via `workflow_dispatch` inputs | transfer | Already mitigated in the workflow itself: `branch` is a constrained `type: choice` and `confirm` flows through the `CONFIRM_INPUT` env var before any shell evaluation (Phase 20-02 security note). No change is made here. |
| T-34-04-04 | Repudiation | no record of when the schema changed | mitigate | The workflow run URL, target branch and the four query outputs are recorded in the SUMMARY, giving a dated, attributable trail. |
| T-34-04-05 | Information Disclosure | a connection string pasted into a log, artifact or SUMMARY while verifying steps 5-8 | mitigate | The verification queries are run by the operator locally against their own environment; the SUMMARY records the query *results* (column names, data types, status counts), never the connection string. |
| T-34-04-06 | Tampering | the Phase 31 provenance CHECK silently widened by the migration | mitigate | Step 6 reads `pg_get_constraintdef` for `client_relationships_source_check` from the live database and asserts it still names only the two provenance values — a live check, independent of what the schema file claims. |
| T-34-04-07 | Denial of Service | `relationship_events.actor_id` typed `uuid`, making every event write fail at runtime against Better Auth's text `users.id` | mitigate | Step 7 reads the live `data_type` and instructs the operator to STOP on `uuid`. This is checked here rather than in a later plan because a wrong type is a migration fix, not a code fix. |
| T-34-04-SC | Tampering | npm/pip/cargo installs | mitigate | No dependency change; this plan modifies no file. |

</threat_model>
