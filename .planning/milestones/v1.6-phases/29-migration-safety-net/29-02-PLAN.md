<objective>
Stop local development from reading and writing production.

`.env.local` currently resolves to `ep-icy-boat-alx5o1tz-pooler` — per
`docs/operations/neon-branch-routing.md`, that is the Neon `main` branch, i.e. production. It
should be the `development` branch, `ep-polished-band-alphc576-pooler`. This is the reason the
standing "never run `db:migrate` locally" rule has been load-bearing: the local env has been one
command away from mutating production schema.

`.env.example` is complicit. Its Phase 20 routing block says *"Local dev: any of the three pooled
URLs works; default is `development` branch"* — a permission slip for exactly this defect. It
becomes a mandate.

**Scope is local runtime data isolation only.** Phase 20's locked rule 3 is NOT relaxed:
migrations continue to fan out only via `db-migrate.yml`. An earlier draft of INFRA-05 wrongly
proposed a local migration path; that was corrected in REQUIREMENTS.md. No task here may add,
document, or suggest `npm run db:migrate` against a real branch.

**The credential is not derivable and must not be fabricated.** Task 2 is a blocking checkpoint:
Antoine fetches the pooled URL from the Neon Console and edits `.env.local` himself. The executing
agent must never `Read`, `Edit`, `Write`, `cat`, `grep` or otherwise open `.env.local`. The only
permitted interaction is running `npm run check:local-db-branch`, which prints the hostname and
never the credential.

Purpose: local writes stop landing in production data.
Output: a corrected `.env.example`, a guard that names the branch the local env points at, and a
verified repoint.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Local developer machine → Neon `main` (production) branch | An unattended local script, test run, or seed command executes against live customer data |
| `.env.local` contents → agent context / CI logs / transcripts | The file holds a live production credential; anything that echoes it leaks it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-29-05 | Tampering | local runtime writing to Neon `main` | mitigate | `.env.local` repointed to `development` (Task 2); `check:local-db-branch` exits 1 if the host is ever set back to `ep-icy-boat-alx5o1tz-pooler`. |
| T-29-06 | Information disclosure | production partner data readable from a dev machine | mitigate | Same repoint. Isolation proven by the ISOLATION-PROBE-29 write test rather than asserted. |
| T-29-07 | Information disclosure | guard script leaking the connection string into logs | mitigate | The script prints the hostname only, extracted with `sed`; asserted by the Task 1 criteria that `postgres://` and `neondb_owner` never appear in its output. It also never `source`s `.env.local`, so no secret enters the process environment. |
| T-29-08 | Elevation of privilege | a repoint being read as licence to migrate locally | mitigate | `.env.example` restates locked rule 3 inline at the point of temptation; the checkpoint routes any migration need through `db-migrate.yml --field branch=development`; Task 1 asserts the script contains no `db:migrate`. |
| T-29-09 | Repudiation | ad-hoc schema change with no audit trail | accept | Unchanged from Phase 20 — `db-migrate.yml` remains the single fan-out path with its audit trail and, for `main`, its required-reviewer gate. |
| T-29-SC | Tampering | npm/pip/cargo installs | accept | No packages installed. The guard is bash using coreutils, `grep` and `sed`; only the `scripts` block of `package.json` changes. |
