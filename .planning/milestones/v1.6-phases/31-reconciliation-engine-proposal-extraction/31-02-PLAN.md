<objective>
Build the reconciliation engine: a **pure planner** that reads a source, derives client
candidates, matches them against each other and against the existing registry, and returns a
`ReconciliationPlan` describing everything it *would* create, merge and flag — **writing
nothing**. Phase 32 reuses this engine by supplying a second `ReconciliationSource`.

in separate modules is also what makes criterion 1's "zero rows written" testable rather than
aspirational — the dry run simply stops after this module returns.

<open_question_resolutions>
Three of CONTEXT.md's five open questions are structural to this module and are **decided here**.
Record all three, with their reasoning, in this plan's SUMMARY.

**OQ-3 — Engine granularity: one global pass across all partners.** Decided this way because
`companies` is a global table (CRM-01): a per-partner pass would create a second company row for
a client two partners share, and then immediately need a merge to undo it. IMPORT-03's
SIREN auto-merge is inherently cross-partner, so a per-partner pass could not satisfy criterion
3 at all. The visibility objection a global pass raises — "a global pass sees pairs no single
partner can" — is already answered by D-11: the queue is admin-only precisely because a flagged
pair routinely has its two sides held by different partners. `client_relationships` are still
created per-owner; only the *matching* is global.

**OQ-2 — Canonical name selection: most frequent raw spelling wins; ties break on the earliest
source-row timestamp, then lexicographic ascending.** Determinism is the load-bearing property,
not linguistic quality: D-15's drift comparison diffs a real run against a stored dry-run
report, so a rule that depends on row arrival order would produce phantom drift on every run.
Frequency is the best available signal of the spelling the partner actually uses; the two
tie-breaks make the result a pure function of the source data.

**OQ-1 — Re-run idempotency: a source row already carrying a `client_relationship_id` is
skipped, and every create is independently idempotent.** Two layers:
1. *Row level.* `planReconciliation` classifies any source row whose proposal already has a
   non-null `client_relationship_id` as `skippedAlreadyLinked` and neither re-parses nor
   re-links it. Phase 30's wizard-minted links are the partner's own explicit choice; a
   name-derived guess must never overwrite one.
2. *Entity level.* Company/relationship/contact creation is keyed so a second run over
   unchanged data plans zero creates: SIREN-bearing companies key on `companies.siren`,
   SIREN-less ones on `(name_normalized)` within the existing registry, relationships on the
   existing `client_relationships_company_id_owner_id_uq` index, contacts per D-06.
This is *behavioural* idempotency for the proposals source. IMPORT-07's provenance-id
idempotency for HubSpot remains Phase 32 and is not implemented here.
</open_question_resolutions>

<candidate_grouping_rule>
This is the exact rule the engine implements. It reconciles D-04 (which speaks about two
proposals from the *same* partner) with success criterion 4 (which speaks about two extracted
*clients*), and it is what plans 04, 05 and 06 assume.

**Step 1 — per-owner candidate derivation.** Group source rows by `ownerId`, then by the DB-
computed `name_normalized` of `companyName`. Within one owner and one normalized name:
- rows carrying the same valid SIREN, and rows carrying no valid SIREN, collapse into **one**
  candidate (a partner has one client called "ACME" in their own book);
- if rows under that name carry two or more *distinct* valid SIRENs, the group splits into one
  candidate per distinct SIREN, plus one SIREN-less candidate if any row lacked one. This is
  D-04: the engine cannot tell a typo from two legal entities sharing a trading name, so it
  refuses to choose.

**Step 2 — global resolution across all candidates and the existing `companies` registry.**
- Same valid SIREN → the same company. Automatic, no flag (IMPORT-03, criterion 3).
- Same `name_normalized`, **not** resolvable by SIREN → two distinct companies **and** one
  flagged pair (IMPORT-04, criterion 4). Reason:
  - `differing` — both sides carry a valid SIREN and the SIRENs differ
  - `one_missing` — exactly one side carries a valid SIREN
  - `both_missing` — neither side carries a valid SIREN
- Before emitting a flag, look the canonical pair key up in `company_pair_decisions`. A row with
  a non-null `verdict` suppresses the flag permanently (criterion 5). A row with a null verdict
  is already pending — report it as pending, do not insert a duplicate.
- Where a prior `merged` verdict exists, both sides resolve to `survivor_company_id`.

**Contacts (D-05/D-06/D-07).** A source row yields a contact only when `contactName` is
non-blank (D-05). A row with a phone or email but no name yields no contact and is added to the
plan's `skippedContacts` list with its source row id (D-07) — `contacts.name` is NOT NULL and
inventing a person contradicts CRM-04. Within one candidate's relationship, two extracted
contacts are the same person when their trimmed lowercase emails match; absent an email on
either, when their normalized names match (D-06). Merging fills blank fields and never
overwrites a populated one.
</candidate_grouping_rule>
