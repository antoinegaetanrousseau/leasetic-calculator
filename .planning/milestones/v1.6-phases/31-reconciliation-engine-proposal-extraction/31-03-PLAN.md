<no_transactions_constraint>
**Read this before writing a single line of `merge.ts`.**

The Neon production driver is `drizzle-orm/neon-http`, whose `.transaction()` throws
`"No transactions support in neon-http driver"` at runtime. This is documented in
`src/lib/crm/actions.ts`'s module header and is a hard constraint, not a preference. Do not call
`db().transaction()`. Do not "temporarily" wrap the merge in one.

The merge therefore runs as an **ordered, idempotent, resumable sequence**. Its ordering rule:
*every repoint completes and is confirmed before the loser company is deleted.* A crash at any
point leaves at worst a partially-repointed loser company that still exists — which the next run
of the same merge finishes, because every step is a no-op when already applied.

The atomicity this design cannot provide, and the residual exposure that follows, is recorded in
this plan's `must_haves` and threat model: between step 3 and step 6 a company that has been
emptied of relationships still exists and is visible in the admin registry. That window is
seconds long, admin-only, and self-healing on retry. It is accepted deliberately, not overlooked.

**Step order (implement exactly this):**
1. **Claim the pair.** One statement:
   `UPDATE company_pair_decisions SET verdict='merged', survivor_company_id=$survivor, decided_by=$actor, decided_at=now(), updated_at=now() WHERE id=$pairId AND verdict IS NULL RETURNING *`.
   Zero rows returned means another admin already resolved it (or it never was pending) — abort
   the whole merge and return a `{ ok: false, reason: 'already_resolved' }` result. This is the
   TOCTOU discipline from commit `1d763b9`: the precondition is compiled into the write, never
   checked by a preceding SELECT.
2. **Resolve the compound case.** Find every `owner_id` holding a relationship with *both* the
   survivor and the loser (a self-join on `client_relationships`). For each such owner, the loser
   relationship cannot simply be repointed — it would violate
   `client_relationships_company_id_owner_id_uq`. Instead:
   a. `UPDATE contacts SET client_relationship_id=$survivorRelId, updated_at=now() WHERE client_relationship_id=$loserRelId`
   b. `UPDATE proposals SET client_relationship_id=$survivorRelId WHERE client_relationship_id=$loserRelId`
      — this UPDATE's `.set(...)` object contains **only** `clientRelationshipId`. It must not
      contain `inputs`, `params_snapshot`, `computed` or `schema_version`: `proposals.inputs` is
      immutable (ARCHITECTURE §2.5 Option A, CRM-05).
   c. `DELETE FROM client_relationships WHERE id=$loserRelId` — now provably empty of contacts
      and proposals.
3. **Repoint the remaining relationships.**
   `UPDATE client_relationships SET company_id=$survivor, updated_at=now() WHERE company_id=$loser`.
   After step 2 no owner collision remains, so this cannot violate the unique index.
4. **Repoint the decision-row references.** `UPDATE company_pair_decisions SET company_a_id=$survivor WHERE company_a_id=$loser`
   and the same for `company_b_id`, so historical rows keep pointing at a live company.
5. **Confirm.** `SELECT count(*) FROM client_relationships WHERE company_id=$loser` must be `0`.
   If it is not, stop, log, and return `{ ok: false, reason: 'incomplete_repoint' }` **without**
   deleting anything. Re-running the merge is then safe and will finish the job.
6. **Delete the loser.** `DELETE FROM companies WHERE id=$loser`. `client_relationships.company_id`
   is `ON DELETE restrict`, so this statement is itself the final proof that step 5's confirmation
   held: if any relationship still pointed at the loser, Postgres rejects the delete rather than
   orphaning it.

`recordKeepSeparate` is step 1 alone, with `verdict='kept_separate'` and no
`survivor_company_id`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → server action | `pairId` and `survivorCompanyId` arrive from the client and are fully attacker-controlled |
| admin session → cross-partner data | the queue renders relationships held by partners other than the caller; CRM-02 makes this an inference-safety question, not just an access-control one |
| action → database with no transaction | a multi-statement merge can be interrupted between any two statements |
