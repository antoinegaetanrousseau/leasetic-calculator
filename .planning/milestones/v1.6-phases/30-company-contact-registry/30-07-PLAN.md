<objective>
Ship `/clients/[id]` — the client record page that answers CRM-06 ("show me everything I have
done for this client") and hosts the CRM-04 contacts editor. `[id]` is a relationship id, never a
company id, and the page's first action after authentication is to prove the caller owns it.

Purpose: this is the IDOR surface of the phase. A partner addresses only their own relationship,
and a probe of somebody else's id must be indistinguishable from a probe of a nonexistent one.

dialog and an `AlertDialog` delete confirmation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `/clients/[id]` path segment → server | a relationship id supplied entirely by the caller |
| contact mutation payload → server action | ids the caller may not own |
| 404-vs-403 response shape → attacker | the distinction itself is a disclosure |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-07-01 | Information Disclosure | IDOR on `/clients/[id]` | mitigate | `getClientRelationshipForOwner(id, session.user.id)` returns null for both not-found and not-owned, and the page calls `notFound()` — never 403, never a redirect (D-18). A test asserts the two cases are indistinguishable (CRM-02) |
| T-30-07-02 | Information Disclosure | contact leakage via fetch-then-hide | mitigate | Contacts and proposals are fetched only after the `notFound()` branch; a test asserts `listContactsForRelationship` has zero calls on the non-owned path, and an acceptance criterion asserts the source ordering (CRM-04) |
| T-30-07-03 | Elevation of Privilege | contact mutation against another partner's relationship | mitigate | All three mutations re-prove ownership inside their own SQL (plan 30-05); the client passes only ids, never an owner |
| T-30-07-04 | Information Disclosure | company-level contact exposure | mitigate | The page addresses a relationship, never a company; there is no company-scoped contact query in the partner-facing modules at all |
| T-30-07-05 | Tampering | destructive action without confirmation | mitigate | Delete goes through `AlertDialog` with an explicit destructive confirm; grep-gated against `window.confirm` in the new tree |
| T-30-07-06 | Information Disclosure | commission envelope (ADMIN-09) | mitigate | The Propositions card reuses `ProposalRow` and the `listProposalsForRelationship` row shape from plan 30-04, which projects no `params_snapshot` and no commission field |
| T-30-07-07 | Information Disclosure | header rendering an em dash for a null SIREN | accept | Cosmetic only; the UI-SPEC omits the chip entirely in headers, which is also the lower-information choice |
| T-30-07-SC | Tampering | npm/pip/cargo installs | mitigate | No package install; `Dialog` and `AlertDialog` are already vendored under `src/components/ui/` |
