<decision_record>
## The gate is discovered server-side, not pre-computed into the page

The won dialog could be told up front whether the company has a SIREN — the page already knows.
It deliberately is not. The dialog submits optimistically and reveals the SIREN field only when
`markProposalWonAction` throws `SIREN_REQUIRED`.

Reasoning: a pre-computed flag is a second source of truth about the gate, and it would go stale the
moment another partner (or an admin, or the reconciliation engine) writes a SIREN onto the shared
`companies` row between page render and submit. Reacting to the server's answer means the gate can
only ever be wrong in the direction of asking for something already present — which the
`siren IS NULL`-guarded inline save handles as a no-op. The `companies` row is shared (CRM-01), so
"the SIREN state at render time" is not a fact this page owns.

## The dialogs are controlled by `ProposalOutcomeControl`, not self-triggering

Following `ContactFormDialog`'s shape (`open` / `onOpenChange` from the parent), not
`CreateClientDialog`'s (own `DialogTrigger`). The control owns which of the two dialogs is open,
because the two triggers sit side by side in one row and only one dialog may be open at a time.
</decision_record>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dialog form → server action | `proposalId`, `date`, `reason`, `siren` cross here from the browser |
| server error → dialog branch | the one place a failure class is distinguished (D-08) |
| shared `companies.siren` → partner input | a value on a row other partners also read |
| derived outcome → render | a value computed from a clock, never stored |
