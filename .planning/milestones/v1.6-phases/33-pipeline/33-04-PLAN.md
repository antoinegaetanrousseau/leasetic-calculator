<decision_record>
## The SIREN_REQUIRED sentinel — a narrow, deliberate exception to bounded-error discipline

`33-PATTERNS.md` flags this and leaves it to the planner. Locked here.

Every other action in this codebase collapses every failure class into one dictionary key
(T-30-05-03) so a caller cannot distinguish "SIREN conflict with another partner" from "database
down". D-08 requires exactly one distinction to survive: the won-outcome submit must be able to
tell the dialog "the company has no SIREN" so the dialog can reveal an inline SIREN field instead
of toasting a dead end.

**Chosen: `markProposalWonAction` throws `new Error(SIREN_REQUIRED)` where
`SIREN_REQUIRED = 'pipeline.error.sirenRequired'`, and throws `new Error('pipeline.toast.error')`
for every other failure class including not-owned, not-found, validation and infrastructure.**

Why this leaks nothing that matters:

1. The distinction is only reachable for a proposal the caller **already owns** — the SIREN
   pre-read is scoped by `proposals.user_id = session.user.id`, so a probing caller who does not
   own the proposal gets the generic error and learns nothing. The two branches are never
   distinguishable across an ownership boundary.
2. The absence of a SIREN on a company the caller holds a relationship with is information the
   caller can already read on `/clients/[id]` (the header renders the SIREN when present). No new
   fact crosses a boundary.
3. `SIREN_REQUIRED` carries no company id, no company name, no other partner's data — it is a bare
   sentinel string.

**This is not a project-wide relaxation.** Two failure classes total, one action. Do not add a
third sentinel, and do not propagate the pattern to `advanceRelationshipStageAction` or
`markProposalLostAction`, which both keep the single bounded key.

## The SIREN pre-read is a UX branch selector, never the authorization

`markProposalWonAction` performs one owner-scoped SELECT to decide which error to raise, then
performs the write with ownership **and** SIREN presence re-proved inside the UPDATE's own WHERE.
The read is not a check-then-act: if the read said "SIREN present" and the SIREN vanished
concurrently, the UPDATE matches zero rows and the action fails closed with the bounded key, and
the DB trigger from plan 33-01 is a third, application-independent layer behind that. This
satisfies T-30-05-05 (no read-then-write authorization) while still giving D-08 its branch.

## Inline SIREN save guards on `siren IS NULL`

`companies` is the **shared** registry (CRM-01) — two partners can hold relationships with the
same company row. A partner filling the gate must therefore only ever be able to fill an *absent*
SIREN, never overwrite one another partner may have entered. The UPDATE carries
`WHERE siren IS NULL` in addition to the ownership join. Zero rows affected is not an error: it
means either "already has a SIREN" (proceed — the won UPDATE will succeed) or "not reachable
through the caller's own relationship" (proceed — the won UPDATE will match zero rows and fail
closed). One statement, idempotent, safe to retry — which is what "no transactions" requires.
</decision_record>
