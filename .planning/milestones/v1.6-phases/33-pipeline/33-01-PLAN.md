<decision_record>
## D-07's DB half is a TRIGGER, not a CHECK — resolved here, in writing

`33-CONTEXT.md` D-07 says the SIREN gate is enforced in **both** the server action and a DB
constraint. The pattern mapper falsified the "constraint" half as literally specified: the
predicate spans `proposals` → `client_relationships` → `companies.siren`, and a PostgreSQL `CHECK`
constraint may only reference columns of the row being checked (no subqueries, no cross-table
joins). A plain CHECK is therefore not buildable.

**Chosen: option (a) — a row-level trigger implementing the cross-table predicate.** Reasoning:

1. It is the only mechanism that satisfies D-07's stated intent (a second, application-independent
   enforcement point) *and* holds under concurrent writes.
2. Option (b) — dropping to a server-action-only gate — is a real weakening of a decision the
   operator made deliberately. D-07's own rationale records that "one write path so a constraint
   is redundant" **already failed once in this project**: Phase 30's single-writer grep gate on
   `proposals.client_relationship_id` had to be widened in Phase 31. Choosing (b) here for
   convenience would repeat exactly that mistake.
3. There is a shape precedent in-tree — `coefficient_history_no_modify` at
   `drizzle/0004_phase12_drafts_and_history.sql:43-47`. It is a shape precedent only: that trigger
   is an immutability guard, this one is a cross-table business-rule gate. Task 2 is therefore the
   phase's least-precedented DDL and is hand-written into the migration exactly as `0008`'s
   `LEAST/GREATEST` index and self-pair CHECK were.

**Concurrency:** the trigger function reads the company row with `FOR SHARE`, so a concurrent
`UPDATE companies SET siren = NULL` on that row blocks until the `proposals` write commits. The
gate can only ever fail *closed* (a SIREN written concurrently makes a retry succeed; a SIREN
removed concurrently makes the write fail) — never open.

**Cost:** both triggers carry a `WHEN` clause, so they do not execute for any write that is not
setting `outcome = 'won'`. Draft creation, finalization, soft-delete, restore and purge — every
existing `proposals` write path — pay nothing.
</decision_record>
