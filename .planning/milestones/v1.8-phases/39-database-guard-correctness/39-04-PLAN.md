<objective>
Rewrite the bash guard so it validates the DATABASE_URL the command about to run will actually
open, and gate `npm run build` and `npm run start` behind it (D-01, D-04).

Purpose: this is the direct fix for the 2026-09-06 incident. `npm run check:local-db-branch` printed
"OK: development branch" while `npm run start` served `ep-icy-boat-alx5o1tz-pooler`, because the
guard hardcodes `ENV_FILE=".env.local"` at line 24 while `@next/env` resolves `.env.production.local`
at higher precedence.

**The subtle half of the fix, which an executor will miss if it is not stated plainly:** it is not
enough to make the guard read `$NODE_ENV`. When `prestart` runs, `NODE_ENV` is unset in the hook's
own environment — `next start` sets it to `production` only after the hook has finished. A guard
that trusted its ambient `NODE_ENV` would resolve the development order, report OK, and the incident
would repeat verbatim. The hooks therefore pass `--node-env production` explicitly, because that is
what the guarded command will run under.

Output: a rewritten `scripts/check-local-db-branch.sh` and two npm lifecycle hooks. The fixture and
differential tests that prove it are plan 39-05.
</objective>

<interface_contract>
The guard's CLI and output contract is fixed here; plan 39-05 asserts against it.

**Invocation:** `bash scripts/check-local-db-branch.sh [--node-env <env>] [--root <dir>]`
- `--node-env <env>` — the NODE_ENV the GUARDED command will run under. Precedence for the
  effective value: this flag, else `$NODE_ENV` from the environment, else `development`.
- `--root <dir>` — directory to resolve env files against. Defaults to `$(dirname "$0")/..`
  (the repo root, preserving today's behaviour). Exists so the fixture test can point the guard at a
  temp dir; the npm hooks never pass it.
- An unknown flag is a usage error: exit 2 with a usage line. Fail closed, never ignore.

**Candidate order** — must equal `envFileOrder` in `scripts/_env-precedence.ts`:
for `--node-env test`: `.env.test.local`, `.env.test`, `.env`; for any other value X:
`.env.X.local`, `.env.local`, `.env.X`, `.env`. First file that assigns a non-empty `DATABASE_URL`
wins. A non-empty `DATABASE_URL` already in the environment beats every file, with source
`process.env`.

**Exit codes and first-line output tokens** (assertions target these tokens plus the hostname and
the `from <source>` fragment, never the whole line):
| Situation | Exit | First token | Must also contain |
|---|---|---|---|
| No candidate file exists under `--root` | 0 | `SKIP:` | the resolved node-env |
| Files exist, none assigns DATABASE_URL | 1 | `ERROR:` | the list of files checked |
| Resolved host is the `development` branch | 0 | `OK:` | hostname, `from <source>` |
| Resolved host is `localhost` / `127.0.0.1` | 0 | `OK:` | hostname, `from <source>` |
| Resolved host is the `preview` branch | 0 | `WARN:` | hostname, `from <source>` |
| Resolved host is the `main` branch | 1 | `ERROR:` | hostname, `from <source>`, `PRODUCTION` |
| Resolved host matches no record | 1 | `ERROR:` | hostname, `from <source>` |
| Value has no `user@host` segment | 1 | `ERROR:` | `from <source>` |
| Unknown flag | 2 | `USAGE:` | — |

`<source>` is a bare filename (`.env.production.local`) or the literal `process.env`. Nothing else
about the connection string is ever printed.

| Boundary | Description |
|----------|-------------|
| env files on disk → guard process | guard reads developer secrets as text; sourcing them would execute arbitrary shell and export the secret |
| guard stdout → transcript / issue tracker | the guard's output is explicitly designed to be pasteable |
| npm lifecycle hook → guarded command | the hook and `next build`/`next start` do not share a NODE_ENV; a mismatch here is a silent fail-open |
| CI / Vercel runner → guard | these legitimately target production; blocking them is a self-inflicted outage |
