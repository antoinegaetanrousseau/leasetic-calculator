<decision_record>
**The momentum queries are a NESTED `Promise.all` inside the page's existing
one**, entered through an `isAdmin ? null : Promise.all([...])` ternary. The
ternary never evaluates its query calls for an admin, so D-15's "no query fires"
is satisfied by evaluation order rather than by a discarded result. Nesting
keeps the page at ONE round of queries (the discipline `page.tsx`'s existing
comment states) and keeps tuple typing intact — a conditionally-built flat array
would need a cast, and a cast in the data path of a privacy-critical surface is
worse than the alternative it avoids.

**`getNowMs()` moves ABOVE the `Promise.all`.** The week window is a query
argument now, so the clock must be read before the queries rather than after.
`requireUser()` remains the first `await` — the existing "requireUser is index 0
in callOrder" assertion still holds because `getNowMs` is not recorded there.

**`page.test.tsx` Test 6's `expect(src).not.toMatch(/role\s*[!=]==/)` is
NARROWED, not deleted.** Its intent was "the chase list's admin behaviour must
not come from a role branch", which remains true and remains testable
behaviourally: `listRelationshipsNeedingFollowUp` is still called
unconditionally, with the admin's own id, and still returns `[]`. The blanket
source regex was a proxy for that intent and now contradicts D-15. Replaced with
the behavioural assertion plus a retained `not.toMatch(/requireAdmin/)`, and the
reasoning recorded in the test's own comment so a future reader does not
"restore" it.
</decision_record>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session role → query execution | The only place in the phase where a role decides whether a query runs. An admin reaching the queries is not a data leak by itself (they own nothing) but IS an inference tell about the feature's existence and applicability. |
| session user id → owner predicate | `userId` must come from the session object and nothing else. A search param or header supplying it would turn an owner-scoped query into an arbitrary-owner query. |
| page composition → what a partner can infer | The card sits beside the metric tiles and the chase list. Nothing in this phase may aggregate across those surfaces in a way that reveals another book. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-05-01 | Information disclosure (admin inference tell) | `page.tsx` call site | mitigate | `isAdmin ? null : Promise.all([...])` means the query calls are never evaluated for an admin, and `{!isAdmin && momentum && <MomentumCard …/>}` means no DOM node exists. Tested at both levels: `toHaveBeenCalledTimes(0)` on all three mocks AND absence of the zero-state copy from the rendered text (D-15). |
| T-35-05-02 | Spoofing / parameter injection | `userId` passed to the momentum queries | mitigate | `userId` is derived from `session.user.id` only; the page accepts no search param or header for it. Asserted by the "first argument is `USER_ID`" test, mirroring the existing T-34-09-02 assertion for the chase list. |
| T-35-05-03 | Elevation of privilege | role destructuring | mitigate | `role` comes from `requireUser()`, which re-reads it from the database per request (AUTH-16's secondary check), so a stale cookie-cached role cannot grant or hide the surface incorrectly. No new auth call is introduced. |
