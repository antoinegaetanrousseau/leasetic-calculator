<decision_record>
**The `perdu` ordinal trap — the single most likely defect in this plan.**
`PIPELINE_STAGES` is ordered `prospect, qualifie, proposition_envoyee,
negociation, perdu, signe, debloque`. `perdu` therefore sits at a HIGHER index
than `negociation`, so a naive "target index > source index means forward" test
classifies `negociation → perdu` as progress — which would hand a partner the
exact gaming route D-11 closes ("a partner could hold a streak by moving deals
to Perdu"). The progress predicate carries an explicit `toStage <> 'perdu'`
conjunct for this reason, and Task 2 has a dedicated regression test for it.

**Accepted asymmetry:** `perdu → negociation` (reopening a dead deal) has a
LOWER index and therefore does not count as progress. This follows
`35-PATTERNS.md`'s literal rule ("a lower index is backward/no-count"). It is
still SHOWN in the week's movements. Recorded rather than silently decided.

**`fromStage IS NULL`** (a relationship's first-ever stage write) counts as
forward — there is no "backward" without an origin (`35-PATTERNS.md`).

**No new index.** `relationship_events_relationship_id_occurred_at_idx` is
composite on `(client_relationship_id, occurred_at)` and does not serve an
owner-wide scan. Adding one would be a migration and would reopen D-23.
Production holds a near-empty `relationship_events` table (ROADMAP measured
constraint #1), so the scan cost is negligible today. Record it as a known
future tuning point; do not add it here.
</decision_record>

   `lte`, so the Sunday-to-Monday boundary cannot double-count.
   Select `eventId`, `relationshipId`, `companyName`, `kind`,
   `toStage` (`payload->>'toStage'`, null for a finalized proposal),
   `occurredAt`, and `total: sql<number>\`COUNT(*) OVER ()\`` — the window

   rows and the full window count that the "+ N autres" line needs. Order by

   `to_char(date_trunc('week', occurredAt AT TIME ZONE <tz>), 'YYYY-MM-DD')`

   the keys returned here are directly comparable to

   Both filters live inside the aggregate, so a single scan answers both axes.
   Coerce both with `Number(rows[0]?.x ?? 0)`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session → query layer | `ownerId` arrives from an already-authenticated session. Every statement in this module must re-establish ownership in SQL rather than trusting that the caller checked. |
| partner A's data ↔ partner B's data | `relationship_events` has no owner column of its own — ownership lives one join away on `client_relationships.owner_id`. A dropped or mis-keyed join silently returns the whole table. This is the phase's principal leak surface. |
| database → aggregate | A COUNT or a week key computed across owners is itself a cross-partner disclosure even though it names nobody (30-SECURITY.md's inference standard). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-02-01 | Information disclosure (cross-partner, direct) | all three exported functions | mitigate | `eq(schema.clientRelationships.ownerId, ownerId)` is the first conjunct of every WHERE, in the SAME statement as the select, reached through an `innerJoin` from `relationship_events` (D-21). A comment-stripped source guard asserts exactly three occurrences; the mutation-verified integration test in 35-04 proves it FILTERS rather than merely composes. |
| T-35-02-02 | Information disclosure (cross-partner, by inference) | `getBadgeCountsForOwner` | mitigate | Both aggregates are computed inside a statement already restricted to one owner, so no denominator, average, rank or peer total can be produced. No function accepts a cohort or comparison parameter, and none may be added — GAME-04 forbids it permanently, not merely in this release. |
| T-35-02-03 | Information disclosure (inference via the timeline) | `listProgressWeekKeysForOwner` | mitigate | Returns only week keys for the caller's own book, unbounded in time but bounded in ownership. A week key set for a foreign owner would reveal that partner's working rhythm; the same owner join prevents it. |
| T-35-02-04 | Tampering / gaming the metric | `isProgressEvent` | mitigate | The predicate excludes `perdu` explicitly and requires a strictly increasing stage index, so a partner cannot manufacture a streak by cycling a deal into Perdu (D-11) or by adding notes (D-01). Regression-tested at source level here and behaviourally in 35-04. |
| T-35-02-05 | Elevation of privilege | admin reaching partner data | mitigate | The module has no role branch and no admin path. An admin id passed in would match no `client_relationships.owner_id` row and yield empty aggregates — but the real control is the call-site gate in 35-05 (D-15), so no query fires for an admin at all. |
| T-35-02-06 | Repudiation / data loss | derived badges | accept | `relationship_events` is `ON DELETE cascade`, so deleting a client can drop a badge (D-07's recorded known limit). Accepted: deletion is rare and deliberate, a reversal is neither, and mitigating it would require the persisted state D-03/D-23 forbid. |
| T-35-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install occurs in this plan. No new dependency is added; every import resolves to an existing workspace module or an existing `package.json` dependency. |
