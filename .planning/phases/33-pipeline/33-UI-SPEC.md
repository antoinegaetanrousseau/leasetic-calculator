# Phase 33 — UI Design Contract

> Visual and interaction contract for Phase 33 (Pipeline). Generated by gsd-ui-researcher,
> verified by gsd-ui-checker.

**Requirements covered:** PIPE-01, PIPE-02, PIPE-03, PIPE-04, PIPE-05.

**Language:** French is the product default; every string below needs both `fr` and `en`
dictionary entries (`_EnHasAllFrKeys` compile-time parity, same discipline as `30-UI-SPEC.md` /
`31-UI-SPEC.md`). Tone: short, sentence case, muted subtitle sentences ending in a period,
UPPERCASE only for table/column-style eyebrows — unchanged from prior phases.

**Locked decisions this spec builds on, not re-derives:** D-01…D-12 in `33-CONTEXT.md`. Quoted
inline where a specific decision drives a specific pixel/copy/behavior choice, never re-argued.

## Scope Boundary (read first)

### In scope — two surfaces

1. **The pipeline board** (PIPE-01, PIPE-02, PIPE-04) — a new partner-facing route, a seven-lane
   kanban built on `src/components/reui/kanban.tsx`, drag (or keyboard-move, or the mobile
   stage-picker) to advance a relationship's stage.
2. **Proposal outcome capture + the SIREN gate** (PIPE-03, PIPE-05) — new controls on the existing
   `/clients/[id]` proposal list (Phase 30's `ProposalRow` + its `actionsSlot`), not a new page.

### Explicitly out of scope for this document

| Item | Why it's not here |
|---|---|
| Relationship timeline, manual notes, next-action date, chase list | ACTV-01..05 — Phase 34. |
| Any streak, badge, target or "what moved recently" surface | Deferred to Phase 35 (D-11, D-12's forward-looking constraint). This board renders **exactly two** motivating elements: conversion rate and stage counts. |
| A "last activity" field on the pipeline card | Phase 34 owns activity data; nothing populates it in v1.6. |
| An edit/undo flow for an already-decided proposal outcome | Not in PIPE-03's stated scope (won/lost/unanswered **with a date and optional reason**); inventing a revision flow would be scope creep. |
| Configurable stages, an admin escape hatch for late stages, a team-level metric | Rejected in D-02/D-04/D-12 respectively. |

## Color

Per [`UIC-03`](../../codebase/UI-CONVENTIONS.md) — same tokens, same 60/30/10 discipline, same
exhaustive per-surface reserve list. Derived mechanically (`grep -o -- "--[a-z-]*: *var(--brand-
accent)" app/globals.css`), not from memory — the seven accent-aliased tokens are `--primary`,
`--ring`, `--sidebar-primary`, `--sidebar-ring`, `--gd`, `--gd-text`, `--green`.

| Role | Token | Usage on this surface |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background |
| Secondary (30%) | `--card` | Kanban cards, dialogs, the conversion-rate `MetricTile` |
| Accent (10%) | `--primary` / `--ring` / `--sidebar-ring` | **Four uses, enumerated below.** |
| Feedback (not accent) | `--success` / `--destructive` / `--muted` families | Outcome badges — see the correction note below; these are **not** brand-accent uses |

**Accent reserved for (exhaustive list, four items):**

1. **Focus ring / focused-control border** — `focus-visible:ring-ring/50` in the base class of
   every `Button`/`Input`/`Select` this surface renders (dialog fields, dialog buttons, the
   mobile stage-picker `Select`). `--ring` aliases `--brand-accent`. The single widest-reaching
   accent use here, as on every prior phase's surface.
2. **Sidebar nav focus ring** — the new "Pipeline" entry renders through `SidebarMenuButton`,
   whose base class is `ring-sidebar-ring … focus-visible:ring-2`. Tabbing to it paints a 2px
   accent ring (same mechanism `31-UI-SPEC.md` documented for "Réconciliation").
3. **Card company-name link hover** — `hover:text-primary` on the kanban card's company-name
   link to `/clients/{id}` — the same convention `31-UI-SPEC.md`'s pair-review card used for its
   own company-name links.
4. **"Marquer gagné" dialog confirm button** — `Button` default variant (`bg-primary
   text-primary-foreground`), the one genuinely primary-filled control on this surface. This is
   the deliberate positive-outcome confirm action; see § Copywriting for why "Marquer perdu"'s
   confirm is `variant="outline"` instead, not the same treatment.

**Also accent-derived, surface-wide (not a per-element choice, not new):** `app/globals.css`'s
base layer applies `outline-ring/50` to any element whose focus outline is browser-default. No
element on this surface relies on that path — every focusable control here is a shadcn primitive
that sets its own focus-visible ring.

**Verified not to render accent here:** `Button variant="default"` anywhere except the one Won-
confirm button named above; `Badge` default variant (every badge on this surface is `outline`,
`secondary`, or the outcome-specific classes below — never unstyled `Badge` default, which would
be `bg-primary`); `--sidebar-primary` (zero call sites in the tree, confirmed in `31-UI-SPEC.md`
and unchanged); `--gd`/`--gd-text`/`--green` (appear in no primitive this surface renders).

**Correction anticipated, stated up front rather than discovered later (the exact mistake
`31-UI-SPEC.md`'s Color section made four times, corrected here in one pass):** outcome badges
use `--success`/`--destructive`/`--muted`, **none of which alias `--brand-accent`** — `--success`
is `var(--color-emerald-500)`, a separate feedback token, not the brand accent under another
name. This is the identical distinction `UIC-03` itself already records for `StatusChip
variant="active"` (`bg-success/15`, not accent). Do not count the outcome badges below against
the accent budget.

| Outcome / lane state | Classes | Token family |
|---|---|---|
| Proposal outcome: won | `bg-success/15 text-success-foreground` | Feedback (success), not accent |
| Proposal outcome: lost | `bg-destructive/15 text-destructive` | Feedback (destructive) |
| Proposal outcome: unanswered (derived, D-06) | `bg-muted/50 text-muted-foreground` | Neutral |
| Reserved-lane badge ("Réservé") | `Badge variant="secondary"` (no custom classes) | Neutral, shadcn default |
| Reserved-lane background wash | `bg-muted/40` | Neutral |
| Reserved-lane drag-refusal ring (drag in progress only) | `ring-destructive/40` | Feedback (destructive), applied only while a drag is active — see § Kanban Mechanics |

## Access & Non-Leakage Contract (read before implementing anything below)

1. **Own-book only, always (D-12).** The board's query reuses `client-relationships.ts`'s
   owner-scoped pattern (D-10) — `ownerId` compiled into the WHERE, exactly like `/clients`. No
   partner-facing count, total, or wording anywhere on this surface may reveal anything about
   another partner's book. This includes the conversion-rate tile: its numerator and denominator
   are **both** computed only from `session.user.id`'s own relationships/proposals — never a
   global or team denominator. There is no leaderboard, ranking, or team aggregate anywhere on
   this surface (D-12, rejected explicitly).
2. **`requireRelationshipHolder()` gates the route, first, before any data access** — same gate
   `/clients` already uses, same `notFound()`-on-admin behavior, no `requireAdmin()` anywhere on
   this surface (this phase is partner-facing, not an admin tree addition).
3. **A `sales`-role user reaches this exact surface, unchanged (ROLE-02).** No role branch, no
   conditional rendering keyed off role — the same owner-scoped query and the same board render
   for `partner` and `sales` alike, matching the precedent `partnerNavItems()` already
   established for `/clients`.
4. **The SIREN gate never blocks quoting or early-stage advancement (D-07/D-08).** It fires
   exclusively inside the "Marquer gagné" dialog. Dragging a relationship through any stage,
   including into `Perdu`, is never gated by SIREN presence. Creating or sending a proposal is
   never gated by SIREN presence. If an implementation accidentally couples the SIREN check to
   anything other than the won-outcome submit, that is a defect against this contract.

## The Decoupling Contract (D-04 — the single easiest thing to get wrong)

**Marking a proposal `won` never writes to `client_relationships.stage`, under any circumstance.**
The relationship's stage and a proposal's outcome are two independent facts, changed through two
independent interactions (drag/keyboard-move/mobile-picker vs. the outcome dialogs), and nothing
in this phase's server actions may couple them. A partner who marks every proposal for a
relationship "won" and never drags that relationship's card past `Négociation` has produced a
**correct**, expected state under D-04 — `Signé`/`Débloqué` stay reserved for the future
contract-tool integration regardless of what proposals say. Do not add an "auto-advance on win"
convenience; D-04 rejected it explicitly, on the reasoning that it would make `Signé` mean "a
partner said so," which is precisely what PIPE-02 reserved it against.

## Kanban Mechanics (D-09 — the core of this phase's interaction design)

### The three lane states, and why they must look different

| State | Applies to | Visual treatment | Accepts drops? |
|---|---|---|---|
| **Active** | Prospect, Qualifié, Proposition envoyée, Négociation | Normal weight: `text-foreground` header, real count badge (`Badge variant="outline" className="bg-background"`, matches the vendored deal-pipeline precedent) | Yes |
| **De-emphasized, terminal** | Perdu | Muted header (`text-muted-foreground`, no bold), real count badge (same styling as Active — the count is meaningful, never suppressed, per UIC-08), card list **collapsed by default** behind a disclosure ("Afficher les dossiers perdus ({n})" / "Masquer") | Yes — same as Active. `Perdu` is partner-settable (D-03), not system-owned; only its *default visibility* is reduced, never its function. |
| **Reserved, system-owned** | Signé, Débloqué | `bg-muted/40` wash on the whole column, `text-muted-foreground` header, `BanIcon` (16px) beside the label, count badge **replaced** by a `Badge variant="secondary"` reading "Réservé" (never a "0" — a real zero would read as "empty and waiting to be filled"; D-04 requires it read as "not yet reachable"), plus a one-line muted caption in place of where cards would render: "Réservé à une intégration future." | **No** — see below |

Conflating "Perdu, collapsed" with "reserved, disabled" is the failure mode this table exists to
prevent: `Perdu` still fully participates in normal pipeline mechanics (drag in, drag out,
uncollapse to see its cards); the two system-owned lanes categorically do not.

### Why `Perdu` stays 280px wide but starts collapsed, not narrowed

Narrowing a lane (as done for the reserved lanes) reads as "this lane matters less structurally."
`Perdu` is a full, real stage a partner actively uses (D-03: "the vocabulary otherwise had
nowhere to put a dead deal") — it needs full card width when a partner does look at it. Its
de-emphasis is about **attention**, not **capability**: collapsed-by-default (so a glance at the
board doesn't lead with losses) is the correct mechanism; a narrower column would also visually
constrain its cards for no reason once expanded.

### Reserved-lane drop refusal — three layers, because a silent snap-back is not enough (D-09.1)

A drag that just snaps back with no explanation is explicitly called out in `33-CONTEXT.md` as
**worse** than no affordance at all. Three layers, all always active together, not alternatives:

1. **Always-on visual muting** (not drag-dependent) — the `bg-muted/40` + `BanIcon` + "Réservé"
   badge treatment in the table above renders whether or not a drag is in progress. A partner
   scanning the board sees the lane reads differently before ever attempting to drag into it.
2. **Drag-in-progress feedback** — while any drag is active (`Kanban`'s root sets
   `data-dragging="true"`, per `kanban.tsx`), each reserved `KanbanColumn` (which already carries
   `data-disabled="true"` from its own `disabled` prop) gets `ring-2 ring-destructive/40` and
   `cursor-not-allowed` for the duration of the drag. `Tailwind`'s `group-data-*` variant does not
   cleanly express a two-element descendant-attribute combinator here (the `data-dragging`
   attribute lives on `[data-slot=kanban]`, a different element than
   `[data-slot=kanban-column][data-disabled=true]`); the simplest correct implementation is a
   plain CSS rule in `app/globals.css`:
   `[data-slot="kanban"][data-dragging="true"] [data-slot="kanban-column"][data-disabled="true"] { ring: 2px solid var(--destructive)/40%; cursor: not-allowed; }` —
   or the Tailwind-in-CSS equivalent (`@apply`). This is plumbing, not a new token; no color or
   spacing value here is new (`--destructive` and the 2px ring width are already in the app's
   vocabulary).
3. **Refusal toast on the drop attempt itself** — the `onMove` handler checks
   `overContainer` against the reserved-stage set and, if matched, does **not** call
   `setColumns` (so the card visually settles back where it started — dnd-kit's own drop
   animation handles the return motion) and instead shows the drop-refused toast (§ Copywriting).
   Because `onMove` fires identically regardless of whether the drag was initiated by mouse,
   touch, or the `KeyboardSensor` (already wired into `kanban.tsx`'s `useSensors` call), **this
   third layer protects keyboard users automatically** — no separate keyboard-specific refusal
   path is needed.

### The write is one deliberate mutation, not a drag-handler side effect (D-09.2)

`Kanban`'s `onMove` prop is the correct integration point: in `onMove` mode, the component does
**not** auto-reshuffle the `value` prop during `dragOver` (`kanban.tsx`'s `handleDragOver` early-
returns when `onMove` is set) and does not call `setColumns` for item moves at all — "the
consumer owns applying the item move" (verbatim from the component's own comment). Concretely:

1. On a legal drop (`overContainer` is not reserved), the `onMove` handler calls a single server
   action — e.g. `advanceRelationshipStageAction(relationshipId, toStage)` — that performs one
   `UPDATE … WHERE id = $1 AND owner_id = $2` (the same ownership-re-proved-inside-the-statement
   discipline `30-05-PLAN.md`/T-30-05-05 established; no read-then-write).
2. The board updates optimistically (`setColumns` called immediately alongside the action call,
   not gated on its resolution — a moved card should feel instant) and rolls back to the prior
   `value` on action failure, pairing the rollback with the generic failure toast.
3. **No success toast on an ordinary drag** — the card's new position on the board is itself the
   confirmation; stacking a toast on top of an already-obvious visual change is the kind of
   redundant feedback this codebase avoids elsewhere (contrast with the modal dialogs below,
   where a toast is the *only* feedback since the modal itself just closed).
4. This single-mutation write path is exactly the shape Phase 34's ACTV-02 ("stage change …
   recorded automatically, with actor and timestamp") will want to hook an audit-log write onto
   later — naming the action clearly and keeping it as the sole write path for stage changes
   (never a bulk/batch endpoint) is worth doing now even though ACTV-02 itself is out of this
   phase's scope.

### Column reordering is not offered

The seven stages are a fixed, code-level enum (D-02) — there is no "add a stage" or "reorder
stages" capability, unlike the vendored `deal-pipeline.tsx` reference (which offers both, via
`AddStageButton` and a draggable `KanbanColumnHandle`). **Do not render `KanbanColumnHandle` or
an add-stage control anywhere on this board.** Columns render in the fixed D-01 order and nothing
else.

### No per-stage color-coded dots

The vendored `deal-pipeline.tsx` reference colors each column with an arbitrary hue dot
(red/amber/emerald). This project runs a **single-accent** color system (UIC-03) specifically to
avoid palette proliferation; inventing five-plus new hues for lane identity would be exactly the
kind of drift UIC-03 exists to prevent. Column identity here is carried by **label text and
position only** — no colored dot indicator, on any lane.

### Item drag must be keyboard-operable — a specific risk in the vendored primitive to verify

`kanban.tsx`'s `KanbanItem` spreads its dnd-kit `attributes` (which include `tabIndex`,
`role="button"`, `aria-roledescription`) onto **its own root node**. But drag-start
**`listeners`** (the `onPointerDown`/`onKeyDown` handlers that actually activate a drag) are
exposed only via `ItemContext` to a separately-rendered `KanbanItemHandle`. The vendored
`deal-pipeline.tsx` reference composes these as **two different DOM nodes**
(`<KanbanItem>{...}<KanbanItemHandle>{card}</KanbanItemHandle></KanbanItem>`) — meaning the
focusable node (`KanbanItem`, carrying `tabIndex`) and the node whose `onKeyDown` actually starts
a keyboard drag (`KanbanItemHandle`, carrying `listeners`) are not the same element. **This is a
real risk that keyboard drag silently does not work if copied verbatim** — Tab would land on the
card, but pressing Space/Enter there may do nothing.

**Required outcome (acceptance criterion, not implementation prescription):** Tab to a
relationship card → visible focus ring → Space/Enter picks it up → Arrow keys move it between
columns → Space/Enter drops it → Escape cancels and returns it to its origin column. Verify this
manually (or with a Playwright keyboard-interaction test) before considering PIPE-01/04 done. If
the split-node composition above breaks it, the fix is to make the card's own root the element
that carries **both** `attributes` and `listeners` — e.g. render the card directly inside
`KanbanItem` without a nested `KanbanItemHandle`, or render `KanbanItemHandle` such that it
receives the outer `tabIndex`/`aria-*` as well (a `render` prop composition). Exact wiring is an
executor decision; the keyboard-operable outcome is not optional.

The 10px `MOUSE_SENSOR_OPTIONS.activationConstraint.distance` already built into `kanban.tsx`
means a plain click (no pointer movement) still fires as a click/navigation to
`/clients/{relationshipId}` rather than being swallowed by drag activation — no extra click-vs-
drag disambiguation logic is needed for the mouse path.

### Laptop-width behavior — horizontal scroll inside the existing capped `<main>`

Seven lanes at 280/280/280/280/280/220/220px plus 16px gaps total roughly **2040px** — wider than
`Shell`'s 1100px-capped `<main>` (UIC-09) at any realistic laptop width. **Do not** widen or
override `Shell`'s `<main>` to fit the board — per UIC-09, no per-page `maxWidth` override.
Instead, wrap the board in a horizontally-scrolling region **inside** the capped main, exactly the
pattern the vendored `deal-pipeline.tsx`'s `BoardScrollArea` already demonstrates: a Base UI
`ScrollArea` (`overflow-x-auto`) with a horizontal `Scrollbar`/`Thumb`, content sized `w-max`. The
board scrolls; the page shell does not change width. This is the direct, concrete answer to "how
does the board behave at laptop width."

### Mobile — no drag-and-drop; an accordion list + explicit stage-picker instead

Below the `md` breakpoint (768px), touch-drag across a seven-column board is not a workable
interaction (per the phase brief's own framing) and is **not attempted**. Instead:

- `hidden md:block` on the kanban board; `block md:hidden` on a `PipelineMobileList` alternative,
  both fed by the same server-provided grouped-by-stage data — one route, one data fetch, two
  render paths.
- The mobile list is a stack of disclosure sections, one per stage, in the same fixed D-01 order,
  each showing the stage label + count badge in its trigger and a vertical list of relationship
  cards (same card content as the board) when expanded. Reserved stages render the same "Réservé"
  treatment, non-expandable (no disclosure caret — there is nothing to expand into).
- Each mobile card carries an explicit **"Changer d'étape"** control (a shadcn `Select`, not a
  drag gesture) listing the five partner-settable stages, plus the two reserved stages rendered
  as disabled options suffixed "(réservé)" so a partner can see they exist without being able to
  select them. Selecting a new stage calls the **same** `advanceRelationshipStageAction` the
  desktop drag calls — one write path, two entry points, matching D-09.2's "single deliberate
  mutation" regardless of which surface triggered it.
- Tapping a card (outside the stage-picker control) still navigates to `/clients/{id}`, same as
  desktop.

### 1. The pipeline board — `/pipeline` (PIPE-01, PIPE-02, PIPE-04)

Composition (server component page fetching data; a client component owns the board/list and its
local drag/disclosure state):

1. `<PageHero title={t('pipeline.page.title', lang)} subtitle={t('pipeline.page.subtitle', lang)} />` — no `actions` prop (nothing to create from this page; clients are created from `/clients`).
2. **Zero-relationships state** — if the partner holds no relationships at all, replace the metric
   tile + board with a single `Empty`/`EmptyDescription` (+ `EmptyTitle`, two-line case per
   UIC-05's "genuinely necessary" exception, since this needs to say *why* the board is empty and
   *what to do*) with a `BuildingIcon` and a CTA linking to `/clients`. **Never** the empty
   7-lane board with no guidance for a partner who has nothing yet.
3. **Conversion-rate `MetricTile`** — one tile, not three (D-11 permits exactly this one metric
   plus the column counts; no other tile). Reuses `MetricTile` verbatim, `variant="total"` (its
   existing `text-primary` color mapping fits a headline stat; no new variant added to the
   component). `label` = "Taux de conversion", `value` = "{pct} %", `sublabel` = "{won} gagnée(s)
   sur {total} proposition(s)". Rendered as a single tile, not a 3-tile grid — the existing
   Partner Home grid CSS is not reused wholesale, just the tile component.
4. **The board** — `hidden md:block`, `Kanban` root wrapping a `ScrollArea`-based
   `KanbanBoardPrimitive`, seven `KanbanColumn`s in fixed D-01 order, no `KanbanColumnHandle`, no
   add-stage control. See § Kanban Mechanics for the full interaction contract.
5. **Mobile list** — `block md:hidden`, `PipelineMobileList` per § Kanban Mechanics.

**Relationship card composition** (`PipelineCard`, used identically on desktop board and mobile
list):

- Rendered inside shadcn `Card size="sm"` (16px padding, `rounded-container` per UIC-04 — no
  radius override, unlike Phase 31's now-closed OPEN-A literal).
- **Company name** — bold link to `/clients/{relationshipId}`, `font-semibold text-[14.5px]
  text-foreground hover:text-primary`.
- **SIREN row** — `text-[13px] text-muted-foreground`, the SIREN value or em dash (UIC-08).
- **Counts row** — "{n} contact(s) · {n} proposition(s)", `text-[13px] text-muted-foreground`,
  real zeros rendered as `0` literally (UIC-08). Both counts come from data this phase's queries
  already have (Phase 30's `contacts`/`proposals` tables via the relationship) — **no** "last
  activity"/"last touched" field; that is Phase 34's ACTV data, not populated by anything here.
- No avatar, no owner badge (a relationship's owner is always the viewing partner themselves —
  showing your own name on every card of your own board is redundant, unlike the admin-only
  pair-review surface in Phase 31 where multiple owners could appear).

**Column header composition** (`PipelineColumnHeader`): stage label (14px/600) + count badge
(real count, `Badge variant="outline" className="bg-background"`) for Active/Perdu columns, or
the "Réservé" `Badge variant="secondary"` + `BanIcon` for reserved columns — see § Kanban
Mechanics' state table for the full rendering split.

### 2. Proposal outcome capture — `/clients/[id]` (PIPE-03, PIPE-05)

Extends the existing Phase 30 page (`app/(authed)/clients/[id]/page.tsx`), **not** a new route.
Each `<ProposalRow>` in the "Propositions" section gains an `actionsSlot` — the exact extension
point Phase 26 built for this class of addition (`draftActionsSlot`/`actionsSlot`, D-06 of that
phase). No change to `ProposalRow`'s own markup or its existing `StatusChip` (lifecycle status is
a separate fact from outcome — both render, side by side, never merged into one chip).

**`ProposalOutcomeControl`** (new, rendered as `actionsSlot`), one of three states per row:

| Row state | Renders |
|---|---|
| No outcome recorded yet, proposal still within validity window | Two `Button variant="outline" size="sm"` triggers: "Marquer gagné" / "Marquer perdu" |
| No outcome recorded, validity window has passed (derived `unanswered`, D-06) | The same two trigger buttons **plus** a muted "Sans réponse" badge (`bg-muted/50 text-muted-foreground`) — the partner can still explicitly decide later; showing the derived label does not remove the ability to override it (D-06: "the partner can set an explicit outcome to override") |
| Outcome recorded (`won` or `lost`) | A single badge only, no buttons — `bg-success/15 text-success-foreground` "Gagné" or `bg-destructive/15 text-destructive` "Perdu". No edit/undo affordance this phase (see Scope Boundary). |

**Won dialog** (`MarkWonDialog`, shadcn `Dialog`):

1. `DialogTitle`: "Marquer cette proposition comme gagnée ?"
2. Fields: **Date de signature** (date input, defaults to today, required) + **Motif
   (facultatif)** (short text, optional).
3. `DialogFooter`: `DialogClose` "Annuler" (`variant="outline"`) + `Button type="submit"` (default
   variant — the one accent-filled control on this whole phase's surface, per § Color) "Confirmer".
4. **Submit calls a server action** (e.g. `markProposalWonAction(proposalId, { date, reason })`)
   which performs the SIREN check server-side **and** relies on the DB CHECK constraint (D-07,
   belt-and-braces).
5. **On success:** dialog closes, toast "Proposition marquée comme gagnée.", `router.refresh()`.
6. **On SIREN-missing failure (D-08 — the gate, composed inline, not a redirect):** the dialog
   does **not** close. It reveals, in place, below the existing (still-filled) date/reason
   fields: the SIREN-gate banner copy, a new **SIREN** input (9-digit validated, same pattern as
   `CreateClientDialog`'s existing SIREN field), and its helper text. The submit button's label
   changes to "Enregistrer le SIREN et confirmer". Resubmitting sends the SIREN **and** the
   already-entered date/reason together — one additional round trip, not a restart, and never a
   navigation away from this dialog. This is the literal shape of D-08: "a dialog at the point of
   failure so the partner adds it and continues."
7. **On any other failure:** generic bounded-error toast (`pipeline.toast.error`), dialog stays
   open with fields intact (same retry-without-re-entering-data discipline `ContactFormDialog`
   already established).

**Lost dialog** (`MarkLostDialog`, shadcn `Dialog` — not `AlertDialog`, because the date field
means it needs form space `AlertDialog` doesn't offer, matching the reasoning `31-UI-SPEC.md`
used for its own Merge flow):

1. `DialogTitle`: "Marquer cette proposition comme perdue ?"
2. Fields: **Date** (defaults to today, required) + **Motif (facultatif)** (optional).
3. `DialogFooter`: `DialogClose` "Annuler" + `Button type="submit" variant="outline"` "Confirmer"
   — **deliberately not `variant="default"`, and not `variant="destructive"` either.** Marking a
   proposal lost deletes nothing (unlike Phase 31's Merge, which does — hence that dialog's
   `destructive` confirm), so the destructive token doesn't apply; but this also isn't the
   positive, brand-colored action Won's confirm is, so it stays neutral rather than borrowing
   the single accent color for a negative business outcome. This is an intentional asymmetry
   between the two dialogs' confirm buttons — not an inconsistency for a checker to flag.
4. Submit calls `markProposalLostAction(proposalId, { date, reason })` — no SIREN gate (D-07
   applies only at `won`).
5. On success: dialog closes, toast "Proposition marquée comme perdue.", `router.refresh()`. On
   failure: generic bounded-error toast, dialog stays open.

## Assumptions (confirm before execution)

1. **A-1 — Route is `/pipeline`, top-level.** If the planner reads D-09/PIPE-04 as wanting the
   board nested under `/clients` instead, the route string is a one-line change; nothing else in
   this contract depends on the exact path. `route-meta.ts`'s tail-matching has no collision risk
   either way since `/pipeline` doesn't share a prefix with `/clients`.
2. **A-2 — Conversion-rate formula is a data-layer decision, not specified here.** This contract
   fixes the **display shape** ("{pct} % · {won} gagnée(s) sur {total} proposition(s)") but not
   whether the denominator is `won + lost` (close rate) or all quoted proposals linked to a
   relationship (true "per-quote" rate implied by PIPE-03's wording). Left to the planner/D-06's
   existing derive-don't-store precedent to resolve; not a UI concern once the shape above is
   fixed.
3. **A-3 — `MetricTile`'s `variant="total"` mapping (`text-primary`) is reused as-is, no new
   variant.** If a future checker or planner prefers a semantically distinct variant name (e.g.
   `'conversion'`) mapped to the identical color, that is a cosmetic rename with zero visual
   change — not a blocker for this contract.
4. **A-4 — `advanceRelationshipStageAction`/`markProposalWonAction`/`markProposalLostAction`
   names are suggestions, not requirements.** Named here only so the planner has continuity with
   Phase 34's future audit-trail hook language (§ Kanban Mechanics, D-09.2 point 4); exact naming
   is implementation discretion.
5. **A-5 — The keyboard-drag verification in § Kanban Mechanics is a hard acceptance gate, not a
   nice-to-have.** If it cannot be made to work within the vendored primitive's constraints
   without disproportionate effort, escalate to the orchestrator rather than silently shipping
   mouse-only drag — the house constraint (UIC-10-adjacent, "a board that can only be operated by
   mouse fails the same standard the Phase 31.1 collapse control was held to") is explicit that
   this is not optional scope.
