<decision_record>
## The headcount table is INSEE's, not the design's example

The design (§ 2) illustrates the point with «"42" renders as "250 à 499 salariés"». In INSEE's
official `tranche_effectif_salarie` code list, `32` is "250 à 499 salariés" and `42` is
"1 000 à 1 999 salariés". The design's example is illustrative of the *mechanism* — codes need a
table — not authoritative about the mapping.

**Chosen: ship the INSEE list, 16 codes (`NN, 00, 01, 02, 03, 11, 12, 21, 22, 31, 32, 41, 42, 51,
52, 53`), and render an unrecognised code as the raw code rather than throwing or blanking.** The
fallback matters more than the table: INSEE has revised this list before, and a partner seeing
"32" is a far smaller failure than a client page that crashes or silently hides the field. A test
asserts the fallback.

## The label tables are French-only data, not dictionary keys

`headcountBandLabel` and `nafSectionLabel` return French INSEE vocabulary, the way a legal-form
code does. They do NOT go through `t()` and do NOT get FR/EN dictionary entries. Reasons: the
values are official French administrative nomenclature with no sanctioned English rendering; the
registry data surrounding them (legal name, address, commune) is French regardless of UI language;
and adding 37 entries × 2 languages to `dictionaries.ts` for a machine-translated approximation
would be worse copy than the original. The *field labels* around them ("Effectif", "Activité") ARE
dictionary keys and were added in plan 34-01.

`src/lib/registry/labels.ts` is a pure module with no `server-only` import, because the client-side
identity panel renders its output.

## D-23's blast radius is FUTURE rows only

`requiredSirenSchema` feeds `clientSiren`, which flows into `proposals.inputs` — immutable per
DATA-01..04. Converging the schema onto `normalizeSiren` changes what a *newly created* proposal
stores (digits-only instead of whatever the partner typed). It does NOT rewrite a single stored
`inputs` blob, and this plan ships no backfill, no migration and no read-time re-normalisation of
existing rows. An acceptance criterion asserts no `drizzle/` file and no `scripts/` file changed.
</decision_record>
