## Four dialogs, one shape

`ContactFormDialog.tsx` is the base for all four, and the details below are load-bearing rather than
stylistic — each is recorded in that file's own comments as a past regression:

- Controlled by the parent via `open` / `onOpenChange` props, with **no `DialogTrigger` inside**
  (`ContactFormDialog.tsx:12-16`). The page owns the open state.
- `type FormValues = z.input<typeof schema>` — the **pre-transform** input type (`:57-59`). Using
  `z.infer` gives the post-transform type and silently breaks the resolver's typing.
- The required-field asterisk is exactly
  `<span className="ml-0.5 text-destructive" aria-hidden="true">*</span>`; a narrower markup was a
  regression once and must not return (`:17-24`).
- Field errors render `t(errors.x.message as DictKey, lang)` inside a `<FieldError role="alert">`
  with `aria-invalid` / `aria-describedby` wired (`:121-135`).
- `<form … noValidate aria-busy={isSubmitting || undefined}>`, every input `disabled={isSubmitting}`.
- On success: `toast.success(...)`, `onOpenChange(false)`, `router.refresh()`. On failure:
  `toast.error(...)` and the dialog **stays open** so the caller can retry without re-entering data
  (`:85-100`).

## The refresh control is a button, not a dialog

`refreshCompanyRegistryAction` takes no user input — the SIREN is already on the row. So the
"Actualiser" control is a `Button` with a pending state, not a dialog. But it consumes a RETURNED
discriminated result exactly the way `MarkWonDialog` does, because its three recoverable outcomes
each deserve different copy:

| Result | Surface |
|---|---|
| `{ ok: true }` | `toast.success('clients.registry.toast.synced')` + `router.refresh()` |
| `{ ok: false, reason: 'not_found' }` | `toast.error('clients.registry.toast.notFound')` — a settled answer; the partner's next move is to correct the SIREN, not to click again |
| `{ ok: false, reason: 'unavailable' }` | `toast.error('clients.registry.toast.error')` — retryable |
| `{ ok: false, reason: 'no_siren' }` | `toast.error('clients.registry.toast.error')`; the control should not have been reachable, because the panel hides it when the company has no SIREN |
| thrown | `toast.error('clients.toast.error')` in the `catch` — never a `.message` comparison |

## Why no dialog here can touch a registry field, stated as a check rather than an intention

D-02 is a structural rule: "a partner-facing form must never be able to write a registry-tier
field." Plan 34-07 enforced the write half (only `registry-sync.ts` names a registry column). This
plan enforces the form half with a grep gate across all four files: none of them may contain
`legalName`, `addressLine`, `postalCode`, `city`, `legalForm`, `nafCode`, `nafSection`,
`headcountBand`, `foundedOn` or `registryState` as a form field name, a `register(...)` argument or
a `defaultValue` key. If a future contributor adds "just an editable city field", the gate fails.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| form field set → writable columns | the surface D-02 constrains; an extra input here is a tier violation |
| client component → server action | caller-supplied values crossing into owner-scoped writes |
| thrown server-action error → client branch | redacted in production; the CR-01 failure mode |
| shared-tier edit → other partners' view | a write whose consequences the acting partner must be told about |
| rendered copy → partner's mental model | strings that could imply a cross-partner view exists |
