<decision_record>
## Every tab fetches server-side, and only the active tab fetches

D-17: "each tab fetches server-side". Two readings are possible — fetch everything and render one,
or fetch only what the active tab needs. The second is chosen:

- The auth gate and `getClientRelationshipForOwner` run for every tab (they establish existence and
  ownership; skipping them would break the 404 contract).
- After the `notFound()` branch, exactly one additional fetch runs, selected on the validated tab:
  Informations → none (the detail row already carries all three tiers after plan 34-05);
  Contacts → `listContactsForRelationship`; Propositions → `listProposalsForRelationship` (+ the
  `deriveProposalOutcome` map the current page already computes); Activité →
  `listRelationshipEvents`.
- The header renders from the detail row only, so it is available on every tab with no extra query.

This keeps the page's cost flat as tabs are added and means a partner sitting on Informations never
causes a timeline read. A test asserts the non-active tabs' queries are NOT called.

## The 404 contract survives the rebuild, word for word (D-16)

D-16 fixes the route: it stays `/clients/[id]`, `[id]` stays a RELATIONSHIP id, and a plain
`notFound()` still covers BOTH not-found and not-owned — the Phase 30 D-18 obscurity rule is
unchanged by this phase.

The current page's doc comment (`page.tsx:32-53`) numbers four steps and states that "order of
operations is the security boundary, not a style preference". The rebuild keeps all four, renumbered
only to insert the tab validation:

1. `requireRelationshipHolder()` — FIRST, before any data access (PITFALLS §7.3). It refuses admins
   via `notFound()`.
2. `getClientRelationshipForOwner(id, session.user.id)` — returns null for BOTH "no such
   relationship" and "exists but owned by someone else".
3. `if (!relationship) notFound();` — not-found and not-owned render byte-identically to a probing
   caller. Never a client-error status that would confirm existence.
4. Validate `?tab=` against an allowlist, falling back to the default. **This happens after the 404
   branch on purpose**: an invalid tab on a relationship the caller does not own must produce the
   same 404 as a valid tab, not a different error, and validation before the gate would be one more
   observable difference.
5. ONLY THEN is the active tab's data fetched, re-scoped to `session.user.id` in its own SQL
   statement.

`export const dynamic = 'force-dynamic'` and the `Metadata` export survive unchanged.

## `?tab=` validation copies the admin partners page, including dropping the default

`app/(admin)/[adminSegment]/partners/page.tsx:47-60` is the enum-allowlist precedent: a
`ReadonlySet` of valid values, and a validator that returns `undefined` for anything else — never a
throw and never a `notFound()`. `PartnersFilterPillTabs.tsx:71-79` shows the matching href builder,
where the DEFAULT tab drops the param entirely so `/clients/[id]` and `/clients/[id]?tab=infos` are
the same URL.

Copy the navigation architecture. Do NOT copy the styling: that component is Phase 18 legacy with
inline `style` objects and raw `rgba(18,150,87,0.10)`. Follow UI-CONVENTIONS (UIC-03 accent reserve,
UIC-04 `rounded-container`, UIC-09 page width) and Tailwind classes as used in the current
`clients/[id]/page.tsx`.

## Files that must NOT move

`tests/server-action-error-contracts.test.ts:88-97` hard-codes
`app/(authed)/clients/[id]/MarkWonDialog.tsx` and `src/lib/pipeline/actions.ts`. The rebuild moves
proposal rendering into a tab, which is a strong temptation to relocate `MarkWonDialog.tsx`,
`MarkLostDialog.tsx` and `ProposalOutcomeControl.tsx` into a `_components/` subfolder.

**Do not.** They stay exactly where they are. If a future refactor genuinely needs to move
`MarkWonDialog.tsx`, that suite is updated in the same commit — an acceptance criterion asserts
`git diff tests/server-action-error-contracts.test.ts` is empty, so an unnoticed move fails the plan.
</decision_record>
