<objective>
Build the private-tier write layer: the three server actions that let a partner record what THEY
know about a relationship — its lead source, its description, a dated note, and the next thing they
intend to do about it.

Purpose: this is D-01's third tier. Everything here is visible to the owning partner only, lives on
`client_relationships` and `relationship_events`, and is structurally unreachable from another
partner's session. It is also the only tier that writes NO audit row — D-03 makes an audit row the
price of a SHARED edit, and these edits are not shared.

Output: `src/lib/relationship/{constants,schemas,actions}.ts` and their tests.
</objective>

<decision_record>
## Which private-tier writes emit a timeline event, and which do not

D-14 fixes the event vocabulary at six kinds. Two of them belong to this plan, and the mapping is
fixed here so 34-11's timeline and 34-13's walkthrough do not have to guess:

| Action | Row write | Event written | Why |
|---|---|---|---|
| `updateRelationDetailsAction` | `lead_source`, `description` | **none** | `relation_updated` is not in D-14's vocabulary, and adding a seventh kind would need a CHECK change and therefore a second migration. Editing a description is a correction, not an occurrence. |
| `addRelationshipNoteAction` | none | `note` | The event IS the note (ACTV-03). |
| `setNextActionAction` — setting a date | `next_action_at`, `next_action_note` | `next_action_set` | ACTV-04's intent becomes visible on the timeline. |
| `setNextActionAction` — clearing (`nextActionAt: null`) | `next_action_at = NULL` | **none** | "Set" is the kind. A cleared date is the absence of an intention, and an event claiming it was set would be false. |

## Statement ordering under a driver with no transactions

34-PATTERNS trap 1: the production driver is `drizzle-orm/neon-http`, whose `.transaction()`
throws at runtime. Every action here is therefore a sequence of individually atomic statements, and
the accepted crash-between outcome is recorded per action:

- `setNextActionAction` writes the ROW first, then the event. A crash between them leaves the date
  set with no timeline entry — the fact survives, the narration is lost. That is the right way
  round and matches `crm/actions.ts:28-30`'s "a harmless orphan, never a corrupted relationship".
- `addRelationshipNoteAction` inverts it deliberately: the event IS the fact, so it is written
  first, and the subsequent `updated_at` bump (which resets the staleness clock 34-05's follow-up
  list reads) is the losable half. A crash between them leaves a note that did not reset staleness
  — the relationship simply stays on the "à relancer" list one cycle longer. Harmless.

Neither action retries, and neither compensates. Recorded so a reviewer does not read the absence
of a transaction as an oversight.

## No audit rows in this plan

D-03: a shared-tier edit writes an audit row with before and after **precisely because** another
partner sees the result. A private-tier edit does not need one. Plan 34-01 deliberately minted only
three new `AuditAction` members, all shared-tier. An acceptance criterion asserts
`grep -c "writeAuditLog" src/lib/relationship/actions.ts` returns 0. If a reviewer later wants
private-tier auditing, that is a new decision with a new action member — not a quiet addition here.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client form → server action | caller-supplied relationship id, lead source, free text and dates |
| session → owner id | the only legitimate source; no action accepts an owner parameter |
| private-tier row → another partner's session | the isolation FICHE-04 is measured on |
| thrown action error → production client | a channel Next.js redacts, and that CR-01 already broke once |
| event payload → audit/analytics surfaces | jsonb that must never carry commission data (ADMIN-09) |
