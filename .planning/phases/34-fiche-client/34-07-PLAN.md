<decision_record>
## Mapping a lookup failure onto the four registry statuses

D-09 says a registry failure "writes `registry_status = 'pending'` and does not enter the bounded
error path". The status vocabulary plan 34-01 shipped has four values, and collapsing every failure
to `pending` would make three of them dead. The vocabulary exists to tell a partner whether
refreshing again is worth a click, so the mapping is fixed here:

| `lookupCompanyBySiren` result | `registry_status` written | Why |
|---|---|---|
| `{ ok: true }` | `synced` | plus `registry_synced_at = now()` and a `registry_synced` event |
| `{ ok: false, reason: 'not_found' }` | `not_found` | a settled answer — this SIREN is not in the registry, or the registry disagrees about which company it is (D-05). Refreshing will not help; correcting the SIREN will. |
| `{ ok: false, reason: 'timeout' }` | `pending` | retryable; the "Actualiser" control is the retry |
| `{ ok: false, reason: 'upstream_error' }` | `pending` | retryable |
| `{ ok: false, reason: 'malformed' }` | `error` | the upstream answered with something we cannot use. Not retryable by the partner, and worth distinguishing so a recurring parser break is visible rather than looking like an outage. |

D-09's actual invariant — **a registry failure NEVER blocks client creation and never enters the
bounded error path** — is preserved on every row of that table. The status written is a nuance
inside "did not block", not a departure from it.

## The audit "before" is a data read, not the authorization step

D-03 requires a shared-tier audit row carrying before AND after. PostgreSQL's `UPDATE … RETURNING`
returns the NEW row, so the OLD values need a read. This codebase deliberately avoids
authorization-shaped pre-SELECTs (`crm/actions.ts:182-216`, `pipeline/actions.ts:62-67`), and the
distinction matters here:

**The owner-scoped SELECT that fetches the "before" values is NOT the authorization step.** The
UPDATE that follows independently re-proves ownership inside its own WHERE via the reachable-company
subquery, exactly as `markProposalWonAction` does. If the SELECT were removed entirely the action
would still be safe; it exists only so the audit payload can carry a before. A comment above it
must say this in those words, because the next reader will otherwise "clean it up" into a
check-then-write, which is the TOCTOU pattern `createContactAction`'s comment forbids.

## A SIREN correction re-runs the lookup, in the same action, after the write

FICHE-03: correcting a wrong SIREN "re-runs the lookup". Order: the SIREN is written first (it is
the shared-tier edit the partner asked for and the audit row records it), then `syncCompanyRegistry`
runs against the new value. If the sync fails, the SIREN correction still stands and the status
reflects the failure — the same non-blocking discipline as D-09. A failed sync must NOT roll back
the correction; there is no transaction to roll back with (neon-http), and pretending otherwise
would leave the two halves inconsistent in the other, worse direction.
</decision_record>
