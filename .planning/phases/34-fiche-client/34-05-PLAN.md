## What "à relancer" means, stated once so it cannot drift

ACTV-05 asks for "a list of relationships needing follow-up, driven by next-action date and
staleness". Neither the design nor 34-CONTEXT fixes the thresholds, so this plan fixes them and
every later plan (the home card in 34-11, the acceptance walkthrough in 34-12) reads them from
here.

**Candidate set** — the caller's own relationships whose `stage` is NOT one of `perdu`, `signe`,
`debloque` (a lost or closed relationship does not need chasing), AND that satisfy either:

- **due**: `next_action_at IS NOT NULL AND next_action_at <= now()`, or
- **stale**: `next_action_at IS NULL AND updated_at < now() - interval '30 days'`.

A relationship with a FUTURE `next_action_at` is neither due nor stale — it is on schedule and must
not appear. That is the single most likely misreading of "driven by next-action date".

**Order** — due rows first, oldest `next_action_at` first; then stale rows, oldest `updated_at`
first. Implemented as one statement with a computed `bucket` (0 = due, 1 = stale) ordered
`bucket ASC, coalesce(next_action_at, updated_at) ASC`, so the ordering is total and stable and the
caller does not merge two result sets.

**Why `updated_at` is the staleness clock, not the newest event.** `client_relationships.updated_at`
is already written by `advanceRelationshipStageAction` and will be written by every Phase 34
private-tier action. Deriving staleness from `MAX(relationship_events.occurred_at)` instead would
add a join and a group-by to a home-page query, and would report a relationship as stale the moment
it was created but never touched — which is correct, but is already covered because `updated_at`
equals `created_at` on a fresh row. The simpler clock gives the same answer. Recorded so a reviewer
does not read the absence of an events join as an oversight.

**Admins.** The home page uses `requireUser()`, not `requireRelationshipHolder()`, so this function
may be called with an admin's user id. It takes `ownerId` as a required parameter compiled into the
WHERE, so an admin — who owns no relationships — receives an empty array. It must NOT throw, and it
must NOT grow a role parameter or an "all owners" flag.

## D-22 goes in the JOIN condition, never the WHERE

`listPipelineBoard` (`src/lib/db/queries/pipeline.ts:80-86`) `leftJoin`s `proposals` on
`and(eq(clientRelationshipId, …), ne(status, 'deleted'))`, missing the
`eq(proposals.userId, ownerId)` predicate that `listProposalsForRelationship` carries as CRM-02
defence in depth.

Adding it to the statement's `.where(...)` instead would degrade the LEFT JOIN to an INNER JOIN:
every relationship with zero owned proposals would produce a NULL `proposals.user_id`, fail the
WHERE, and vanish from the board entirely. A partner's brand-new prospects — the majority of the
Prospect lane — would disappear. The predicate belongs inside the `leftJoin`'s `and(...)`, and a
regression test asserts a relationship with no proposals still appears with
`proposalsCount === 0`.
