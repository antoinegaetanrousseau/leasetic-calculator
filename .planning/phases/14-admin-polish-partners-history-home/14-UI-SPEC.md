**Phase 14 page layout (every new/modified admin surface):**
- Outer page container (inside `<Shell>` main content slot): max-width **1040px** centered horizontally (matches Phase 13 step-3). Vertical padding **32px (4xl)** top + bottom on the paper-bg main area.
- Page header block (h1 title + optional subtitle) → first content card: **24px (2xl)** gap.
- Card-to-card vertical spacing (when multiple cards stack): **16px (lg)**.
- Title `h1` (heading/hero) → subtitle `p` (body/large) gap: **8px (sm)**.

**Per-surface layout exceptions (Figma-grounded, NO new tokens):**
- **`/partners/new` form card** uses inner padding **28px (3xl)** (matches `.card`). - **`/coefficients` 2-col grid:** `display: grid; grid-template-columns: minmax(0, 1fr) 360px; gap: 24px;` (matches Phase 13 step-3 exact dimensions). Max-width 1040px. Wraps to single column at `@media (max-width: 999px)` (sidebar moves below editor).

- **`/history` page** rows are full-width `.card` instances with padding **28px (3xl)** inside each row. Row-to-row gap: **16px (lg)**.
- **Diff panel** (inside `/history` row OR inside CoefficientHistorySidebar row inline expansion) uses a 2-col grid: `display: grid; grid-template-columns: 1fr 1fr; gap: 24px;` (Avant | Après). Each column gets internal vertical padding **24px (2xl)**. The summary line at the bottom sits **20px (xl)** below the last diff row.

### 4.4 NEW class `.chip-invited` (Phase 14 ADDS to `app/globals.css`)

Per D-26, partner list adds an `invited` StatusChip variant. Phase 11 ships 4 variants (active/draft/expired/disabled) — Phase 14 ships the 5th. The visual contract is **identical to `.chip-draft`** (gold tint over 12% bg) but the class name is SEMANTICALLY DISTINCT so that future changes to one don't accidentally cascade to the other.

```css
/* Add to app/globals.css after .chip-draft (line ~371) */
.chip-invited {
  background: rgba(224, 133, 48, 0.12);
  color: var(--gold);
}
```

**Verification:**
- `grep -c "\.chip-invited" app/globals.css` returns 1 (the declaration).
- `grep -rn "chip-invited\|variant=\"invited\"" src/ app/` returns ≥1 match in `AccountsList.tsx` (the consumer) and 1 match in the StatusChip component (the variant union extension — see §5.7).

### 4.5 StatusChip variant union extension (Phase 14 MODIFIES `src/components/ui/StatusChip.tsx`)

The current Phase 11 `StatusChipProps` declares:
```ts
variant: 'active' | 'draft' | 'expired' | 'disabled';
```

Phase 14 extends to:
```ts
variant: 'active' | 'draft' | 'expired' | 'disabled' | 'invited';
```

The component body is unchanged — it already templates `chip chip-${variant}` so a new class name is automatically respected once `.chip-invited` exists in CSS. Vitest test added: `AC-SC-08: <StatusChip variant="invited" label="invité.e" />` renders `<span class="chip chip-invited">invité.e</span>` with computed bg `rgba(224, 133, 48, 0.12)` and color `rgb(224, 133, 48)`.

## 12. Open issues + Phase-14 blockers

### 12.1 Phase 9 history table on `/coefficients` — keep or remove?

Per §5.6: the existing Phase 9 `<HistoryTable>` (cursor-paginated, lives below the editor on `/coefficients`) overlaps with the new `<CoefficientHistorySidebar>` (5 most-recent only) and `/history` standalone page (full pagination). Three options:

- **Option A — Remove the Phase 9 history table from `/coefficients`.** Sidebar covers at-a-glance; `/history` covers the full need. Cleanest UX. RECOMMENDED.
- **Option B — Keep the Phase 9 history table AND the new sidebar.** Both live on `/coefficients`. Redundant. Risk: confusing for admins.
- **Option C — Move the Phase 9 history table to `/history` as the row-rendering pattern.** Reuse the Phase 9 row CSS classes for `/history` rows. Saves implementation work but mixes Phase 9 + Phase 14 design epochs.

**Decision deferred to planner.** Recommendation: A.

### 12.2 `.chip-invited` vs `.chip-draft` semantic distinction

Per §4.4: both classes have IDENTICAL chrome. The semantic distinction is in the class NAME, not the visual. A future v1.3+ change might want to:
- Differentiate `invited` (gold ring around chip) from `draft` (solid gold tint) — slight visual variation to disambiguate at a glance.
- Or unify them under `.chip-pending` if the team decides the semantic gap doesn't justify separate classes.

For Phase 14: ship as two separate classes per D-26 + §4.4. Document in planner SUMMARY that the duplication is intentional.

### 12.3 `changed_by` display: email vs displayName

Per §5.2 row meta: the `row.changed_by` field is the result of joining `coefficient_history.changed_by_user_id` to `users`. The displayed value can be `email`, `displayName`, or `name` (Better Auth fallback chain). Recommendation: `displayName ?? name ?? email`. Some admins may not have displayNames set; the email is the most universally recognizable. Planner picks; document in plan SUMMARY.

### 12.4 Diff-panel field-label localization

Per §6.8: diff-panel renders flattened paths like `commission_pct`, `coefficients.t1.36` as labels — these are technical/internal keys, NOT user-friendly French/English. For v1.2 (admin-only, FR-primary), this is acceptable. A future v1.3+ polish pass could humanize the labels (e.g., `commission_pct` → `Commission apporteur`). Not blocking for Phase 14 ship.

### 12.5 `CoefficientDiffPanel` shared vs split

Per §5.4 + 14-CONTEXT.md `<Claude's Discretion>`: ship as a SHARED component with `mode: 'condensed' | 'full'` prop. The two layouts share enough structure (flattened diff rows, summary line, gold-tint changed-row highlight) that branching internally is cleaner than maintaining two files. If the modes diverge significantly in v1.3+, planner extracts them then.

### 12.6 308 redirect for `/accounts` — `next.config.ts` vs server-component stub

Per D-02: two implementation paths for the `/accounts` → `/partners` 308 redirect:
- **Option A — `next.config.ts` redirects array:** declarative, runs at the Next.js routing layer before any React renders. Cleanest.
- **Option B — `app/(admin)/[adminSegment]/accounts/page.tsx` server-component stub:** renders `redirect(`/${adminSegment}/partners`, RedirectType.permanent)`.

Recommendation: **Option A** (`next.config.ts`) for performance + cleaner separation. Plan task: ensure the `[adminSegment]` dynamic param is preserved through the redirect (Next.js redirects array supports parameterized rewrites). Confirm via curl HEAD probe in smoke test.

### 12.7 Phase 11 `.chip-invited` SHOULD have been added by Phase 11

Per Phase 11 §6.6: the StatusChip ships 4 variants (active/draft/expired/disabled). Phase 11 did NOT ship `invited` — the `invited` semantic is Phase 12 territory (`listInvitedPartners` helper) and the visual is Phase 14 territory (consumer of the chip).

This is a minor scope mis-allocation: in retrospect, Phase 11 could have shipped 5 variants. The mitigation is Phase 14 adds the 5th class + extends the union (§4.5). Documented in plan SUMMARY; no rework of Phase 11 required.
