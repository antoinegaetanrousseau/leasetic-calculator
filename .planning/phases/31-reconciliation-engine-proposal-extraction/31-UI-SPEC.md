# Phase 31 — UI Design Contract

> Visual and interaction contract for Phase 31 (Reconciliation Engine & Proposal Extraction).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Requirements covered:** IMPORT-01, IMPORT-03, IMPORT-04, IMPORT-05, IMPORT-06 — but only the
**human-facing slice** of those requirements. Extraction, SIREN auto-merge, the CLI script and
the dry-run report file are non-UI work; see "Out of Scope" below.

**Language:** French is the product default; every string in this contract needs both `fr` and
`en` dictionary entries (the `_EnHasAllFrKeys` compile-time parity check enforces this — same
discipline as `30-UI-SPEC.md`). Tone matches `30-UI-SPEC.md`: short, sentence case, muted
subtitle sentences ending in a period, UPPERCASE only for table/column-style eyebrows.

## Scope Boundary (read first)

### In scope — the one real UI surface

**The admin pair-review queue** (D-16): a new admin route where a human resolves each
`name_normalized`-matched, SIREN-ambiguous pair (D-04, D-10) by merging the two companies into
one (D-09, D-12) or marking them permanently separate (D-09). This is the entire visual/
interaction surface this phase ships.

### Explicitly out of scope for this document

| Item | Why it's not here |
|---|---|
| The CLI import script (`scripts/`) | D-13 — a terminal tool, not a UI. No screen, no route. |
| The dry-run report (Markdown + JSON) | D-14 — a **file on disk**, reviewed by opening it in an editor/terminal, not rendered by this app. Do not build a "view the dry-run report" screen; that would be inventing a requirement no D-decision asks for. |
| SIREN auto-merge (D-04 partial, IMPORT-03) | Fully automatic, no human step, therefore no UI. |
| Extraction of companies/relationships/contacts from `proposals.inputs` (IMPORT-01) | A batch write the script performs; nothing for a person to look at mid-run. |

### Out of scope — deferred to the app-shell refresh phase

The user's invocation for this research session carried five global app-shell directives. Per
this repo's own precedent (Phase 16 shell-refresh, Phase 28 ReUI migration), these become **a
separate dedicated phase** and are **not** specified here:

2. Breadcrumbs in the shell header.
3. Converging the sidebar toward the vendored `src/components/blocks/app-shell-1/` block.
4. Shrinking the brand logo.
5. Fixing the collapsed-sidebar layout.

This spec adds exactly one ordinary sidebar entry ("Réconciliation") using the **existing**
`AppSidebar`/`adminNavItems()`/`adminHrefs` mechanism Phase 30 already established — that is a
routine per-surface addition, not shell chrome, and is unaffected by the deferred items above.

## Container Radius (LOCKED — decoupled from `--radius`)

> Tracked project-wide as [`OPEN-A`](../../codebase/UI-CONVENTIONS.md#open-items) — a recorded **open item**, not a settled
> convention. `--radius` itself stays pinned per [`UIC-04`](../../codebase/UI-CONVENTIONS.md). A checker should read the
> 18px/24px split as deliberate and deferred, not as a defect.

`app/globals.css` pins `--radius: 0.625rem` deliberately, after a documented incident where a
larger `--radius` inflated the whole derived scale (`--radius-sm` through `--radius-4xl`) and
broke Input/Button rounding app-wide (see `app/globals.css:67-74`). **Do not touch `--radius`
or the `@theme inline` multiplier block in this phase.**

Per the orchestrator's locked decision, this phase expresses its **container** surfaces (the
pair-review card, and the two new dialogs) with a **literal, decoupled radius** rather than the
`--radius`-derived `rounded-2xl` token Phase 30's `.card` class resolves to (`--radius-2xl` =
0.625rem × 1.8 = 18px). This is the same pattern the vendored `app-shell-1` block already uses
(`rounded-[24px]`, confirmed at `src/components/blocks/app-shell-1/components/app-shell.tsx:60-64`)
— fully independent of `--radius`.

| Element | Radius | Token vs. literal |
|---|---|---|
| Pair-review card (`PairReviewCard`) | `rounded-[24px]` | **Literal** — the Maia container contract value for this phase |
| `DialogContent` / `AlertDialogContent` on the two new confirm dialogs | `rounded-[24px]` (className override) | **Literal** — same contract value, first application to dialog chrome in this app |
| Buttons, `Badge`, `RadioGroup` items, inputs inside those dialogs | Unchanged shadcn defaults (`--radius`-derived) | **Token** — controls are explicitly NOT part of this exception |

**This is a deliberate, documented, short-term inconsistency**, not an error: Phase 30's
existing `.card` (18px, token-derived) and this phase's new pair-review card (24px, literal) will
visibly differ until the app-shell refresh phase formalizes a named container-radius token and
back-applies it everywhere. Flag this for the planner so it is not "fixed" as a bug mid-phase —
the orchestrator's instruction is explicit that the formal token naming is that later phase's job,
not this one's.

## Color

Per [`UIC-03`](../../codebase/UI-CONVENTIONS.md) — same tokens, same 60/30/10 discipline, same explicit accent reserve
list. UIC-03 permits a phase to declare a **stricter** accent budget than the baseline, which is
what this surface does. **This surface
introduces zero new color tokens and, deliberately, near-zero new accent (`--primary`) usage:**

| Role | Token | Usage on this surface |
|------|-------|-------|
| Dominant (60%) | `--background` | Page background |
| Secondary (30%) | `--card` | Pair-review cards, dialog panels |
| Accent (10%) | `--primary` (and `--ring`, which aliases the same `--brand-accent`) | **Three uses, enumerated below.** There is no page-level CTA — pairs are system-generated, nothing is created by hand — and no control uses `Button variant="default"`. |
| Destructive | `--destructive` | The **Merge** confirm submit button only (`Button variant="destructive"` inside the merge `Dialog`) — merging deletes the loser company (D-12), so it earns the same destructive treatment `DeleteContactDialog` already established. |
| Neutral badge | `--border`/`--foreground` via `Badge variant="secondary"` | Owner-type badge per side ("Partenaire" / "Interne") — reused verbatim from `admin.companies.relation.type.*`, same chrome, same tokens, no new badge variant |
| Muted / secondary text | `--muted-foreground` | SIREN values, counts, reason label |

**Accent reserved for (exhaustive list, three items).** Derived by resolving every token that
aliases `--brand-accent` (`--primary`, `--ring`, `--sidebar-primary`) through each primitive this
surface renders — not by reading this phase's own files:

1. **Focus ring and focused-control border** — `focus-visible:ring-ring/50` +
   `focus-visible:border-ring`, in the base class of `button.tsx` and `radio-group.tsx`.
   `--ring` aliases `--brand-accent`, so this is the accent. It renders on **every** control here
   on keyboard focus: both row triggers per pair card, the merge dialog's cancel and its default
   close "X", both survivor radios, and both keep-separate actions. The merge confirm is the one
   exception — `variant="destructive"` overrides it to `ring-destructive`. This is the most
   widespread accent render on the surface.
2. **`RadioGroupItem` checked indicator** — `data-checked:bg-primary` / `data-checked:border-primary`
   from `radio-group.tsx`. A survivor is always pre-selected (A-3), so a filled accent swatch
   renders on every merge-dialog open.
3. **Company-name link hover** — `hover:text-primary` on each side of a pair card. The only one of
   the three written in this phase's own code.

**Verified not to render accent here**, so deliberately absent from the list: `Button`/`Badge`
`bg-primary` (needs `variant="default"`; this surface uses only `outline`, `secondary`,
`destructive` and the dialog's built-in `ghost` close); `PageHero`'s `text-primary` eyebrow (the
eyebrow is conditional and this page passes only title and subtitle); and `EmptyDescription`'s
`[&>a:hover]:text-primary` (needs an anchor inside it; this empty state is plain text).

Every *Button* on this surface is `variant="outline"` (row triggers, keep-separate confirm and
cancel, merge cancel), `variant="destructive"` (merge confirm only), or the `variant="ghost"`
close button `DialogContent` renders by default. This is still a stricter budget than Phase 30's
list of accent-eligible elements, which UIC-03 permits: there is no dialog-level "one accent use"
carve-out here the way Phase 30's create-client dialog had one, because nothing here is a create
action.

> **Correction (2026-09-02) — this section was wrong three times.** It claimed, in order: a
> "literally zero" budget with an empty list; then "exactly one use" (missing the checked radio);
> then "two uses" (missing the focus ring, the most widespread of the three). Each revision
> enumerated `--primary` by reading the phase's own files. **That method does not work.** The
> check that closes it is mechanical: resolve every token aliasing `--brand-accent` and grep the
> accent utilities out of each primitive the surface actually renders, then eliminate the ones
> whose variant or condition does not occur here. The list above was produced that way.

## Access & Non-Leakage Contract (the load-bearing rule of this spec)

This is the single most important contract in this document — read it before implementing
anything below.

1. **Admin-only, no exceptions (D-11).** The route calls `requireAdmin()` first, before any data
   access, exactly like `CompaniesPage` (`app/(admin)/[adminSegment]/companies/page.tsx`) — 404,
   never a 403, on failure (D-18 URL-secrecy pattern, `src/lib/auth/require.ts`).
2. **No partner-facing trace of this surface exists anywhere.** `partnerNavItems()` does not
   gain an entry; no partner-facing page, toast, empty state, or count ever mentions a "flagged
   pair," a "review queue," or a pending-resolution count. A `sales`-role user (ROLE-02) is a
   partner-equivalent for this purpose and also never sees it — only `admin` reaches this route.
3. **Within the admin-only queue, showing full detail is correct, not a leak.** CRM-03 already
   grants an admin the right to see every relationship on a company, including which partner (or
   sales/house owner) holds each one (`CompanyRelationsTable`'s TITULAIRE/TYPE columns, Phase 30).
   This queue re-presents exactly that class of fact — company name, SIREN, owner display name,
   owner type, relationship/contact/proposal counts — grouped by flagged pair instead of by
   single company. **It creates no new information-disclosure surface**; it is a faster view onto
   data the same admin could already assemble by opening both companies' detail pages separately.
4. **The compound-merge case (D-12) names exactly one owner, never two owners against each
   other.** By construction, the compound case is "a single partner/sales user holds a
   relationship with BOTH companies" — there is only one name to show, not a cross-partner
   comparison. If a future engine variant ever flagged a pair where the compound condition
   involved two DIFFERENT owners, that is out of D-12's defined scope and must not be rendered by
   this UI without a new decision — flag it to the planner rather than inventing a display for it.
5. **No ambient pending-count signal outside this route.** This phase does not add a "N pairs
   need review" badge to the sidebar, the admin home, or any other surface. Keeping the signal
   contained to the one route where it's actionable avoids growing this into an unplanned
   dashboard feature; a badge count can be added later as a scoped follow-up if an operator
   actually asks for one.

## Surface-by-Surface Contract

### 0. Route map (new)

| Route | Layout group | Access | Purpose |
|---|---|---|---|
| `/[adminSegment]/companies/review` | `(admin)` | `admin` only | Pair-review queue — IMPORT-04/05 human resolution |

Placed under the existing `companies/` route directory (a sibling of `page.tsx` and `[id]/`, next
to what Phase 30 shipped — "alongside the companies tree" per D-16) rather than at the top level,
because a flagged pair is fundamentally about the company registry, not a separate domain. It is
still its own component tree and its own route, not nested under a specific `[id]`.

**Container convention (unchanged from Phase 30):** renders directly inside `Shell`'s capped
`<main>`, no custom `maxWidth` wrapper — matches every other admin page.

### 1. Pair-review queue — `/[adminSegment]/companies/review` (IMPORT-04, IMPORT-05)

**Focal point:** the two company names inside each pair card — that comparison is the entire
reason an admin opens this page. The reason label and counts are supporting evidence for the
decision, not competing focal points; the action buttons are a clear secondary tier at the
bottom of each card.

Composition (server component page):

1. `<PageHero title={t('admin.reconciliation.page.title', lang)} subtitle={t('admin.reconciliation.page.subtitle', lang)} />` — **no `actions` prop.** There is no page-level CTA (nothing to create).
2. A vertical stack of `PairReviewCard` components, `flex flex-col gap-6` — **not** a single
   table wrapper. This is a deliberate divergence from `CompaniesList`/`PartnersList`'s
   table-per-row pattern (same kind of documented divergence Phase 30 made for Card-vs-Frame):
   a table row is the wrong shape for "two full company summaries side by side plus a warning
   plus two actions" — that content needs its own card, not a `<td>`.
3. Cursor-based **"Charger plus"** footer button (`Button variant="outline"`), matching the app-
   wide list convention (`PartnersList`, `ProposalsList`, Phase 30's `ClientsGrid`) — reused, not
   reinvented. Ordering: oldest-flagged-first (FIFO), so the queue drains from the front — no
   sort control, no search box; this is a small, bounded work list, not a directory (see
   Assumptions for the rationale on omitting search).
4. Empty/success state (see below) replaces the stack entirely when zero pairs remain.

**`PairReviewCard` composition** (one per flagged pair, `rounded-[24px]` per the Container
Radius contract, `.card`-equivalent background/border/shadow otherwise unchanged from the
existing `.card` class):

- **Reason label** (top of card, 13px muted): one of the three Copywriting Contract reason
  strings, computed from the pair's SIREN state on each side.
- **Two-column grid** (`grid grid-cols-2 gap-5`), side A | side B, each column:
  - Company name — **link** to `/[adminSegment]/companies/{id}` (existing Phase 30 detail page,
    `text-foreground` with `hover:text-primary`, matching the existing internal-link convention;
    opens same tab so back-navigation returns to the queue) — `font-semibold text-[14.5px]`.
  - SIREN — `text-[13px] text-muted-foreground`, em-dash fallback when absent.
  - Owner line(s) — for each relationship on this side: owner display name + neutral
    `Badge variant="secondary"` ("Partenaire"/"Interne"), `text-[13px]`. Multiple owners render
    as a stacked list (a company can have several relationships).
  - Counts — **"{n} relations · {n} contacts · {n} propositions"**, `text-[13px] text-muted-foreground`, real zeros rendered as `0` (never `—`).
- **Compound-merge warning** (only when the pair has one, D-12) — inline banner between the
  two-column grid and the action row: `AlertTriangleIcon` (existing icon, `size={16}`,
  `text-destructive`) + the compound-warning copy, `text-[13px] text-destructive`, on a
  `bg-destructive/10` strip with the same corner treatment as the card's controls (not the
  literal 24px — this inner strip is a control-tier surface, `rounded-lg`/`--radius`-derived).
- **Action row** (bottom, right-aligned, `flex gap-2`): `Button variant="outline" size="sm"`
  "Fusionner" (opens the Merge dialog) + `Button variant="outline" size="sm"` "Marquer séparées"
  (opens the Keep-Separate dialog). Neither button is colored ahead of its confirm step — color
  (destructive red) appears only inside the merge confirmation, matching the
  `DeleteContactDialog` discipline of keeping the row trigger neutral and reserving destructive
  color for the actual point of no return.

**Empty / success state.** This queue drains to empty **by design** — reaching zero is the
success condition, not a first-run gap. Do not reuse Phase 30's "nothing here yet + CTA" tone.

**Shape deviation from [UIC-05](../../codebase/UI-CONVENTIONS.md), stated deliberately:** this is
the two-line case UIC-05 reserves `EmptyTitle` for. A success state has to say *that* the queue
cleared and *why that is good*; collapsing both into a lone `EmptyDescription` would read as an
absence of data rather than a completed job.

```
<Empty className="px-5 py-12">
  <EmptyMedia><CheckCircleIcon size={32} /* default/muted styling, NOT --success emerald or
    --primary accent — see Color section: this surface's accent is reserved (see § Color) */ /></EmptyMedia>
  <EmptyTitle>{t('admin.reconciliation.empty.title', lang)}</EmptyTitle>
  <EmptyDescription>{t('admin.reconciliation.empty.body', lang)}</EmptyDescription>
</Empty>
```

No CTA button — there is nothing to create from this screen. This is the one meaningful copy/
tone difference from every other Phase 30 empty state, and it's deliberate (see phase brief:
"the empty state is a success state... get the copy right").

### 2. Merge flow

A shadcn `Dialog` (not `AlertDialog`) — **because merging requires a decision input** (which
company survives), and `AlertDialog` has no room for a form control. This is the first real-app
adoption of `radio-group.tsx` outside vendored blocks and shadcn internals (`field.tsx`,
`context-menu.tsx`, `dropdown-menu.tsx` use it internally; no page-level feature has yet), flagged
the same way Phase 30 flagged `Dialog`/`AlertDialog`'s first real adoption (A-6).

Contents:
- `DialogTitle`: "Fusionner ces deux sociétés ?"
- Body: the base description (interpolated with both company names) — **and, when the pair has a
  compound-merge case, the compound warning sentence appended directly beneath it**, repeating
  the card's inline warning so the decision-critical fact is visible at the point of commitment,
  not only earlier on the page.
- `RadioGroup` (required, no default-empty state — see below): "Société à conserver" label, one
  `RadioGroupItem` per side, each item rendering company name + SIREN (or "—") + the same
  "{n} relations · {n} contacts · {n} propositions" line used on the card, so the choice is
  informed without needing to scroll back up.
  - **Default selection:** the side with more linked propositions (proposals are the strongest
    signal of which record is "the real one"); tie-break on relationship count; further tie on
    side A. The admin can always override before confirming. (Flagged for the planner: this is a
    sensible default, not a hard requirement — Open Question #2 in `31-CONTEXT.md`, "canonical
    name selection," is explicitly left open, and this default doesn't need to match whatever
    rule the extraction engine itself later uses for auto-created companies, since this dialog
    covers the human-review path only.)
- `DialogFooter`: `DialogClose` "Annuler" (`variant="outline"`) + `Button type="submit" variant="destructive"` "Fusionner" (disabled until a survivor is selected — though a default is always pre-selected per above, so in practice it's only ever disabled if that default logic fails to resolve, which should not happen in normal operation).
- Submit calls the resolve action (planner names it — e.g. `mergeCompanyPairAction(pairKey, survivorCompanyId)`), on success: dialog closes, toast "Sociétés fusionnées.", `router.refresh()` to drop the resolved pair from the list. On failure: generic bounded-error toast, dialog stays open (same retry-without-re-entering-data pattern as `ContactFormDialog`).

### 3. Keep-separate flow

A shadcn `AlertDialog` — pure confirm, no input, exactly like `DeleteContactDialog`'s existing
pattern but **not destructive-colored**, because nothing is deleted; the permanence is temporal
("never re-flagged"), not data-loss.

- `AlertDialogTitle`: "Marquer ces sociétés comme définitivement séparées ?"
- `AlertDialogDescription`: the keep-separate copy, interpolated with both company names.
- `AlertDialogCancel`: "Annuler" (default/outline, unchanged from primitive default)
- `AlertDialogAction`: "Marquer séparées" — **`variant="outline"` is REQUIRED, not optional.**
  `AlertDialogAction` passes no variant of its own (`alert-dialog.tsx:142-145`), so it falls
  through to `Button`'s default variant (`button.tsx:35`), which is `bg-primary
  text-primary-foreground` (`button.tsx:11`). Omitting the override therefore ships a
  `--primary`-filled button, which is not one of the two reserved accent uses in § Color. (The
  `variant = "outline"` default at `alert-dialog.tsx:157` belongs to **`AlertDialogCancel`**,
  not to `AlertDialogAction` — an earlier revision of this spec cited it for the wrong component
  and concluded, wrongly, that no override was needed.) No `variant="destructive"` either: this
  action is not destructive.
- Submit calls the resolve action (e.g. `keepPairSeparateAction(pairKey)`), writing the D-09
  decision row. On success: dialog closes, toast "Paire marquée comme séparée.",
  `router.refresh()`. On failure: generic bounded-error toast, dialog stays open.

## Assumptions (confirm before execution)

1. **A-1 — Route lives at `/[adminSegment]/companies/review`, not a top-level `/[adminSegment]/reconciliation`.** D-16 says "its own admin route, alongside the `/[adminSegment]/companies` tree Phase 30 shipped" — read here as a sibling directory inside the same `companies/` route tree (joining `page.tsx` and `[id]/`), not a new top-level segment. If the planner reads D-16 differently, the route string is a one-line change; nothing else in this contract depends on the exact path.
2. **A-2 — No search/filter/sort UI on the queue.** This is a small, bounded work list expected to drain, not a directory to browse — matches the "own empty state and resolve actions... drains to empty" framing in `31-CONTEXT.md`. If real volume proves this wrong (e.g., the first extraction run flags hundreds of pairs), a search box is a scoped follow-up, not a blocker for this phase.
3. **A-3 — Merge dialog always has a pre-selected survivor.** The default-selection heuristic (most linked proposals → most relationships → side A) is Claude's-discretion territory per `31-CONTEXT.md`'s explicit list, not a locked decision. The planner may substitute a different tie-break without touching the rest of this contract.
4. **A-4 — The compound-merge warning is computed by the query layer, not derived client-side.** The UI expects a payload field (planner names it, e.g. `compoundMergeWarning: { ownerName: string; ownerType: 'partner' | 'sales' } | null`) per pair; this document specifies its rendering, not its computation.
5. **A-5 — No pending-count badge anywhere outside this route** (see Access & Non-Leakage Contract point 5). If an operator later asks for one on the admin home, that's a new, separately-scoped UI decision — not assumed here.
