<phase_design_contract>
These names are fixed here and consumed verbatim by plans 02–08. Do not rename them later.

**Provenance column (D-08, resolves CONTEXT Open Question 4 — scope decided as all three tables):**
- Column name: `source`, `text`, **nullable**. `NULL` means "entered by a human". Added to
  `companies`, `client_relationships` AND `contacts`.
- Allowed values: `'proposal_extraction'` (this phase) and `'hubspot_import'` (reserved for
  Phase 32, written by no code in this phase).
- Rationale for the three-table scope (record this in the SUMMARY): D-08's stated purpose is
  "a bad import cannot be surgically undone". Undoing an extraction means deleting the
  companies and relationships it created, not only the contacts — a contacts-only column would
  leave the two harder-to-identify populations unmarked. Adding the column now is one ALTER;
  adding it after the first real import needs a migration *plus* a backfill that no longer has
  the information to be correct. This is exactly CRM-08's precedent.

**Pair-decision table (D-09/D-10):** `company_pair_decisions` (Drizzle export
`companyPairDecisions`). A row is inserted **pending** (`verdict IS NULL`) when the engine
flags a pair, and updated in place when an admin resolves it. This single-table shape is what
makes criterion 5's "never re-flagged" a query the engine runs *before* flagging.

**Pair key (D-10, refined — record this refinement explicitly in the SUMMARY):** D-10 says the
pair is keyed on its normalized-name pair. Taken literally that key is degenerate for this
phase's dominant case: two candidates that "match only on `name_normalized`" have the *same*
`name_normalized`, so the pair would be `(x, x)`. The key is therefore refined to an unordered
pair of **side identity keys**, each derived only from data that exists before any company row
does:
- side key = `siren:<9 digits>` when the side carries a valid 9-digit SIREN
- side key = `owner:<ownerId>|name:<name_normalized>` when it does not

This preserves every property D-10 asked for — computable before any write, computed from the
DB's `leasetic_normalize_company_name()` rather than TypeScript, and stable across a merge that
deletes one company id — while staying non-degenerate. `name_normalized` is stored alongside as
its own column so the D-10 lineage remains inspectable.
</phase_design_contract>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration file → production database | `.github/workflows/db-migrate.yml` applies committed SQL with elevated privileges; a wrong statement here is not reversible by a code deploy |
| schema definition → every downstream query | column nullability and CHECK constraints are the last line of defence when application-layer validation is bypassed by the CLI script (which runs outside the request path and outside `requireAdmin`) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-01-01 | Tampering | `drizzle/0008_phase31_reconciliation.sql` | mitigate | Additive only. Task 3 asserts the file contains no `DROP TABLE` and never touches `proposals`' snapshot columns, preserving the CRM-05 / ARCHITECTURE §2.5 immutability invariant |
| T-31-01-02 | Tampering | `company_pair_decisions` uniqueness | mitigate | The `LEAST/GREATEST` unique index is enforced by Postgres, not by application ordering — a caller that submits `(B,A)` after `(A,B)` was decided gets a constraint violation, not a duplicate pending row (criterion 5) |
