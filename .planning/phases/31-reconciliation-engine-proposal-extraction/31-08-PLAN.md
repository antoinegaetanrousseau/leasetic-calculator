  <action>
    Create `docs/operations/reconciliation-import.md` in the house style of
    `docs/operations/neon-branch-routing.md`, with these sections:

    1. **What this is** — a one-time historical migration turning every client implied by an
       existing proposal into a real company plus per-partner relationship, run by an operator
       from a terminal (D-13). Not a product feature; there is deliberately no UI trigger.
    2. **Locked rules**, numbered, each one sentence:
       - Never run the real mode without a dry run first. The tool enforces it; do not
         circumvent it.
       - Never point this script at a branch you have not first dry-run against — the fingerprint
          guard aborts, and that abort is correct.
       - This script applies no migrations. `drizzle/0008_phase31_reconciliation.sql` reaches a
         real branch only through `.github/workflows/db-migrate.yml`; see
         `docs/operations/neon-branch-routing.md` locked rule 3.
       - `--allow-drift` accepts a difference between the reviewed report and the current world.
         Use it only after reading the printed drift and deciding each change is expected.
    3. **Prerequisites** — `drizzle/0008_phase31_reconciliation.sql` applied to the target branch;
       `DATABASE_URL` pointing at that branch in `.env.local`; admin access to
       `/[adminSegment]/companies/review`.
    4. **Step 1 — dry run.** `npm run db:reconcile:dry-run`. Explain the four files it writes
       under `.reconcile/`, that the directory is git-ignored because the report contains live
       client names, and which Markdown sections to read first (counts table, then "Pairs flagged
       for review", then "Skipped rows").
    5. **Step 2 — review the report.** What to look for: an unexpectedly large flagged-pair count
       suggests bad source data rather than a bug; every skipped row is listed with its proposal
       id and reason, so a suspicious skip is traceable back to a specific proposal.
    6. **Step 3 — real run.** `npm run db:reconcile`, and
       `RECONCILE_CONFIRM=YES npm run db:reconcile` when the target is a `*.neon.tech` host.
       Document the exit-code contract as a table.
    7. **Step 4 — resolve the queue.** Open `/[adminSegment]/companies/review` as an admin. Each
       card shows both companies with their SIRENs, owners and counts. Merge picks a survivor and
       deletes the other; keep-separate is permanent and the pair is never flagged again.
       Note that the queue is admin-only by design: a flagged pair often has its two sides held by
       different partners, and showing it to a partner would reveal that someone else is working
       the other company.
    8. **Step 5 — confirm.** Re-run the dry run. A converged import reports zero companies to
       create, zero relationships to create and zero new pairs.
    9. **Rolling back a bad import** — every row this tool creates carries
       `source = 'proposal_extraction'`, so a bad run is removable by provenance. Give the
       three DELETE statements in dependency order (contacts, then client_relationships, then
       companies), each filtered on `source = 'proposal_extraction'`, with an explicit warning
       that they also remove rows from an *earlier good* run and that a `created_at` window
       should be added in practice.

    Add no new npm script and change no source file in this task.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| runbook → operator action against a real branch | a wrong or incomplete instruction here causes an irreversible bulk write |
| checkpoint procedure → production data | the verification itself runs destructive operations and must be confined to a non-production branch |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-08-01 | Tampering | the checkpoint's own merge/keep-separate steps run against production | mitigate | The procedure names the `development` branch explicitly and forbids running step 4 onward against production; step 1's row-count comparison is the only step safe anywhere and is still specified against the same branch |
| T-31-08-02 | Tampering | the runbook's rollback statements deleting rows from an earlier good import | mitigate | The rollback section carries an explicit warning that `source = 'proposal_extraction'` matches every run, and instructs the operator to add a `created_at` window in practice |
| T-31-08-03 | Information Disclosure | the runbook teaching an operator to commit a report containing live client data | mitigate | Step 1 states that `.reconcile/` is git-ignored and why; the report location is fixed in code so no instruction can redirect it |
| T-31-08-04 | Information Disclosure | the checkpoint confirming leakage only by absence of a nav item | mitigate | Verification group 6 checks the HTTP status directly for both a logged-out visitor and a partner, and requires `404` rather than any other status, so a 403 or a revealing redirect fails the checkpoint (D-18, CRM-02) |
| T-31-08-05 | Repudiation | an approval with no recorded evidence | mitigate | The acceptance criteria require the operator to record concrete before/after values — four row counts, one `inputs` value, two absent pairs, two HTTP statuses — into the SUMMARY, not merely to type "approved" |
| T-31-08-06 | Elevation of Privilege | the runbook documenting a way to bypass the dry-run guard | accept | `--allow-drift` is documented because hiding it would not remove it, and an operator who reads the printed drift is making an informed decision. The locked rules constrain its use rather than concealing the flag |
| T-31-08-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs no packages and changes no source file. If execution finds one is needed, stop and escalate |
</threat_model>
