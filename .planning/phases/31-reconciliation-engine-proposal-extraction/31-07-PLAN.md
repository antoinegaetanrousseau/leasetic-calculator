  <behavior>
    `runReconciliation({ dbi, source, mode, rootDir, databaseFingerprint, now, allowDrift, log })`
    where `mode` is `'dry-run' | 'apply'`:

    Dry-run mode:
    - calls `planReconciliation`, then `writeDryRunReport`, then returns
      `{ mode: 'dry-run', plan, reportPaths, counts }`
    - **never** calls `applyReconciliationPlan` — asserted by a spy
    - performs zero inserts, updates or deletes — asserted by spies on `dbi.insert`,
      `dbi.update`, `dbi.delete`

    Apply mode:
    - reads the last dry-run report; when it is absent, returns
      `{ mode: 'apply', aborted: true, reason: 'no-dry-run-report' }` and writes nothing
    - when the report's `databaseFingerprint` differs from the current one, aborts with
      `reason: 'fingerprint-mismatch'` and writes nothing
    - when the report's `sourceId` differs, aborts with `reason: 'source-mismatch'` and writes nothing
    - computes a fresh plan, then `computeDrift` against the stored envelope
    - when drift is present and `allowDrift` is `false`, aborts with `reason: 'drift'`, returning
      the change list, and writes nothing
    - when drift is present and `allowDrift` is `true`, logs the formatted drift and proceeds
    - on a clean comparison (or accepted drift), calls `applyReconciliationPlan` **with the
      freshly computed plan**, never with the stored one — the stored plan is the authorization,
      the fresh plan is the truth
    - returns `{ mode: 'apply', aborted: false, applied: <the apply counts>, drift }`
    - every abort path is reached before any call to `applyReconciliationPlan`

    In both modes `log` is called with progress lines and is injectable, so tests capture output
    instead of writing to stdout.
  </behavior>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator shell → production database | `DATABASE_URL` decides which branch a bulk write lands on; there is no environment gate above the shell |
| report file on disk → authorization to write | the stored dry-run report is what permits an apply run to proceed |
| CLI process → the whole registry | the script writes across every owner with no session and no `requireAdmin` above it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-07-01 | Tampering | an accidental real run against production | mitigate | An apply run against a `*.neon.tech` hostname requires `RECONCILE_CONFIRM=YES`; the check uses `URL.hostname`, not `URL.host`, per the documented bug_011 fix that a port suffix otherwise defeats |
| T-31-07-02 | Tampering | a real run writing something the reviewed report never promised | mitigate | Apply mode aborts before any write on `no-dry-run-report`, `fingerprint-mismatch`, `source-mismatch` and unaccepted `drift`; Task 1's acceptance criteria require every abort return to sit structurally above the single `applyReconciliationPlan` call site, and Task 2 tests each one |
| T-31-07-03 | Tampering | a dry-run report from another database authorizing a write | mitigate | `databaseFingerprint` is compared before planning; a mismatch is a hard abort with exit code 3 |
| T-31-07-04 | Tampering | the script applying a migration | mitigate | The script never invokes `drizzle-kit` or `db:migrate`; a grep criterion asserts zero non-comment occurrences and `check-no-drizzle-push.sh` runs in this plan's verification. Migrations reach real branches only via `.github/workflows/db-migrate.yml` (locked rule 3) |
| T-31-07-05 | Information Disclosure | credentials in logs or in the fingerprint | mitigate | Only `hostname` and the database name are hashed and only `hostname` is ever printed; the full `DATABASE_URL` is never logged, never hashed and never written to the report |
| T-31-07-06 | Elevation of Privilege | the CLI write path reachable from the app | mitigate | `src/lib/reconcile/index.ts` deliberately does not re-export `applyReconciliationPlan`, `mergeCompanyPair` or `recordKeepSeparate`, reinforcing plan 05's `app/`-import gate |
| T-31-07-07 | Repudiation | an apply run with no record of what it did | mitigate | Plan 05 writes an audit row per created entity with `actorId: null`, and the dry-run report archive keeps a timestamped record of what each run was authorized to do |
| T-31-07-08 | Denial of Service | a partially applied run leaving the registry unusable | mitigate | Plan 05's writes are individually idempotent, so a crashed apply is finished by re-running the same command; exit code 3 (refused) is deliberately distinct from 1 (crashed) so an operator can tell which happened |
| T-31-07-SC | Tampering | npm/pip/cargo installs | mitigate | This plan installs no packages — `tsx`, `dotenv` and `node:crypto` are already present. If one appears necessary, stop and escalate |
</threat_model>
