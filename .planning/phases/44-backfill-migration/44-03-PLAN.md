<objective>
Build the two safety modules that stand between the plan and the irreversible write: the two-form
dry-run report (D-08) and the drift check (D-09).

Purpose: D-01 removed the rollback, so these are load-bearing rather than nice-to-have. The report
is what the operator actually reads before clicking approve, and it is the artifact job 2 downloads
so that "the run I approved" and "the run that happened" are the same run by construction. The drift
check is what stops the approved plan and the executed plan from diverging in between.

Output: `report.ts` + `drift.ts` and their tests. Both are pure modules — filesystem for the report,
nothing else. Neither imports the database, the blob store or the PDF renderer.
</objective>

    Create `src/lib/backfill/drift.ts`. Pure module — no filesystem, no database, no imports beyond the
    type import from `./types`.

    Export `computeBackfillDrift(args: { stored: BackfillReportEnvelope; fresh: BackfillCandidate[];
    migratedIds: readonly string[] }): BackfillDriftResult`.

    `BackfillDriftResult` — `{ status: 'clean' | 'drift'; added: string[]; removed: string[];
    alreadyMigrated: string[] }` — is ALREADY declared in `src/lib/backfill/types.ts` (plan 01).
    Import it from `./types` and re-export it from this module for convenience. Do NOT redeclare it
    here: plan 04's `RunBackfillResult` in `types.ts` carries a drift verdict, so a declaration in
    `drift.ts` would make `types.ts` depend on a module that depends on `types.ts`.

    The classification is three-way, and getting it wrong breaks MIG-05:
    - `added` — a proposal id present in `fresh` but absent from `stored.rows`. This is real drift: a
      proposal was finalized after the report was approved, so approving the report did not authorise
      overwriting it.
    - `alreadyMigrated` — a proposal id present in `stored.rows` but absent from `fresh`, AND present
      in `migratedIds`. This is NOT drift. It is the expected shape of a resumed run: apply-mode's
      candidate query anti-joins on the `proposal.pdf_backfill` marker, so every row a previous
      interrupted run completed drops out of the fresh set. Classifying these as `removed` would make
      the second half of an interrupted migration abort on its own progress, and MIG-05 would fail.
      Write that reasoning into a comment on this branch — it is the non-obvious case a later reader
      will "simplify" away.
    - `removed` — a proposal id present in `stored.rows`, absent from `fresh`, and NOT in
      `migratedIds`. Real drift: the row was hard-purged, or its status left the `('active','deleted')`
      scope, between approval and apply.

    `status` is `'drift'` when `added` or `removed` is non-empty, and `'clean'` otherwise —
    `alreadyMigrated` never moves the verdict, no matter how large it is.

    Also export `formatBackfillDrift(result: BackfillDriftResult): string` producing operator-readable
    lines in reconcile's `+` / `-` prefix style, one per `added` and `removed` id, plus a summary count
    line for `alreadyMigrated`. It prints proposal ids only — never a blob key, a user id, a figure or a
    hostname.

    Write `src/lib/backfill/drift.test.ts`. Cover at minimum:
    - Identical stored and fresh sets → `status: 'clean'`, all three arrays empty.
    - A fresh id absent from stored → `status: 'drift'` with that id in `added`.
    - A stored id absent from fresh and present in `migratedIds` → `status: 'clean'`, the id in
      `alreadyMigrated`, and `removed` empty. Name this test for MIG-05 resumability so a future
      reader sees why it exists.
    - A stored id absent from fresh and NOT in `migratedIds` → `status: 'drift'` with the id in
      `removed`.
    - A mixed case producing all three non-empty at once, with `status: 'drift'`.
    - A run where every stored id is in `migratedIds` and `fresh` is empty → `'clean'` (the whole
      migration is already done; a re-run must be a no-op, not an abort).
    - `formatBackfillDrift` output contains the drifted ids and matches neither
      `/[a-z][a-z0-9+.\-]*:\/\//i` nor `/proposals\//`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| database rows → GitHub Actions artifact | The dry-run report leaves the private database and is stored on GitHub for 30 days, downloadable by anyone with repo read access. |
| approved report → the write decision | A file on disk between two jobs decides whether an irreversible bulk overwrite proceeds. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-12 | Information disclosure | `writeBackfillReport` output | mitigate | `toReportRows` is a closed allow-list projection; `blobKeyPresent` replaces the key so no user id leaves the database; a test asserts on the raw JSON text that none of `amountHT`, `loyerHT`, `coeff`, `commission`, `params_snapshot` or a sample user id appears. |
| T-44-13 | Information disclosure | `databaseFingerprint` in the report | mitigate | The fingerprint is a SHA-256 hex digest of `hostname/database` computed by the CLI (plan 05); the report module receives an opaque string and never constructs one, so no connection string can reach the artifact through this path. |
| T-44-14 | Tampering | report file substituted between jobs | mitigate | Three independent checks: `reportVersion` must be `'1'` or the reader returns `null`; plan 04 compares `databaseFingerprint` and aborts on mismatch; `computeBackfillDrift` aborts on any `added` or `removed` id. Both jobs run in the same workflow run from the same checked-out ref. |
| T-44-15 | Denial of service | `alreadyMigrated` misclassified as `removed` | mitigate | The three-way split is unit-tested including the all-migrated case; without it a resumed apply aborts on its own progress and the migration can never finish, leaving documents split across two layouts indefinitely. |
| T-44-16 | Repudiation | which plan the operator approved | mitigate | The archived timestamped copy is written beside the `latest` pair on every dry run, so the approved plan survives a later dry run overwriting `dry-run-latest`. |
| T-44-SC | Tampering | npm/pip/cargo installs | mitigate | No dependency is added; both modules use Node builtins only. No package-manager install task exists in this plan. |
</threat_model>
