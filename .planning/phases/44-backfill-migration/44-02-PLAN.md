<objective>
Build the two pure modules that turn one stored proposal row into one re-rendered PDF: the props
builder (`pdf-data.ts`) and the mode-aware per-row worker (`render-row.ts`). Both take their
dependencies as arguments, so the whole render/upload/persist path is unit-testable with no
database, no blob store and no live PDF renderer.

Purpose: this is where MIG-03 and MIG-04 are actually satisfied. MIG-03 is direct — the row's own
`language` column feeds the document. MIG-04 is satisfied transitively per D-05: `computed` was
derived from that proposal's `params_snapshot` at finalization, so printing it verbatim reproduces
the exact figures more strictly than a replay would. Nothing here calls `computeLoyer`, reads
`getLatestGlobalParams`, or opens `params_snapshot` — and that absence is a feature, not a gap.

Output: two modules, two test files, and one restatement line in REQUIREMENTS.md recording the
MIG-04 interpretation in the same style Phase 42/43 used for PROF-03 and DOC-03.
</objective>

    Export `renderRow(args: { row: BackfillCandidate; advisor: AdvisorIdentity | null;
    mode: BackfillMode; deps: BackfillDeps }): Promise<RowOutcome>`. It must never throw.

    Sequence:
    1. `buildBackfillPdfData({ row, advisor })`. On the failure form, return the matching `failed`
       `RowOutcome` immediately — nothing is rendered, nothing is written.
    2. `deps.renderPdf(data)`. Wrap in try/catch; on throw return
       `{ status: 'failed', reason: 'render-failed', detail: <redacted message> }`. Take `sha256` and
       `sizeBytes` from the result and ignore `contentHash` — it is not persisted anywhere.
    3. If `mode === 'dry-run'`: return `{ status: 'rendered', proposalId, lcRef, language, sizeBytes }`
       and RETURN HERE. Steps 4-6 must be unreachable in dry-run mode. This early return is MIG-01's
       "without a single blob being written" and it is what the workflow's job 1 relies on.
    4. Compute the blob key as `proposals/${row.userId}/${row.id}.pdf` — the identical expression used
       at the finalize call site. Call `deps.putBlob(key, buffer)`. Annotate this call: because
       `VercelBlobStorage.put()` passes `addRandomSuffix: false`, this is an in-place OVERWRITE of the
       delivered document, there is no versioning in the store and no sidecar copy is taken (D-01);
       the dry-run report and the workflow's approval gate are the only safety net. On throw →
       `'upload-failed'`.
       Do NOT call `deps` for a `head()` existence probe first and do NOT branch on whether the object
       exists: D-04 says a row whose object is missing from storage is processed like any other row and
       is repaired as a side effect — no orphan category, no separate counter, no distinct reporting.
    5. `deps.persistPdfArtifact({ proposalId: row.id, pdfBlobKey: key, pdfSha256: sha256,
       pdfSizeBytes: sizeBytes, pdfGeneratedAt: deps.now() })`. Writing a fresh `pdf_sha256` is
       correct and required (DATA-09 — the column describes the blob that now exists); it is NOT and
       must never become the skip signal, because the raw hash varies per render
       (`src/lib/pdf/render.ts:19`). Passing `pdfBlobKey` also repairs a row whose key was null.
       On throw → `'persist-failed'`.
    6. `deps.writeMarker({ proposalId: row.id, language: row.language, sizeBytes })` LAST. Ordering is
       load-bearing: the marker is the MIG-05 idempotence signal, so it must only ever exist for a row
       whose blob and columns are already written. A crash between 5 and 6 leaves the row unmarked and
       therefore a candidate again on the next run — a harmless second overwrite with the same inputs,
       which is exactly the resumability MIG-05 asks for. Record that reasoning in a comment. A throw
       here returns `'persist-failed'` too, and the comment must say why that is safe: the blob is
       already correct, the row will simply be re-processed.
    7. Return `{ status: 'migrated', proposalId, lcRef, language, sizeBytes }`.

    Also export `redactDetail(input: unknown): string` from this module and use it for every `detail`
    produced from a caught error. It must: take `err instanceof Error ? err.message : String(err)`,
    replace every match of `/[a-z][a-z0-9+.\-]*:\/\/\S+/gi` with `[redacted-url]`, and truncate the
    result to 200 characters. A storage or database error message can carry a store URL or a
    connection string, and every `detail` ends up in a report that is uploaded as a GitHub artifact
    and pasted into transcripts — the same disclosure rule `scripts/_db-branch-guard.ts` documents.

    Write `src/lib/backfill/render-row.test.ts` driving a fully stubbed `BackfillDeps` (vi.fn()s).

    - DRY-RUN ZERO-WRITE: with `mode: 'dry-run'` and a valid row, `deps.renderPdf` is called once and
      `deps.putBlob`, `deps.persistPdfArtifact` and `deps.writeMarker` have `toHaveBeenCalledTimes(0)`.
      This is MIG-01's core proof.
    - APPLY ORDER: with `mode: 'apply'`, all four are called, and the invocation order recorded by a
      shared spy array is exactly render → put → persist → marker.
    - The key passed to `putBlob` equals `proposals/<userId>/<id>.pdf` for a row with a known userId
      and id — and falsify by changing the row's `userId` and asserting the key changes.
    - The `pdfSha256` handed to `persistPdfArtifact` is the value `renderPdf` returned, and
      `pdfGeneratedAt` is the value `deps.now()` returned.
    - A `putBlob` rejection yields `{ status: 'failed', reason: 'upload-failed' }`, `writeMarker` is
      never called, and `renderRow` resolves rather than rejecting.
    - A `writeMarker` rejection still leaves `putBlob` and `persistPdfArtifact` called once each, and
      yields a `failed` outcome (the row stays a candidate for the next run).
    - A row that `buildBackfillPdfData` rejects never reaches `renderPdf`.
    - `redactDetail` turns an error message containing `postgres://user:pw@host/db` into one

    - A source-level assertion that `render-row.ts` does not match `/head\(|@\/lib\/storage|@\/lib\/db|@\/lib\/pdf'/`

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored jsonb → PDF render | `proposals.inputs` and `proposals.computed` are attacker-influenced only insofar as a partner typed them years ago, but they are wholly untyped at rest and are fed straight into a renderer. |
| render/storage error text → report artifact | Caught error messages from the blob driver and the database cross into a file that is uploaded to GitHub and pasted into transcripts. |
| this process → the delivered partner document | An `apply`-mode `putBlob` destroys the previously delivered PDF with no recovery path. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-06 | Tampering | `buildBackfillPdfData` `computed` binding | mitigate | The stored jsonb is assigned verbatim and the module is pinned by a source assertion that it never matches `computeLoyer|getLatestGlobalParams|paramsSnapshot`; a value-level test falsifies the binding by changing a stored figure and asserting the prop changes with it. A recomputation would silently move a figure on a delivered document. |
| T-44-07 | Tampering | `render-row.ts` write ordering | mitigate | Marker written strictly last; a crash before it leaves the row unmarked and therefore re-processed, never marked-but-unwritten. Order pinned by an invocation-order test. |
| T-44-08 | Information disclosure | `RowOutcome.detail` | mitigate | Every `detail` derived from a caught error passes through `redactDetail`, which strips any `scheme://…` token and truncates to 200 chars; unit-tested against a `postgres://user:pw@host/db` message. Zod failure details carry field NAMES only, never field values. |
| T-44-09 | Information disclosure | blob access level | mitigate | `deps.putBlob` receives key and buffer only. `StorageAdapter.put` exposes no public-access option and `DEFAULT_CACHE_CONTROL` stays `private, max-age=0, no-store` (PITFALLS §5.2/§5.4). This plan sets no `access`, issues no signed URL and changes no TTL. |
| T-44-10 | Denial of service | irreversible overwrite of a delivered document | accept | Accepted by D-01 at the milestone level: the ROADMAP's "irreversibly" was taken at face value and a `.pre-v19.pdf` sidecar was considered and declined. Compensating controls live in plans 03-05 (dry-run report, drift refusal, GitHub Environment reviewer gate), not here. |
| T-44-11 | Repudiation | which rows were overwritten | mitigate | Every successful row writes a `proposal.pdf_backfill` audit row carrying the proposal id, so the mutation set is reconstructable after the fact from `audit_log` alone. |
| T-44-SC | Tampering | npm/pip/cargo installs | mitigate | No dependency is added; `zod` is already a project dependency. No package-manager install task exists in this plan. |
</threat_model>
