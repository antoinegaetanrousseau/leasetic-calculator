<objective>
Assemble the pieces into `runBackfill` — the mode-aware orchestrator both the CLI and the tests
drive — and wire the production dependencies in a separate module so `run.ts` itself stays free of
`server-only` imports and its tests stay plain unit tests.

Purpose: this is the single place where a write is authorised. Every refusal path — no approved
report, wrong database, drifted set — returns before the loop that writes. The dry-run branch never
reaches a write at all, and that is a passing test rather than a comment, exactly as
`src/lib/reconcile/run.ts` did for the reconciliation engine.

Output: `run.ts`, `live-deps.ts`, `index.ts`, and a `run.test.ts` that proves the zero-write
guarantee, the three refusal reasons, drift override, resumability, and failure containment.
</objective>

    Create `src/lib/backfill/run.ts`. It imports only from `./types`, `./render-row`, `./report` and
    `./drift`. No `@/lib/db`, no `@/lib/storage`, no `@/lib/pdf`, no `server-only`. Everything
    external arrives through `args.deps`.

    Export `runBackfill(args: RunBackfillArgs): Promise<RunBackfillResult>`.

    Shared preamble for both modes: call `deps.listCandidates()` once, then `deps.getAdvisor()` ONCE
    for the whole run — not once per row. Annotate that choice: the advisor is a live read (D-02 /
    Phase 43 D-13), reading it once keeps every document in a single run internally consistent and
    avoids one query per proposal; a `null` advisor is a valid run and must NOT be guarded against or
    turned into a refusal.

    DRY-RUN branch:
    1. Loop the candidates serially — `for...of` with `await`, no `Promise.all`, no concurrency. Each
       PDF render is CPU- and memory-heavy and holds a Buffer; a serial loop keeps peak memory at one
       document. Log a progress line every 25 rows through `deps.log` in the form
       `[backfill] <n>/<total> planned` — the count only, never a proposal id, a blob key or a
       hostname.
    2. For each row call `renderRow({ row, advisor, mode: 'dry-run', deps })` and collect the
       `RowOutcome`. Do not retain the rendered Buffer beyond the call.
    3. Call `writeBackfillReport({ candidates, outcomes, databaseFingerprint, now: deps.now(),
       rootDir })`.
    4. Return the dry-run result form with `reportPaths` and `counts`.
    The dry-run branch must contain no call to `deps.putBlob`, `deps.persistPdfArtifact` or
    `deps.writeMarker` — those are reachable only from `renderRow` in apply mode.

    APPLY branch, in this order, with every gate returning before the loop:
    1. `readLatestBackfillReport(rootDir)`. `null` → return
       `{ mode:'apply', aborted:true, reason:'no-dry-run-report' }` and log that no approved report was
       found. This is the guard that makes "apply without an approved dry run" impossible.
    2. `stored.databaseFingerprint !== args.databaseFingerprint` → return
       `reason:'fingerprint-mismatch'`. The report was made against a different database; approving a
       plan for one database must never authorise writes to another.
    3. Re-plan: use the candidates already fetched in the preamble (the fresh set), and call
       `deps.listMigratedIds()`. Compute `computeBackfillDrift({ stored, fresh: candidates,
       migratedIds })`.
    4. `drift.status === 'drift'` and `!allowDrift` → log `formatBackfillDrift(drift)` and return
       `reason:'drift'` with the drift attached. `drift.status === 'drift'` and `allowDrift` → log the
       same text plus a line stating drift was accepted via `--allow-drift`, then continue.
    5. Only now, the loop: serially call `renderRow({ row, advisor, mode: 'apply', deps })` for every
       candidate, collecting outcomes. Best-effort per row — `renderRow` never throws, so no try/catch
       is needed around it, but if one is added it must continue rather than rethrow. Log a progress
       line every 25 rows.
    6. Return `{ mode:'apply', aborted:false, counts, failures, drift }` where `failures` is the
       `RowOutcome[]` filtered to `status === 'failed'`. Log a closing summary in purge's style:
       migrated count, failed count, and, when any failed, a line saying a re-run retries exactly the
       failed rows because they remain unmarked. The caller (plan 05's CLI) is what turns a non-empty
       `failures` into a non-zero exit code — say so in a comment so nobody "helpfully" calls
       `process.exit` from inside this module.

    Add a module docstring stating, in the shape of reconcile's: the dry run is not a convenience,
    MIG-01 requires it to write zero blobs and zero rows and `run.test.ts` is where that is proven;
    and D-01 removed the rollback, so gates 1-4 are the entire safety net between the approved plan
    and an irreversible overwrite.

    Write `src/lib/backfill/run.test.ts` with a fully stubbed `BackfillDeps` and a temp `rootDir`.
    Cover at minimum:
    - ZERO WRITES IN DRY-RUN: with three candidates, `deps.putBlob`, `deps.persistPdfArtifact` and
      `deps.writeMarker` all have `toHaveBeenCalledTimes(0)`, while `deps.renderPdf` was called three
      times. Name the test for MIG-01.
    - The dry-run report file exists afterwards and its `counts.candidates` is 3.
    - A candidate whose stored `computed` is `null` appears in the report as a failure with reason
      `invalid-computed`, and the other two still render — the log-and-continue proof (D-10).
    - `getAdvisor` is called exactly once for a three-row run.
    - A run with `advisor` resolving to `null` completes with `ok` outcomes.
    - APPLY, NO REPORT: apply against an empty `rootDir` returns `aborted: true, reason:
      'no-dry-run-report'` and `deps.putBlob` was never called.
    - APPLY, FINGERPRINT MISMATCH: write a report with fingerprint `aaa`, run apply with `bbb` →
      `reason: 'fingerprint-mismatch'`, zero writes.
    - APPLY, DRIFT: write a report for ids [A, B], run apply with fresh [A, B, C] and empty
      `migratedIds` → `reason: 'drift'`, zero writes.
    - APPLY, DRIFT OVERRIDE: the same case with `allowDrift: true` → `aborted: false` and
      `deps.putBlob` called three times.
    - RESUMABILITY (MIG-05): write a report for ids [A, B], then run apply with fresh [B] and
      `migratedIds` [A] → `aborted: false` and exactly one `putBlob` call, for B. Then run apply again
      with fresh [] and `migratedIds` [A, B] → `aborted: false`, zero `putBlob` calls,
      `counts.rendered === 0`. This pair is the executable form of MIG-05.
    - FAILURE SURFACING: an apply where one row's `putBlob` rejects returns `failures` of length 1 and
      `aborted: false`, and the other rows still completed.
    - A source-level assertion that `run.ts` matches neither `/process\.exit/` nor

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| approved report on disk → the write loop | A JSON file, downloaded from a GitHub artifact into the apply job's workspace, is what authorises an irreversible bulk overwrite. |
| pure orchestrator → live database + blob store | `live-deps.ts` is the single crossing point between the tested logic and production credentials. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-17 | Elevation of privilege | `runBackfill` apply branch | mitigate | Three gates return before the loop — missing report, fingerprint mismatch, drift — each with a distinct `BackfillAbortReason` and each covered by a test asserting `deps.putBlob` was never called. There is exactly one loop that writes and it sits after all three. |
| T-44-18 | Tampering | dry-run branch silently writing | mitigate | The dry-run branch never reaches `putBlob`/`persistPdfArtifact`/`writeMarker` (they are only reachable from `renderRow` in apply mode) and a `toHaveBeenCalledTimes(0)` test pins it. |
| T-44-19 | Information disclosure | `deps.log` output | mitigate | Progress lines carry counts only. No proposal id, blob key, user id, hostname or URL is logged from `run.ts`; drift lines print proposal ids only, and every error `detail` was already passed through `redactDetail` in plan 02. Script output is expected to be pasted into transcripts (`scripts/_db-branch-guard.ts` docstring). |
| T-44-20 | Information disclosure | `proposal.pdf_backfill` payload | mitigate | `live-deps.ts` writes `{ language, pdfSizeBytes }` and nothing else; pinned by a grep gate that `computeLoyer`/`getLatestGlobalParams` never appear in the file. |
| T-44-21 | Tampering | widening the persisted column set | mitigate | `persistPdfArtifact` is wired to the existing `finalizePdfBlobOnProposal`, which sets only the four PDF columns; no new update function is written, so `inputs`/`paramsSnapshot`/`computed` remain unreachable from this phase (DATA-01..04). |
| T-44-22 | Denial of service | memory exhaustion on a large run | mitigate | The loop is serial with no `Promise.all`, so peak memory holds one PDF Buffer; buffers are not retained after `renderRow` returns. |
| T-44-23 | Elevation of privilege | blob made public or long-lived signed URL | mitigate | `putBlob` passes key, buffer and `contentType` only; the adapter has no public-access option and `DEFAULT_CACHE_CONTROL` stays `private, max-age=0, no-store`. This phase issues no signed URL and changes no TTL. |
| T-44-SC | Tampering | npm/pip/cargo installs | mitigate | No dependency is added in this plan. No package-manager install task exists. |
