<objective>
Make the `sales` role real in the application layer: widen the `Role` type and the
`requireUser()` resolution, add the partner-or-sales route gate the new `/clients` tree needs,
and update every admin-facing query and mutation that currently hardcodes `role = 'partner'` so
Commercial accounts do not silently disappear from admin oversight the moment the migration
backfills them.

Purpose: ROLE-01 requires the CHECK constraint and *every access gate* to move together. Plan
30-01 shipped the constraint and the backfill; this plan is the other half. Without it, a
`Commercial` account becomes invisible to `/partners`, drops out of the "Partenaires actifs"
tile and vanishes from the admin activity feed — an admin *losing* visibility, which ROLE-03
forbids.

Output: a three-role auth layer, four widened queries, `partnerType`-driven role derivation on
the invitation flow, and regression tests proving nothing changed for `partner` or `admin`.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `users.role` DB value → `Role` type | untrusted-at-runtime string crossing into authorization decisions |
| admin form submission → `users.role` | a client-supplied `partnerType` influencing an authorization field |
| Better Auth session cookie → role | a value cached for up to 5 minutes |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-03-01 | Elevation of Privilege | `requireUser()` role resolution | mitigate | Allowlist over `['partner','admin','sales']` with a fail-closed default of `'partner'`; an unrecognised DB value can never resolve to `'admin'` |
| T-30-03-02 | Elevation of Privilege | `partnerType` → `role` derivation | mitigate | `roleForPartnerType` returns only `'partner'` or `'sales'` and is grep-asserted to contain no `role: 'admin'` write; the derivation runs server-side inside `requireAdmin()`-gated actions, never from a client-supplied role field |
| T-30-03-03 | Elevation of Privilege | re-inviting or re-typing an existing admin | mitigate | Both actions read the current row's `role` and skip the write when it is `'admin'`, so an admin cannot be demoted (or, through a subsequent re-promotion path, laundered) |
| T-30-03-04 | Information Disclosure | admin oversight of Commercial accounts | mitigate | Every `role = 'partner'` predicate widened to `IN ('partner','sales')`, grep-asserted to zero remaining occurrences, so the 30-01 backfill cannot hide accounts from `/partners`, the aggregates or the activity feed (ROLE-03) |
| T-30-03-05 | Information Disclosure | commission envelope (ADMIN-09) | mitigate | The only new projection is `users.role`, an access classification; a grep gate requires zero non-comment `commission`/`params_snapshot`/`global_params` references in the four widened query files |
| T-30-03-06 | Spoofing | stale cookie-cached role after a role change | accept | Better Auth `cookieCache.maxAge` is 5 minutes, but `requireUser()` re-reads `role` from the DB on every request (AUTH-16), so the cached value is never the one authorization uses |
| T-30-03-07 | Elevation of Privilege | `sales` reaching an admin surface | mitigate | `requireAdmin()` is unchanged and compares against `'admin'` exactly; a unit test asserts `notFound()` fires for `'sales'` |
| T-30-03-SC | Tampering | npm/pip/cargo installs | mitigate | No package install occurs in this plan |
