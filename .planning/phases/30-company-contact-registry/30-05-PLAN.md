<objective>
Build the write layer for the registry: the create-client action with silent server-side SIREN
dedup (CRM-01), and contact create / update / delete scoped to the owning relationship (CRM-04).
Every mutation re-proves ownership in its own SQL, and none of them ever tells the caller that a
company or relationship belongs to somebody else.

Purpose: dedup is where CRM-02 is easiest to break. "This company already exists" is the natural
thing to tell a user and the exact channel-conflict leak this phase exists to prevent. The
resolution is that dedup is silent: the same "Client créé." message regardless of whether the
company row was created or reused.

Output: `src/lib/crm/schemas.ts`, `src/lib/crm/actions.ts`, an extended audit-action union, and
tests covering the leak-shaped failure modes.
</objective>

`export async function createClientRelationshipAction(raw: unknown): Promise<{ relationshipId:
string }>`:
1. `const { session } = await requireRelationshipHolder();` — FIRST, before any data access
   (PITFALLS §7.3 ordering rule).
2. `const input = createClientSchema.parse(raw);`
3. Inside a single `db().transaction(async (tx) => { ... })`:
   - If `input.siren` is present: `SELECT id FROM companies WHERE siren = $siren`. If found, use it.
     If not, `INSERT INTO companies (name, siren) ... ON CONFLICT (siren) DO NOTHING RETURNING id`,
     and if the insert returned nothing (a concurrent creator won), re-select by siren. Do not
     branch the user-visible outcome on which path ran.
   - If `input.siren` is absent: always `INSERT INTO companies (name)`. Do NOT attempt any
     `name_normalized` match — cross-partner name matching is explicit Phase 31 scope
     (IMPORT-03/04), and doing it here would leak the existence of another partner's company.
   - `INSERT INTO client_relationships (company_id, owner_id) VALUES ($companyId,
     $session.user.id)` with `.onConflictDoNothing()` on the `(company_id, owner_id)` unique index,
     `RETURNING id`. If nothing was returned, `SELECT id FROM client_relationships WHERE company_id
     = $companyId AND owner_id = $session.user.id` — the caller already held this client, so return
     their existing id. `owner_id` is ALWAYS `session.user.id`; the action signature must expose no
     owner parameter at all.
4. `writeAuditLog({ actorId: session.user.id, action: 'client_relationship.create', targetType:
   'client_relationship', targetId: relationshipId, payload: { companyId } })`. Do not put the
   company name or SIREN of a pre-existing company in the payload beyond what the caller
   themselves submitted.
5. Wrap in try/catch. On any failure `console.error` the raw error server-side and throw
   `new Error('clients.toast.error')` — a single bounded key, identical for every failure class,
   so a caller cannot distinguish "SIREN conflict with another partner" from "database down"
   (the `classifyError` discipline established in plan 05-07).

Extend the `action` string union in `src/lib/db/queries/audit-log.ts` with
`'client_relationship.create'`, `'contact.create'`, `'contact.update'` and `'contact.delete'`,
each with a short trailing comment in the file's existing style.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → server action | arbitrary JSON reaching a mutation, including ids the caller does not own |
| error message → partner | a message whose wording could confirm another partner's data |
| audit payload → admin log | data written under an actor's identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-05-01 | Elevation of Privilege | forged owner in an action payload | mitigate | No action accepts an owner parameter; `owner_id` is always `session.user.id` from `requireRelationshipHolder()`. Grep-asserted on the exported signatures |
| T-30-05-02 | Information Disclosure | SIREN dedup revealing another partner's company | mitigate | Dedup is silent — attaching to an existing company and creating a new one both return `{ relationshipId }` and both surface "Client créé."; no "already exists" wording appears anywhere in the module (grep-gated) (CRM-02) |
| T-30-05-03 | Information Disclosure | error-message oracle | mitigate | Every failure class throws the single bounded key `clients.toast.error`; the raw error goes to `console.error` server-side only, following the `classifyError` discipline from plan 05-07 |
| T-30-05-04 | Elevation of Privilege | IDOR on contact mutations | mitigate | Each mutation compiles `owner_id = session.user.id` into its own single statement (`INSERT…SELECT`, `UPDATE…WHERE…IN (SELECT…)`, `DELETE…WHERE…IN (SELECT…)`); zero affected rows throws. No separate check-then-act path exists (CRM-04) |
| T-30-05-05 | Tampering | TOCTOU between ownership check and write | mitigate | The check and the write are the same statement, so no window exists between them |
| T-30-05-06 | Repudiation | untracked registry mutations | mitigate | Every action writes an `audit_log` row with `actorId = session.user.id` and a bounded payload |
| T-30-05-07 | Information Disclosure | commission envelope (ADMIN-09) | mitigate | Audit payloads carry only ids and caller-submitted values; no `global_params`, `params_snapshot` or commission field is read or written by this module |
| T-30-05-08 | Elevation of Privilege | admin using the partner mutation path | mitigate | `requireRelationshipHolder()` calls `notFound()` for admins, so admins cannot create relationships or contacts under their own identity through this surface |
| T-30-05-09 | Denial of Service | duplicate-submit creating runaway rows | mitigate | `client_relationships_company_id_owner_id_uq` plus `onConflictDoNothing` makes create-client idempotent per (company, owner) |
| T-30-05-SC | Tampering | npm/pip/cargo installs | mitigate | No package install occurs in this plan |
</threat_model>
