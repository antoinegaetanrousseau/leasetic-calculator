<objective>
Build the read layer for the registry: an owner-scoped client book with cursor pagination,
server-side sort and free-text search (CRM-07), the owner-scoped relationship / contacts /
proposals fetches behind the client detail page (CRM-06, CRM-02), and the admin-only company
registry queries (CRM-03). Prove cross-tenant isolation with both unit assertions and a real
Postgres integration test.

Purpose: CRM-02 is the requirement most likely to regress silently. Putting the ownership
predicate inside the query function signature — as a required argument that is always compiled
into the WHERE — makes it impossible for a page or action to forget it, and makes the omission a
type error rather than a data leak.

Output: two new query modules, a barrel export, unit tests introspecting every WHERE clause, and
a skip-by-default integration test that runs the real cross-tenant probes.
</objective>

`export interface ClientBookRow { relationshipId: string; companyId: string; companyName: string;
siren: string | null; proposalsCount: number; lastActivityAt: Date | null; createdAt: Date }`

`export type ClientBookSort = 'company' | 'lastActivity'`
`export type ClientBookDir = 'asc' | 'desc'`

`export async function listClientBook(args: { ownerId: string; q?: string; sort?: ClientBookSort;
dir?: ClientBookDir; cursor?: string; limit?: number }): Promise<{ rows: ClientBookRow[];
nextCursor: string | null }>`
- `FROM client_relationships INNER JOIN companies ON companies.id = client_relationships.company_id`
- `LEFT JOIN proposals ON proposals.client_relationship_id = client_relationships.id AND proposals.status <> 'deleted'`,
  `GROUP BY` the relationship + company columns, selecting `COUNT(proposals.id)` as
  `proposalsCount` and `MAX(proposals.created_at)` as `lastActivityAt`
- WHERE always includes `eq(schema.clientRelationships.ownerId, args.ownerId)`
- `q` search: `or(ilike(companies.name, '%'+q+'%'), ilike(companies.siren, '%'+q+'%'))` — use
  Drizzle's `ilike()` so the pattern is bind-parameterized, never string-concatenated into raw SQL.
  A null `siren` must not break the search; `ilike` on NULL yields NULL which `or` treats as
  non-matching, which is the desired behavior.
- Sort defaults: `sort = 'lastActivity'`, `dir = 'desc'`. Sorting is server-side only; the cursor
  tuple must be built from the ACTIVE sort key plus `client_relationships.id` as tiebreak, so
  "Charger plus" appends rows already in the correct order. For `sort = 'company'` order by
  `companies.name` then `client_relationships.id`; for `lastActivity` order by the aggregate then id.
  Use `NULLS LAST` on the `lastActivity` ordering so relationships with zero proposals sort to the
  end rather than jumping to the top on a DESC ordering.
- Cursor: base64url JSON `{ k: string; id: string }` where `k` is the stringified active sort key
  value (ISO 8601 for a date, raw text for a name). Encode/decode exactly like `partners.ts`; return
  `null` from `decodeCursor` on any malformed input and treat that as "no cursor" rather than throwing.
- Overflow probe with `limit + 1`, default limit 20.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| page/action → query module | a caller that could omit or forge the owner scope |
| search input `q` → SQL | untrusted free text reaching an ILIKE pattern |
| cursor string → SQL | untrusted base64url payload reaching an ORDER BY comparison |
| result metadata (counts, totals, cursors) → partner | aggregates that could reveal another partner's rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-30-04-01 | Information Disclosure | cross-tenant read of relationships | mitigate | `ownerId` is a required non-optional parameter on every partner-facing function and is compiled into the WHERE; a table-driven unit test asserts the predicate for every exported function, and the integration test proves zero rows for a non-owner (CRM-02) |
| T-30-04-02 | Information Disclosure | IDOR on `/clients/[id]` | mitigate | `getClientRelationshipForOwner` returns `null` for both "not found" and "not yours"; callers map `null` to `notFound()`, never 403, so the two are indistinguishable (D-18) |
| T-30-04-03 | Information Disclosure | contact leakage | mitigate | `listContactsForRelationship` joins `client_relationships` and carries `owner_id = ownerId` in the SAME statement; it accepts no pre-checked boolean and performs no TypeScript-side filtering (CRM-04) |
| T-30-04-04 | Information Disclosure | inference via counts, totals or pagination | mitigate | No total-count or page-count is computed anywhere; `proposalsCount` and `lastActivityAt` are aggregates over rows already inside the owner scope, and `nextCursor` is derived from the last in-scope row. `DataGridPagination` (the only component needing a global count) is not adopted — see plan 30-06 |
| T-30-04-05 | Information Disclosure | inference via search suggestions | mitigate | The only query surface is a server-side `ilike` over the caller's own scope; there is no autocomplete, typeahead or suggestion endpoint (UI-SPEC A-5) |
| T-30-04-06 | Tampering | SQL injection via `q` | mitigate | `q` reaches Drizzle's `ilike()`, which bind-parameterizes the pattern; it is never concatenated into a `sql\`\`` template |
| T-30-04-07 | Tampering | forged or malformed cursor | mitigate | `decodeCursor` returns `null` on any parse failure and the caller treats that as "no cursor"; the decoded values are interpolated through Drizzle's parameterized `sql` tag with explicit casts, and a forged cursor can at worst re-window the caller's own already-scoped result set |
| T-30-04-08 | Information Disclosure | commission envelope (ADMIN-09) | mitigate | No query selects `params_snapshot` or anything from `global_params`; where a monthly figure is needed it is projected as a single scalar, never the raw `computed` JSONB. Grep-gated in both modules |
| T-30-04-09 | Elevation of Privilege | admin queries called from a partner page | mitigate | Admin functions live in a separate module (`companies.ts`) whose header states it performs no authorization and must sit behind `requireAdmin()`; an accidental partner-side import is visible on the import line |
| T-30-04-SC | Tampering | npm/pip/cargo installs | mitigate | No package install occurs in this plan |
</threat_model>
