# Phase 30 — UI Design Contract

> Visual and interaction contract for Phase 30 (Company & Contact Registry). Generated by
> gsd-ui-researcher in `--auto` mode (no interactive questions — see Assumptions section).
> Verified by gsd-ui-checker.

**Requirements covered:** CRM-01..08, ROLE-01..03.
**Language:** All user-visible copy below is French (product default), matching existing
`dictionaries.ts` tone — short, sentence case, muted subtitle sentences ending in a period,
UPPERCASE only for table column headers and `.ctitle` section eyebrows.

## Design System

| Property | Value |
|----------|-------|
| Tool | **none** — no `components.json` on this branch (see Assumption A-1) |
| Preset | not applicable |
| Component library | Hand-rolled Tailwind v4 + CSS custom properties (`app/globals.css`) — `.card`, `.fld`, `.chip`, `.btn-green/navy/out`, `.dg`, `.yn-group` primitives. No Radix/shadcn/cva in `package.json` on this branch. |

This phase adds **zero new design tokens**. Every color, radius, spacing, and typography value
below is a token or literal already shipped in `app/globals.css` / existing components. New
surfaces reuse existing primitives (`PageHero`, `StatusChip`, `SearchBar`, `.card`, table chrome
from `PartnersList.tsx`, modal chrome from `CreatePartnerModal.tsx`, `EmptyBlock` pattern from
`ProposalsList.tsx`) rather than inventing new ones.

## Spacing Scale

The codebase does not use named spacing tokens (no `--space-*` CSS vars) — it uses literal px
values consistently at 4px increments. Declared scale for this phase, matching shipped usage:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside chips/badges |
| sm | 8px | Inline gaps (icon+label buttons, PageHero eyebrow-to-title) |
| md | 16px | Card internal padding subdivisions, form field vertical rhythm, gap between stacked cards |
| lg | 20–24px | Table cell padding (`16px 20px`), section padding, PageHero-to-content gap |
| xl | 28–32px | `.card` padding (28px), PageHero bottom margin (32px) |
| 2xl | 48px | Empty-state block vertical padding range (40px used, rounds to this band) |

Exceptions: table header/cell padding uses `12px 20px` / `16px 20px` (not a clean 4px multiple
step but exact match to `PartnersList.tsx` — reuse verbatim, do not invent new values). Modal
panel padding is `28px`; backdrop z-index `200`, panel z-index `201` (from `CreatePartnerModal`).

## Typography

The codebase already runs a richer scale than the generic 3–4/2-weight guideline (in production
since Phase 4/16). Declared for Phase 30 — reuse these four sizes and three weights exactly,
introduce no new ones:

| Role | Size | Weight | Line Height | Existing precedent |
|------|------|--------|-------------|---------------------|
| Page title (H1) | 32px | 700 | 1.2 | `PageHero` title |
| Table header / eyebrow | 11.2–11.8px | 700, uppercase, `letter-spacing: 0.04–0.06em` | 1.4 | `PartnersList` `TH_BASE_STYLE`, `.ctitle` |
| Body / row primary text | 14.5px | 400 (body copy), 600 (row emphasis: names, values) | 1.55 | global `body` rule; `PartnersList` name cell |
| Small / secondary text | 13px | 400 | 1.4 | `PartnersList` email cell, muted metadata, empty-state body |

Deviation note (accepted, matches existing codebase): three weights in active use — 400 regular,
600 semibold (row emphasis, active states), 700 bold (H1 + uppercase labels) — rather than a
strict 2-weight system. This mirrors every shipped phase since Phase 4; do not attempt to
collapse to 2 weights as part of this phase.

## Surface-by-Surface Contract

### 1. Route map (new)

| Route | Layout group | Access | Purpose |
|---|---|---|---|
| `/clients` | `(authed)` | `partner`, `sales` | Client book — CRM-07 |
| `/clients/[id]` | `(authed)` | `partner`, `sales` (owner-of-relationship only) | Client detail — CRM-06, CRM-04 |
| `/[adminSegment]/companies` | `(admin)` | `admin` | Company registry list — CRM-01, CRM-03 |
| `/[adminSegment]/companies/[id]` | `(admin)` | `admin` | Company detail, all relationships — CRM-03 |

`[id]` on `/clients/[id]` is the **relationship ID** (`client_relationships.id`), not the company
ID — a partner never addresses a company directly, only their own relationship to it. This is
load-bearing for CRM-02: the route itself cannot be used to probe another partner's relationship
IDs into visibility, because `requireUser()` + an ownership check (`relationship.partnerId ===
session.user.id`) gates the page exactly like `proposals/[id]/page.tsx` gates on
`proposal.userId !== session.user.id` → `notFound()` (not 403 — same D-18 URL-obscurity
convention: a partner probing another partner's relationship ID gets an identical 404 to a
nonexistent ID, never a "found but not yours" signal).

`/[adminSegment]/companies/[id]` uses the **company ID** — this is the one surface allowed to
address the shared record directly, because only admins reach it.

### 2. Client book — `/clients` (CRM-07)

Composition (server component page, mirrors `partners/page.tsx` exactly):

1. `<PageHero title="Clients" subtitle="Retrouvez vos clients et leurs propositions." actions={<Link className="btn-green">Nouveau client</Link>} />`
2. `<SearchBar lang={lang} />` (reused verbatim — already generic, placeholder key
   `clients.search.placeholder` = **"Rechercher un client…"**)
3. List: a table reusing `PartnersList.tsx`'s exact chrome (`TH_BASE_STYLE`/`TD_BASE_STYLE`,
   `.card` wrapper with `padding: 0, overflow: hidden`, cursor-based "Charger plus" footer link
   styled `.btn-out`). Columns:
   - **CLIENT** (company name, bold 14.5/600, `var(--ink)`)
   - **SIREN** (13px muted, or "—")
   - **PROPOSITIONS** (count, 13px muted, right- or center-aligned)
   - **DERNIÈRE ACTIVITÉ** (most recent proposal `createdAt` for this relationship, formatted via
     existing `formatDate()`, em-dash fallback — same pattern as `PartnersList` `lastActivityAt`)
4. Row click → navigates to `/clients/{relationshipId}` (entire `<tr>` clickable, matching the
   `ProposalRow` clickable-div convention, not just a link in one cell).

**Query scope (CRM-02 enforcement, UI-visible consequence):** the list query is always scoped to
`WHERE client_relationships.partner_id = session.user.id` (or `sales`'s own ID). There is no
admin-style "all clients" toggle on this page, no cross-partner count anywhere on this surface,
and the search box searches only within the caller's own relationships — never across the shared
`companies` table directly. Typing a company name that exists globally but is held only by
another partner must return the plain "Aucun résultat." empty state above, with zero UI signal
that a record exists.

Empty states: "zero clients" (see Copywriting) vs "search yields nothing" (see Copywriting),
using the same `EmptyBlock` pattern from `ProposalsList.tsx` (icon 38px/`strokeWidth 1.3`/muted/
opacity 0.4 — use `Building2` for zero-clients, `SearchX` for zero-search-results).

### 3. Create-client flow (feeds CRM-01 + CRM-07's "+ Nouveau client")

A modal, chrome copied verbatim from `CreatePartnerModal.tsx` (backdrop `rgba(17,44,59,0.45)`
z-index 200, centered panel `max-width: 480px` z-index 201, focus trap + Escape-to-close, RHF +
zodResolver, `.fld` field chrome). Two fields only: **Nom de la société** (required, text) and
**SIREN** (optional, 9-digit numeric validation when present). Submit button: `.btn-green`
**"Créer le client"**.

**Security-critical interaction constraint (CRM-02):** this form has **no autocomplete, no
typeahead, and no "existing company found" suggestion UI** as the partner types the name or
SIREN. Server-side dedup happens silently on submit:
- If SIREN is provided and matches an existing `companies.siren`, the new relationship attaches
  to that existing (shared) company row. The partner sees only a generic success toast —
  **"Client créé."** — never a message implying the company record pre-existed or naming another
  partner.
- If no SIREN is provided, or the SIREN is new, a new `companies` row is created for this
  relationship (name-only fuzzy matching against other partners' companies is explicitly Phase 31
  scope, not Phase 30 — see REQUIREMENTS.md "Out of Scope: Fuzzy matching at query time").

On success: modal closes, toast **"Client créé."**, redirect to the new `/clients/{relationshipId}`.

### 4. Client detail — `/clients/[id]` (CRM-06, CRM-04)

Composition mirrors `proposals/[id]/page.tsx`'s two-column layout (no custom `<main>` wrapper —
render directly inside `Shell`'s existing `<main>`, which already caps at 1100px / 24px padding;
do **not** repeat `PartnersPage`'s nested `<main maxWidth:1280>` pattern, that is a pre-existing
outlier, not a convention to imitate):

**Header row** (mirrors proposal-detail header):
- `<h1>` = company name, 22px/700/`var(--ink)` (matches `proposal.detail.title` sizing, not the
  32px PageHero size — this is a sub-page, same visual weight class as the proposal detail title)
- SIREN shown inline next to the title, small/muted, or omitted entirely when absent (never "—"
  in a header context — simply don't render the SIREN chip if null)
- No status chip here (relationships don't have a lifecycle status yet — that's Phase 33 PIPE-01)

**Left column (primary, ~640px):**
- Card 1 — **"Contacts"** (`.ctitle` with teal dot, matching `proposal.detail.section.inputs`
  precedent): list of contact cards, each showing name (600 weight), role (13px muted), phone +
  email (13px muted, icon-prefixed using `Phone`/`Mail` lucide icons at 14px). Each contact row
  carries an edit (pencil) and delete (trash, `var(--danger)` on hover) icon-button pair,
  right-aligned, `strokeWidth={1.6}`, matching the icon-button sizing already used in
  `PartnerRowActions`. "+ Ajouter un contact" `.btn-out` button below the list (not `.btn-green` —
  reserve green for the one primary page-level CTA which lives in the PageHero-equivalent header
  area; this is a secondary in-card action, same tier as "+ Nouveau partenaire" secondary
  affordances elsewhere).
- Card 2 — **"Propositions"** (`.ctitle` with gold dot, matching `proposal.detail.section.computed`
  precedent): reuses the existing `ProposalRow` component list (LC ref, client-facing amount,
  date, `StatusChip`) filtered to `client_relationship_id = this relationship`. Each row links to
  the existing `/proposals/[id]` detail page — no new proposal-row component needed.

**Right column (360px, sticky):** not required for Phase 30 (no PDF preview applies at the
relationship level) — omit the right column entirely and let the left column run full-width up to
640px, OR keep a single-column 640px-max layout centered. **Decision (see Assumption A-2):**
single-column, `max-width: 720px`, no sticky sidebar — this surface has no natural "preview"
object the way a proposal has a PDF.

**Contacts editor interaction (CRM-04):**
- Add/Edit: modal, identical chrome to `CreatePartnerModal.tsx` (480px panel, focus trap, RHF +
  zod). Fields: Nom (required), Fonction (optional), Téléphone (optional, no format enforcement
  beyond non-empty-if-provided), Email (optional, email-format validated when non-empty). Submit
  label: **"Enregistrer le contact"** (add) / **"Enregistrer les modifications"** (edit — reuse
  same modal component with a `mode: 'create' | 'edit'` prop and pre-filled `defaultValues`).
- Delete: `window.confirm()` inline per the Copywriting Contract row above — no modal, matching
  `DeleteButtonClient`'s convention for single-item destructive actions elsewhere in this app.
- Validation errors render inline via `.error-msg` under each field, exactly like
  `CreatePartnerModal`'s email-exists pattern.

**Visibility enforcement (CRM-02 + CRM-04, UI-visible consequence):** `requireUser()` first,
then `relationship.ownerId !== session.user.id → notFound()` (D-18 pattern — 404, not 403). The
Contacts card and its data are fetched only after that ownership check passes; there is no
code path where another partner's contact rows are queried and then hidden client-side — they are
never fetched.

### 5. Admin company view — `/[adminSegment]/companies` + `/[adminSegment]/companies/[id]` (CRM-03)

Must **visually distinguish itself from the partner view** per phase scope. Distinguishing
elements (reusing existing admin-surface conventions, not inventing new ones):
- Lives under the `[adminSegment]` URL prefix (same obscurity gate as `/partners`, `/coefficients`).
- Sidebar entry appears only in the admin nav set, labeled **"Sociétés"**, icon `Building2`,
  positioned after `admin-partners` and before `admin-coefficients` in `RetractableSidebar.tsx`'s
  `adminNavItems`.
- List page (`/companies`) reuses the exact `PartnersList` table chrome, but an **extra
  "RELATIONS" column** (count badge, `chip chip-type` neutral style) makes clear this is an
  aggregate/oversight view, not a personal book — a partner's `/clients` list never shows a
  relations-count column because a partner only ever sees their own single relationship per row.
  Columns: **SOCIÉTÉ**, **SIREN**, **RELATIONS** (count), **DERNIÈRE ACTIVITÉ**.
- Detail page (`/companies/[id]`) header uses the `PageHero`-style H1 (32px/700 — the admin
  surface gets the full PageHero treatment other admin list pages get, e.g. `/partners`), with
  eyebrow **"SOCIÉTÉ"** in `var(--gd-text)` uppercase (matches the existing `PageHero eyebrow`
  precedent used for "ADMIN" elsewhere) — this is the visual tell that a partner's client-detail
  page (22px plain `<h1>`, no eyebrow) never has.
- Below the header: a **"Relations"** table (one row per `client_relationship`), columns:
  **TITULAIRE** (owner display name), **TYPE** (neutral badge: "Partenaire" / "Interne" per the
  Copywriting Contract), **CRÉÉE LE** (date), **PROPOSITIONS** (count), **CONTACTS** (count), and
  a **"Voir →"** link per row opening an admin-only relationship-detail view showing that
  relationship's own contacts + proposals (admin sees everything — no ownership gate here, only
  `requireAdmin()`).
- This "Voir →" per-relationship detail can reuse the partner-facing client-detail layout
  (Contacts card + Propositions card) with the eyebrow/owner name added to the header — same
  component, admin route, no ownership check, `requireAdmin()` gate instead of
  `relationship.ownerId` check.

**ADMIN-09 envelope:** none of the new columns/badges above are commission data — company name,
SIREN, relationship owner, dates, and proposal/contact counts carry zero commission signal. No
new grep-contract gate is anticipated to be needed for Phase 30, but the planner should confirm
no proposal aggregate query accidentally projects `params_snapshot`/commission fields onto these
new list/detail rows (same discipline as `ProposalRowDto` in the existing 19-gate suite).

### 6. Role surfacing — `sales` role (ROLE-01, ROLE-02)

- `Role` type in `src/lib/auth/require.ts` extends from `'partner' | 'admin'` to
  `'partner' | 'admin' | 'sales'`. `requireUser()`'s DB-role coercion
  (`role === 'admin' ? 'admin' : 'partner'`) must be corrected to a 3-way match — this is a code
  change the planner owns, flagged here only because it changes what `RetractableSidebar` derives
  `isAdmin`/nav-set from.
- **Sidebar nav:** `sales` users get the **same nav set as `partner`** (Home, Nouvelle proposition,
  Propositions, **Clients** (new), Aide) — per ROLE-02 "reaches the same pipeline/client-book
  surfaces a partner reaches." No new "Sales" visual nav treatment; a `sales` user's shell is
  pixel-identical to a `partner`'s except for the data scope underneath.
- **Admin-side role display/selection (new, this phase's UI surface for ROLE-01):** extend
  `CreatePartnerForm.tsx` / `CreatePartnerModal.tsx` with a segmented control (reuse the exact
  `.dg`/`.db.on` chrome already used for the Language `fr`/`en` picker in `CreatePartnerModal`),
  labeled **"Type de compte"**, two options: **"Partenaire"** (default, preserves current
  behavior) / **"Interne (Sales)"**. This sets `users.role = 'sales'` instead of `'partner'` at
  invitation time. On `PartnersList` (admin), a `sales` account shows the same row shape with its
  existing `partnerType` badge column now also capable of reading **"Interne"** as a role-driven
  overlay — **exact mechanism is an open design choice, see Assumption A-3.**
- **No visibility change for existing accounts (ROLE-03):** nothing above alters what an existing
  `partner` or `admin` row renders — the segmented control defaults to "Partenaire" and is purely
  additive on the create-invitation form.
