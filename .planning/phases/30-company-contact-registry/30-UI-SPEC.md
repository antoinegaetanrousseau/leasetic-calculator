## Spacing Scale

**D-B ratified exception, re-derived.** `app/globals.css` and the shadcn/base-maia primitives do
not use named spacing tokens — Tailwind's own 4px-step utility scale (`p-1`=4px, `p-2`=8px, `p-3`=
12px, `p-4`=16px, `p-5`=20px, `p-6`=24px, `p-7`=28px, `p-8`=32px, …) is used directly at every call
site inspected (`PageHero` `mb-8`/`mb-2`/`mt-2`, `.card` `padding: 28px`, `table-chrome.ts`
`px-5 py-3` / `px-5 py-4`, `SectionTitle` `mb-4`/`gap-2`). This is **finer than GSD's default
{4,8,16,24,32,48,64}** (it also uses 12px/20px/28px steps) but is **still a strict 4px-multiple
scale** — every value found divides evenly by 4. The base-maia migration did not introduce a
new/wider scale; if anything it made the existing exception unnecessary to justify further,
since nothing in the current codebase deviates from 4px steps. The exception is therefore
**retained in a narrower form**: declare the finer step, not a departure from multiples-of-4.

| Token | Value | Usage (verified against current code) |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps inside badges/chips (`gap-1`) |
| sm | 8px | Inline icon+label gaps (`PageHero` eyebrow-to-title, `.search-bar` gap) |
| md | 12px–16px | Table header cell padding (12px vertical), form field vertical rhythm, card-to-card stack gap |
| lg | 20px | Table cell horizontal padding (`px-5` = 20px), section padding |
| xl | 24px | Shell page padding (`Shell` `<main>` is `px-6` = 24px), 2-column grid gap on proposal detail |
| 2xl | 28px–32px | `.card` internal padding (28px, unchanged token), `PageHero` bottom margin (`mb-8` = 32px) |
| 3xl | 48px | Empty-state block vertical padding band (`.card px-6 py-12` ≈ 48px) |

Exceptions: none beyond the finer step itself — no non-4px-multiple literal was found anywhere
touched by this phase's surfaces. Radius is **not** a spacing concern here — it is driven
entirely by the single `--radius: 0.625rem` token via the `@theme inline` multiplier scale
(`--radius-sm/md/lg/xl/2xl/3xl/4xl`); new surfaces use `rounded-2xl` (cards) and `rounded-xl`
(inputs/segmented controls) exactly like existing surfaces, never a literal px radius.

## Typography

**D-B ratified exception, re-derived against Inter + base-maia.** The prior spec's 4-size/
3-weight table was measured against Plus Jakarta Sans and the old hand-rolled `body` rule; both
are gone. Re-measured against the current `app/globals.css` `body` rule and every shadcn/ReUI
primitive touched by this phase:

| Role | Size | Weight | Line Height | Verified against |
|------|------|--------|-------------|-------------------|
| Page title (H1 / `PageHero`) | 30px (`text-3xl`) | 700 (`font-bold`) | 1.2 (`leading-tight`) | `PageHero.tsx` line 31 |
| Sub-page title (client detail `<h1>`) | 22px | 700 | 1.2 | matches `proposal.detail.title` sizing precedent — see Surface 4 |
| Table header / `SectionTitle` eyebrow | 11.2–11.8px, 700, uppercase, `tracking-[0.04–0.06em]` | 700 | 1.4 | `table-chrome.ts` `tableHeadClass`, `SectionTitle.tsx`, `PageHero` eyebrow |
| Body / row primary text | 14.5px, 400 (body copy) / 600 (row emphasis: names) | 400 / 600 | 1.55 | `app/globals.css` `body` rule; `PartnersList.tsx` name cell (`font-semibold`) |
| Small / secondary / muted metadata | 13px | 400 | 1.4 | `table-chrome.ts` `tableCellClass`, `PageHero` subtitle |

**Two weights in active use for this phase's new surfaces: 400 (regular) and 600/700 (semibold/
bold, used interchangeably as "emphasis" — Tailwind's `font-semibold`/`font-bold` map to the same
Inter 600/700 files already loaded).** This is narrower than the old spec's "three weights,
never collapse" note: Inter is loaded at five weights (300/400/500/600/700) for latitude
elsewhere in the app, but nothing this phase touches reads 300 or 500. **Declare 2 in-scope
weights for Phase 30 (400, 700), reusing 600 only where an existing primitive already hard-codes
it (`PartnersList` row-name `font-semibold`)** — do not introduce a new 500-weight use in new
Phase 30 code. This satisfies the GSD 2-weight default without a fight; the "richer scale"
exception from the old spec is not needed at Inter's weights, only at spacing's finer step.

All values are CSS custom properties from `app/globals.css`. **Do not reintroduce `--paper`,
`--surface`, `--gd`, `--teal`, `--gold`, `--danger` as if they were primary tokens** — they are
legacy aliases kept only so ~400 pre-migration call sites keep working; they resolve to the
ReUI/shadcn tokens below and Phase 30's new code should read the shadcn tokens directly
(`bg-background`, `text-foreground`, `bg-card`, `text-muted-foreground`, `bg-primary`,
`text-destructive`, `bg-success/15 text-success-foreground`, etc.) the same way `StatusChip.tsx`
and `PageHero.tsx` already do.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` (`oklch(1 0 0)`, pure white light / `oklch(0.145 0 0)` dark) | Page background, `<body>` |
| Secondary (30%) | `--card` (aliased by legacy `.card` class → `--surface`) | `.card` panels, table surface, sidebar (`--sidebar`), dialog/sheet panels |
| Accent (10%) | `--primary` = `--brand-accent` (`#01cc72`, the ONE brand color that survived the migration by explicit decision 2026-08-29) | **Reserved for:** the single primary page-level CTA per surface ("Nouveau client", "Ajouter un contact" when it is the page-level action, `StatusChip variant="active"`, `SectionTitle` default bullet (`accent="gd"` → now literally `bg-primary`), the sidebar's active-item indicator |
| Destructive | `--destructive` | Delete-contact `AlertDialog` action button, delete-contact confirm copy, inline field validation errors (`aria-invalid` ring — global rule in `globals.css` already handles this for bare `<input>`; shadcn `Input`/`Field` style their own `aria-invalid` state) |
| Muted / secondary text | `--muted-foreground` | SIREN column, "DERNIÈRE ACTIVITÉ" column, empty-state body copy, contact role/phone/email secondary lines |
| Neutral badge | `--border` background / `--foreground` text (via shadcn `Badge variant="secondary"`, the same treatment `PartnersList`'s TYPE column already uses) | Relationship-owner-type badge ("Partenaire" / "Interne") on the admin company view — deliberately NOT `--primary`, so it never competes with the one accent CTA on the page |

**Accent reserved for (explicit list, never "all interactive elements"):** the "+ Nouveau client"
CTA on `/clients`, the "+ Ajouter un contact" CTA on the client detail page, `StatusChip
variant="active"` labels inside the Propositions list, and `SectionTitle`'s default bullet. Every
other button on these surfaces (secondary actions, "Annuler", filter clears, row overflow
triggers) uses shadcn `Button variant="outline"` or `variant="ghost"` — never `--primary`. This
collapses the old spec's separate "`--teal` link/focus accent, not counted against budget" carve-
out: `--teal` is now just an alias for `--muted-foreground` (see `app/globals.css`, "Legacy v10
aliases" block) — it is not a second brand color post-migration, so there is nothing left to
carve out. Links use `text-primary` (sparingly, e.g. "Voir la fiche société →") or
`text-muted-foreground` for inline secondary affordances, matching what `PartnersList`'s
"Effacer les filtres →" link already does (`text-teal` there resolves to muted-foreground now).

## Critical Adaptation — `solution-crm-3` Ownership Model Is Inverted

`solution-crm-3` is a **shared** contacts directory: any viewer sees every contact from every
account, and "Assign owner" bulk-reassigns contacts between reps from a plain dropdown
(`ContactsSelectionBar.tsx`) with zero access check. **This is structurally the opposite of
CRM-02/CRM-04.** Reused verbatim, it would let any partner browse every other partner's clients
and reassign ownership at will — the exact channel-conflict leak the phase exists to prevent.

What is reused vs. inverted, explicitly:

| `solution-crm-3` mechanic | Phase 30 equivalent | Inversion |
|---|---|---|
| `ContactsGridView` — one global grid, `CONTACTS` array, all accounts visible | Client book (`/clients`) — grid scoped server-side to `WHERE client_relationships.partner_id = session.user.id` | No cross-partner directory exists. There is no admin toggle on the partner-facing page to see "all clients." |
| `ContactsSelectionBar` — bulk "Assign owner" dropdown, no gate | **Not built for partners at all.** The closest analogue — reassigning which sales/house owner holds a relationship — is an **admin-only** action, and even then Phase 30 does not build a bulk-select UI for it; ROLE-02's "house relationship" assignment (if it needs a UI beyond direct DB/import assignment) is single-row, admin-gated, and out of this phase's explicit surface list. | Bulk multi-select checkboxes (`DataGridTableRowSelect`/`RowSelectAll`) are **omitted** from the Client book's columns entirely — not hidden, not disabled, not present in the column list. |
| `ActionsCell` dropdown → "View Details" opens a `Sheet` | Client book row click navigates to a full page, `/clients/{relationshipId}` | CRM-06 says "on one page" — a slide-over sheet is the wrong affordance for "browse every proposal I've made for them"; that needs real scroll room and a real URL to bookmark/share internally. Sheet chrome IS reused, but for the smaller Contact add/edit form (see Surface 3), not for the client record itself. |
| `AlertDialog` delete-contact confirm | Reused as-is (chrome and copy pattern), scoped to `DELETE` on a contact the caller owns via the relationship's ownership check, never a bare client-side `toast.message('Delete requested')` placeholder | Same UI, real authorization underneath |
| `IContact.company: string` (a free-text label, not an FK) | `contacts` FK-scoped to `client_relationships.id` (CRM-04) | The block's data model doesn't even have relationships as an entity — Phase 30's does, and contacts hang off the relationship, not the company, by design (CRM-04's explicit rationale: "the mobile number a partner worked to get is that partner's asset") |

**Compatibility note for Phase 31+:** `solution-crm-1/2/4/5` (pipeline dashboard, deal kanban,
deal detail sheet, activity timeline — Phase 33/34 surfaces) use `account: string` /
`owner: {name, avatar, initials}` / `activityType: 'call'|'email'|'meeting'|'note'|'task'` shaped
data. Phase 30's `client_relationships` (owner_id → users) and future `contacts`/`activity`
tables should keep an owner-display-name + avatar-friendly shape and a note/system-event type
enum that a Phase 34 timeline can consume directly — this is a forward-compatibility note for the
planner, not a Phase 30 UI surface.

## Surface-by-Surface Contract

### 0. Route map (new)

| Route | Layout group | Access | Purpose |
|---|---|---|---|
| `/clients` | `(authed)` | `partner`, `sales` | Client book — CRM-07 |
| `/clients/[id]` | `(authed)` | `partner`, `sales` (owner-of-relationship only) | Client detail — CRM-06, CRM-04 |
| `/[adminSegment]/companies` | `(admin)` | `admin` | Company registry list — CRM-01, CRM-03 |
| `/[adminSegment]/companies/[id]` | `(admin)` | `admin` | Company detail, all relationships — CRM-03 |

`[id]` on `/clients/[id]` is the **relationship ID** (`client_relationships.id`), never the
company ID — a partner addresses only their own relationship, never the shared company record
directly. This is load-bearing for CRM-02: `requireUser()` + `relationship.ownerId ===
session.user.id` gates the page exactly like `proposals/[id]/page.tsx` gates on `proposal.userId
!== session.user.id → notFound()` (D-18 pattern, confirmed still current in
`src/lib/auth/require.ts` — `requireAdmin()` calls `notFound()`, not a 403, "to preserve URL
secrecy"). A partner probing another partner's relationship ID gets an identical 404 to a
nonexistent ID.

`/[adminSegment]/companies/[id]` addresses the **company ID** directly — the one surface allowed
to, because only `requireAdmin()`-gated users reach it.

**Container convention:** neither new route repeats `PartnersPage`'s custom
`<main style={{maxWidth:1280}}>` wrapper — confirmed in `app/(admin)/[adminSegment]/partners/
page.tsx` this is a pre-existing outlier from before `Shell` had its own capped `<main>`
(`Shell.tsx` line 109: `max-w-[1100px] px-6 pt-6 pb-8`). New Phase 30 pages render directly
inside Shell's `<main>`, exactly like `/proposals` and `/proposals/[id]` already do.

### 1. Client book — `/clients` (CRM-07)

Composition (server component page):

1. `<PageHero title={t('clients.page.title')} subtitle={t('clients.page.subtitle')}
   actions={<Dialog>…<Button>Nouveau client</Button>…</Dialog>} />` — subtitle: **"Retrouvez vos
   clients et les propositions que vous leur avez faites."**
2. `<SearchBar lang={lang} />` — reused verbatim, zero changes. Placeholder key
   `clients.search.placeholder` = **"Rechercher un client…"**. It already renders
   `autoComplete="off"` (confirmed in `SearchBar.tsx`) — this is the existing default, not a new
   affordance added for CRM-02, but it is exactly the property A-5 depends on; no change needed,
   just confirmed compatible.
3. The list itself — **see the DataGrid decision below.**

**DataGrid decision (resolves the documented blocker head-on — REQUIREMENTS.md:121,
`reui-blocks-audit.md` §2):** ReUI's `DataGrid` is page-index (`PaginationState{pageIndex,
pageSize}`, `pageCount`); every list query in this app (`listPartnersWithLastActivity`, the
proposals list) is cursor-based (`buildListResponse`-style `{rows, nextCursor}`). Rather than
avoid `DataGrid` entirely (which would mean re-hand-rolling sortable/resizable column chrome
`PartnersList` doesn't have) or force cursor pagination into `pageIndex` math (which requires
knowing a total count the server never computes), **this phase splits the block's two concerns**:

- **Adopt:** `DataGrid` + `DataGridTable` + `DataGridColumnHeader` from `@/components/reui/
  data-grid/*` for the table itself — sortable column headers, consistent skeleton-loading cell
  shapes, TanStack-table-backed row model. This is a genuine upgrade over `PartnersList`'s plain
  shadcn `Table` and the first real adoption of DataGrid's table machinery in this app.
- **Do NOT adopt:** `DataGridPagination` (page-index footer). In its place, render the exact same
  cursor-based **"Charger plus"** `Button variant="outline"` link/control `PartnersList` and
  `ProposalsList` already use, wired to `nextCursor` from the server query. `recordCount` is
  passed as `rows.length` (current page only) — `DataGridPagination` is the only sub-component
  that needs a global count, and it is not used.
- **Do NOT adopt:** the `Filters` query-builder chrome (`is`/`contains`/`starts_with` operator
  UI). CRM-02 means the only legal query surface is "search within my own relationships" — a
  free-text box, not a field-and-operator builder that would invite constructing queries against
  fields the server doesn't expose. `SearchBar` (existing) stays the only filter affordance.
- **Do NOT adopt:** row selection (`DataGridTableRowSelect`/`RowSelectAll`) or the bulk
  owner-assignment bar. See the Critical Adaptation section above — this is the load-bearing
  inversion.

**Surface consistency decision: Card, not Frame.** `docs/design/reui-blocks-audit.md` frames this
as an open per-block choice ("no blanket rule… each block is previewed and judged on its own").
For Phase 30 the choice is not close: every existing list this app ships (`PartnersList`,
`ProposalsList`, the proposal detail's two content cards) wraps its content in the app's own
`.card` class (→ shadcn `Card` semantics, `rounded-2xl`, `--card`/`--border`/`--shadow-card`).
Wrapping the new DataGrid in `<Frame>` instead would introduce a third surface language into a
codebase that already resolved this exact ambiguity once (Phase 4, per the table-chrome.ts
comment: "shadcn `Table`... — LcReferencesList was carrying a verbatim copy"). **Client book,
client detail, and the admin companies list all use `.card` — `<Frame>`/`<FramePanel>`/
`<FrameHeader>` are not used anywhere in Phase 30.**

Columns (rendered via `DataGridColumnHeader` for sort affordance where sortable):

| Column | Sortable | Cell |
|---|---|---|
| CLIENT | yes | company name, `font-semibold`, `text-[14.5px]` |
| SIREN | no | 13px `text-muted-foreground`, or "—" |
| PROPOSITIONS | no | count, 13px muted, right-aligned |
| DERNIÈRE ACTIVITÉ | yes | most recent proposal `createdAt` for this relationship, `formatDate()`, em-dash fallback |

Row click → navigates to `/clients/{relationshipId}` (whole `<TableRow>` clickable, matching the
existing `ProposalRow` clickable-row convention — not just a link in one cell).

**Query scope (CRM-02 enforcement, UI-visible consequence):** the list query is always scoped to
`WHERE client_relationships.owner_id = session.user.id`. No admin-style "all clients" toggle
exists on this page. Typing a company name that exists globally but is held only by another
partner returns the plain "Aucun résultat…" empty state, with zero UI signal that a record
exists anywhere.

Empty states use shadcn `Empty`/`EmptyTitle`/`EmptyDescription` (`src/components/ui/empty.tsx`,
already installed, not yet adopted anywhere in the app — first real consumer) rather than a
hand-rolled `.card px-6 py-10/12 text-center` block: it is the design-system-correct primitive
for exactly this state and was installed by the migration specifically to replace ad hoc
empty-state markup. Icon: the new `BuildingIcon` (zero-clients) / existing `SearchIcon` at empty
size (search-yields-nothing) — see Component Inventory.

### 2. Create-client flow (feeds CRM-01 + CRM-07's "+ Nouveau client")

A shadcn `Dialog` (`@/components/ui/dialog`) — **not** a copy of `CreatePartnerModal.tsx`'s hand-
rolled `role="dialog"` chrome. `CreatePartnerModal` predates this migration and has not been
ported yet (confirmed: it still imports `segmentedGroupClass`/`segmentedItemClass` and a manual
backdrop); Phase 30 is new code and should use the real primitive rather than propagate the
legacy pattern forward. RHF + `zodResolver`, `Field`/`FieldLabel`/`FieldError` + shadcn `Input`
inside `DialogContent`.

Two fields only: **Nom de la société** (required, text) and **SIREN** (optional, 9-digit numeric
validation when present, helper text per Copywriting Contract). Submit button:
`<Button>Créer le client</Button>` (default/`--primary` variant — this dialog's one accent use).

**Security-critical interaction constraint (CRM-02, A-5 — hard requirement, not a UX
preference):** this form has **no autocomplete, no typeahead, and no "existing company found"
suggestion UI** as the partner types the name or SIREN. Server-side dedup happens silently on
submit:
- SIREN match against an existing `companies.siren` → the new relationship attaches to that
  existing (shared) company row. The partner sees only **"Client créé."** — never a message
  implying the company record pre-existed or naming another partner.
- No SIREN, or a new SIREN → a new `companies` row is created (name-only fuzzy matching across
  partners is explicit Phase 31 scope, not Phase 30 — REQUIREMENTS.md "Out of Scope: Fuzzy
  matching at query time").

On success: dialog closes, toast **"Client créé."**, redirect to `/clients/{relationshipId}`.

### 3. Client detail — `/clients/[id]` (CRM-06, CRM-04)

**Header:**

  sub-page title, one weight class below `PageHero`'s 30px)
- SIREN shown inline next to the title, small/muted, **omitted entirely when null** (never "—"
  in a header — headers don't render absent-optional chips at all, only body content does)
- No status chip — relationships have no lifecycle status until Phase 33 (PIPE-01)

**Section 1 — Contacts** (`<SectionTitle>Contacts</SectionTitle>` inside a `.card`, default

inputs`'s `accent="teal"` precedent structurally but using the default accent here since there is
no competing second section needing a different tint):
- List of contact rows: name (`font-semibold`), role (13px muted), phone + email (13px muted,
  icon-prefixed — new `PhoneIcon` + existing `MailIcon`, both `size={14}`)

  page-level `--primary` CTA for this surface lives in the header area if/when one is added —

**Section 2 — Propositions** (`<SectionTitle>Propositions</SectionTitle>` in its own `.card`):
- Reuses the existing `ProposalRow` component list (LC ref, client-facing amount, date,
  `StatusChip`) filtered to `client_relationship_id = this relationship`. Each row links to the
  existing `/proposals/[id]` detail page — **no new proposal-row component needed.**
- "+ Nouvelle proposition" CTA (this section's own secondary action) — links to
  `/proposals/new/parametres?clientRelationshipId={id}`.

**The "how does a proposal get linked" mechanism (previously unspecified — fixed here):** the
proposal wizard's step-1 route (`/proposals/new/parametres`) accepts an optional
`clientRelationshipId` search param. When present, the wizard: (a) validates the caller owns that
relationship (same `ownerId` check as the client-detail page — silently drops the param and
proceeds as a normal unlinked proposal if the check fails, never an error page, since a bad/stale
param should degrade gracefully, not block quoting); (b) pre-fills the client-info wizard fields
(`clientCo`, `clientSiren`, etc.) from the relationship's current company/contact data as a
**starting point the partner can still edit** (matches the existing `proposal.toast.duplicate.
prefilled` precedent: "Champs pré-remplis... Modifiez si nécessaire."); (c) carries the
`clientRelationshipId` through the wizard's server state and writes it to `proposals.
client_relationship_id` (CRM-05's nullable FK) at finalization — the `inputs` JSONB snapshot is
untouched, exactly as CRM-05 requires. A proposal started **without** this param (e.g. from the
sidebar's "Nouvelle proposition" or from `/proposals`) is created with `client_relationship_id =
NULL` and never retroactively linked — that is Phase 31's reconciliation-engine scope
(IMPORT-01), not Phase 30's.

**Empty states (both use shadcn `Empty`):**
- Zero contacts: `BuildingIcon`-adjacent — actually **UsersIcon** (existing, already used for
  "Partenaires" conceptually adjacent to "people") + copy from the Copywriting Contract + "+
  Ajouter un contact" CTA.
- Zero proposals: existing `FileTextIcon` (already in the vocabulary, used elsewhere for
  document-shaped empty states) + copy + "+ Nouvelle proposition" CTA.

**Contacts editor interaction (CRM-04):**
- Add/Edit: shadcn `Dialog`, same chrome as the create-client dialog (RHF + zod, `Field`/`Input`).
  Fields: Nom (required), Fonction (optional), Téléphone (optional, no format enforcement beyond
  non-empty-if-provided), Email (optional, email-format validated when non-empty, reusing
  `error.field.email.invalid`). Submit label: **"Enregistrer le contact"** (create) /
  **"Enregistrer les modifications"** (edit) — one component, a `mode: 'create' | 'edit'` prop,
  pre-filled `defaultValues` for edit.
- Delete: shadcn `AlertDialog` (see Copywriting Contract + Component Inventory — this is the
  first real-app adopter of `AlertDialog`, superseding `window.confirm()` for this one new
  interaction; existing `window.confirm()` call sites elsewhere in the app are unchanged and out
  of scope).
- Validation errors render via `FieldError` under each field, same pattern as `CreatePartnerForm`.

**Visibility enforcement (CRM-02 + CRM-04, UI-visible consequence):** `requireUser()` first, then

queried and then hidden client-side; they are never fetched.

### 5. Role surfacing — `sales` role (ROLE-01, ROLE-02)

- `Role` type in `src/lib/auth/require.ts` extends from `'partner' | 'admin'` to `'partner' |
  'admin' | 'sales'`. The DB CHECK constraint on `users.role` (currently `IN ('partner',
  'admin')`, confirmed in `src/db/schema.ts`) gets a matching migration. `requireUser()`'s
  current 2-way coercion (`role === 'admin' ? 'admin' : 'partner'`) becomes a straight pass-
  through of the DB value once the type is 3-way.
- **Sidebar nav:** `sales` users get the **same nav set as `partner`** — `AppSidebar.tsx`'s
  `isAdmin` boolean already drives the only branch point (`adminNavItems` vs `partnerNavItems`);
  a `sales` user is simply another `isAdmin === false` case, so **zero code change is needed in
  `AppSidebar` beyond the type widening** — `partnerNavItems()` already returns the right 4 items
  (Accueil, Nouvelle proposition, Propositions, Aide), and Phase 30 adds a 5th, "Clients", to that
  same array (both `partner` and `sales` see it — ROLE-02's "reaches the same pipeline/client-
  book surfaces a partner reaches" is then true by construction, not by a special case).
- **Admin-side role mechanism — this is the one place the old spec over-built (A-3 resolved,
  much narrower than previously assumed):** `CreatePartnerForm.tsx` already has a `partnerType`
  field — a native `<select>` (not a segmented control; segmented.ts is not used here, confirmed
  reading the actual form) — with three options, one of which is **already `'Commercial'`**
  (REQUIREMENTS.md's own framing: "`users.partner_type` already carries `'Commercial'` — an
  internal salesperson, not a channel partner"). **No new selector, no new label, no new copy is
  needed on this form.** The mechanism this phase specifies: the server action backing
  `CreatePartnerForm` derives `users.role` from the submitted `partnerType` — `partnerType ===
  'Commercial' → role = 'sales'`, otherwise `role = 'partner'` (admin accounts are created through
  a separate, unrelated path and are out of this form's scope, unchanged). This is additive and
  reversible: existing `Agent`/`Partenaire` submissions are unaffected, and it requires zero new
  UI surface — the visual contract for this requirement is **"no visible change to
  `CreatePartnerForm`."**
- **Existing `Commercial` accounts:** the migration backfills `role = 'sales'` for any existing
  `users` row where `partner_type = 'Commercial'` — a data migration, not a UI concern, flagged
  here only so the planner doesn't miss it.
- **No visibility change for existing accounts (ROLE-03):** nothing above alters what an existing
  `partner` or `admin` row renders — `partnerType` still defaults to `'Partenaire'` and this is
  purely additive on the create-invitation flow.

1. **A-1 — RETIRED.** The prior spec's blocking assumption ("ReUI/shadcn migration not present

   `components.json` exists (`style: base-maia`), and six ReUI CRM blocks are vendored. This
   entire spec is re-derived against that reality.

2. **A-2 — Client detail page uses a single-column layout, not the 2-column primary+sticky-
   preview layout `proposals/[id]` uses.** Re-confirmed against the current proposal detail page
   (`EmbeddedPdfPreview` genuinely occupies the right column; nothing at the relationship level
   fills that role yet). Revisit when Phase 34's activity timeline needs a home — it is the
   natural right-column occupant then.

   segmented-control "Type de compte" field for `CreatePartnerForm`. Re-reading the actual form
