## Radius Scale — supersedes UIC-04's multiplier clause (D-02)

> **This is the mechanism this phase exists to fix, not a side effect.** Read
> `app/globals.css:66-74` before touching anything here — it is the incident record UIC-04
> locks: `--radius` was briefly `1rem`, and because every step derived from that one value via a
> multiplier (`×0.6` … `×2.6`), the top of the scale hit 41.6px and every `Input`/`InputGroup`
> rendered as a pill. **D-02 replaces the multiplier mechanism itself** so that incident becomes
> structurally impossible — not just avoided by picking a smaller number.

**UIC-04's multiplier clause is superseded. UIC-04's `.card`-tracks-the-token clause and its
underlying *reason* (containers must never be a per-file literal) survive and are strengthened,
not weakened, by this change.** `.planning/codebase/UI-CONVENTIONS.md` UIC-04 needs a revision
pass after this phase ships — flagged here for the planner, not performed by this document.

### The new scale (explicit per-step, not multiplied)

Replace the `@theme inline` block at `app/globals.css:481-487`
(`--radius-sm: calc(var(--radius) * 0.6)` … `--radius-4xl: calc(var(--radius) * 2.6)`) with
explicit per-step values matching Colibris's measured scale:

| Token | Value | Notes |
|---|---|---|
| `--radius-sm` | 12px | |
| `--radius-md` | 16px | |
| `--radius-lg` | 24px | |
| `--radius-xl` | 32px | |
| `--radius-2xl` | 40px | |

**Colibris declares no `--radius` base and no 3xl/4xl step — the steps are explicit, not
derived.** This scale does the same: **retire the `--radius` base token as the driver of
container radii.** Retain `--radius: 0.625rem` (10px) *only* as the value shadcn's own
control primitives (`Input`, `Button`, `Select`, `Badge`, radio items) read directly — those are
unaffected by D-01/D-02 (D-03: controls keep 8px, and Colibris measures the same). Concretely:
`--radius-sm`/`-md`/`-lg`/`-xl`/`-2xl` become **standalone declared values**, no longer
`calc(var(--radius) * n)`. This is why the regression is now structurally impossible: raising
`--radius` to "get a bigger radius" no longer touches container tokens at all, because they no
longer read `--radius`. `--radius-3xl` / `--radius-4xl` are retired (no callsite in the repo
reads them beyond the multiplier block itself — confirm at implementation time via grep before
deleting).

**Container-radius token (Claude's Discretion, resolved):** name it **`--radius-container`**,
aliased to `--radius-md` (16px) — `--radius-container: var(--radius-md);`. Two names exist
because they answer different questions: `--radius-md` is "the 16px step of the scale" (a
primitive), `--radius-container` is "what a card/panel/sheet/dialog uses" (a semantic role). A
future container size change (e.g. a phase wants panels at `--radius-lg` instead) then edits one
alias, not every call site. `.card` and every surface in the table below reads
`var(--radius-container)`, never `var(--radius-md)` directly and never a literal px value.

### Back-application (closes OPEN-A, D-01/D-05)

| Surface | Before | After |
|---|---|---|
| Phase 30 `.card` (`app/globals.css:260-272`) | `var(--radius-2xl)` (calc'd 18px) | `var(--radius-container)` (16px) |
| Phase 31 `PairReviewCard` | `rounded-[24px]` (literal) | `rounded-[var(--radius-container)]` (16px) |
| Phase 31 `MergeDialog` / `KeepSeparateDialog` (`DialogContent`/`AlertDialogContent`) | `rounded-[24px]` (literal, className override) | `rounded-[var(--radius-container)]` (16px) |

OPEN-A closes at **16px**, not either of the two prior values — Colibris measured 16px, which is
below Phase 31's 24px literal and within 2px of Phase 30's 18px. Phase 31's literal moves
**down**; Phase 30's token-derived value moves down by 2px automatically because it now reads
`--radius-container` instead of `--radius-2xl`.

**Controls are explicitly untouched.** `Input`, `Button`, `Select`, `Badge`, radio items keep
reading `--radius` (10px base) → their own derived shadcn defaults, unaffected by this section.
D-03 confirms Colibris's controls measure 8px too — nothing to reconcile.

**Verification gate for the executor:** after wiring the new scale, render the wizard's
`ParametresForm` (the surface `app/globals.css:66-74`'s incident specifically named) and confirm
every `Input`/`InputGroup` corner is still control-tier (8-10px), not container-tier. This is
the direct regression check for the incident this section fixes.

## Header (D-04, D-05, D-06)

### Layout

Left group: **header toggle + breadcrumb trail**. Right group: **ADMIN badge** (unchanged,
`isAdmin` only). `TopbarTitle` is **removed from the render tree** (D-04) — the page title
already lives in `PageHero`, which every authed page already renders; the header no longer
duplicates it.

**Height: 52px** (down from 64px / `--topbar-h`). This is a Colibris-measured value applied via
the existing `--topbar-h` custom property — **change the value, not the mechanism**: the
proposal detail page's sticky offset (`top: calc(var(--topbar-h) + 24px)`) automatically follows
because it already reads the variable rather than a literal. Update `--topbar-h: 64px` →
`--topbar-h: 52px` at its single declaration site (`app/globals.css`, the "Legacy v10 aliases"
block region) and nowhere else.

### Header toggle (D-07 — replaces the in-sidebar chevron)

Leasétic already has the correct primitive: `<SidebarTrigger className="-ml-1 md:hidden" />` in
`Topbar.tsx`, currently hidden above the `md` breakpoint. **Unhide it** (drop `md:hidden`,
keep `-ml-1`) so it renders at every width, matching Colibris's "labelled 32×32 Toggle Sidebar
button in the header" at every width, not only mobile.

- **Icon:** unchanged — `SidebarTrigger`'s own Hugeicons `SidebarLeftIcon` (this is exactly the
  Hugeicons tier UIC-07 reserves for primitive-internal chrome; no new icon).
- **Label (UIC-10 — explicit `aria-label` required):** `SidebarTrigger` currently renders a
  hardcoded English `<span className="sr-only">Toggle Sidebar</span>` with no override prop.
  Pass an explicit `aria-label` from the call site: `<SidebarTrigger aria-label={t('shell.topbar.toggleSidebar', lang)} />`
  — `aria-label` on the underlying `Button` takes precedence over the sr-only child text for the
  accessible name, so the hardcoded English string is superseded (not removed — leaving it as
  dead sr-only markup is harmless; removing it is a nice-to-have, not required by this contract).
  **New key required** (does not exist yet): `shell.topbar.toggleSidebar` — see i18n Key Plan.
  This is a **single static label**, not a collapse/expand-conditional pair — matches Colibris's
  measured single "Toggle sidebar" label exactly, and avoids plumbing sidebar `state` into the
  server-rendered `Topbar.tsx`.
- **Delete the in-sidebar chevron entirely** (`AppSidebar.tsx` lines ~192-210: the hand-rolled
  `<button>` with `ChevronLeftIcon`/`ChevronRightIcon` and `sidebar.collapse`/`sidebar.expand`
  labels). **Two controls must not announce the same accessible name** (ROADMAP criterion 2) —
  deleting the sidebar chevron rather than keeping both is what satisfies this; do not keep a
  second, differently-labelled toggle "just in case." The existing `sidebar.collapse` /
  `sidebar.expand` dictionary keys become unused by this deletion — leave them in the dictionary
  (harmless dead keys, not a violation) rather than deleting keys as a side effect of a shell
  phase.
- **`SidebarRail`** (the primitive's own drag-to-toggle edge control, currently
  `aria-hidden="true"` in `AppSidebar.tsx`) stays exactly as-is — already correctly excluded from
  the accessibility tree, already not competing for an accessible name. No change needed here.

### Breadcrumb (D-04, D-06)

Composition, left-aligned after the toggle:

```tsx
<Breadcrumb>
  <BreadcrumbList>
    {segments.map((seg, i) => (
      <React.Fragment key={seg.href ?? seg.labelKey}>
        <BreadcrumbItem>
          {i === segments.length - 1 || !seg.href ? (
            <BreadcrumbPage>{t(seg.labelKey, lang)}</BreadcrumbPage>
          ) : (
            <BreadcrumbLink href={seg.href}>{t(seg.labelKey, lang)}</BreadcrumbLink>
          )}
        </BreadcrumbItem>
        {i < segments.length - 1 && <BreadcrumbSeparator />}
      </React.Fragment>
    ))}
  </BreadcrumbList>
</Breadcrumb>
```

- **Source: `getRouteMeta`, extended, not a parallel route table** (per `31.1-CONTEXT.md`
  canonical refs). `getRouteMeta` currently returns a single `{titleKey, activeNav}` pair per
  route; this phase's mechanism is to derive an ordered segment list from the **same** underlying
  route-matching logic already in `getRouteMeta`, not a second lookup table that could drift out
  of sync. Concretely: extend `RouteMeta` (or add a sibling function reusing the same
  `if (tail.startsWith(...))` chain) to also return a `breadcrumbKeys: DictKey[]` (or equivalent
  ordered list), so `getRouteMeta` stays the single source of truth for "what route am I on."
- **Trail depth (Claude's Discretion, resolved) — 2 levels for every route in this phase's
  scope, never 3+:** `[Section, Current page]`. Examples:
  - `/clients` → `Sociétés` is not shown for partners (partner nav label is "Clients", singular
    section) → breadcrumb: **just `Clients`** as the current (non-link) page — a 1-segment trail
    is valid when there is no meaningful parent to show above a top-level nav route.
  - `/clients/[id]` → **`Clients` (link) → `{company name}` (current page)**.
  - `/[adminSegment]/companies` → **`Sociétés`** (1-segment, top-level).
  - `/[adminSegment]/companies/[id]` → **`Sociétés` (link) → `{company name}` (current page)**.
  - `/[adminSegment]/companies/review` → **`Sociétés` (link) → `Réconciliation` (current page)**
    — a section-relative child, matching the route's own `/companies/review` nesting and its
    `admin-companies`-then-`admin-reconciliation` prefix-match ordering already established in
    `route-meta.ts`.
  - `/proposals/[id]` → **`Propositions` (link) → `{LC ref or client name}` (current page)**.
  - `/[adminSegment]/partners/new` → **`Partenaires` (link) → `Nouveau partenaire` (current
    page)**.
  - Top-level list/home routes (`/`, `/proposals`, `/[adminSegment]`,
    `/[adminSegment]/coefficients`, `/aide`) → **1 segment, current page, no link** (there is
    nothing meaningfully "above" a top-level nav item other than the section itself, and showing
    `Accueil → Accueil` would be a duplicate, not a trail).
  - **Colibris shows a 3rd level** (`Leasétic Group` breadcrumb above company-family entries) —
    **not adopted.** Leasétic has no group/workspace-switcher concept yet (explicitly deferred,
    see Scope Boundary). 2 levels is the ceiling for this phase.
- **Language:** every `labelKey` resolves through the viewer's `lang`, reusing the **existing**
  `sidebar.nav.*` keys wherever a segment IS a nav item (e.g. `sidebar.nav.clients`,
  `sidebar.nav.adminCompanies`) — do not mint new keys for labels that already exist. New keys
  are needed only for non-nav "current page" leaves (a company name is data, not a dictionary
  key — rendered directly; "Nouveau partenaire" / "Réconciliation" etc. need new or reused
  `admin.*`/`clients.*` keys — see i18n Key Plan for the ones genuinely new).
- **Current page is always non-link `BreadcrumbPage`**, never `BreadcrumbLink` — matches the
  primitive's own semantics (`aria-current="page"`) and ROADMAP criterion 3's explicit wording.

**`TopbarTitle.tsx` (Claude's Discretion, resolved): delete it, don't keep as an unused
export.** It has exactly one call site (`Topbar.tsx`), which this phase edits directly to remove
the import; there is no migration window where both old and new header content need to coexist
(unlike, say, `window.confirm()` vs `AlertDialog`, which UIC-06 deliberately keeps side-by-side
because dozens of call sites exist). Zero call sites survive after this edit, so an unused
export is dead code, not a compatibility shim — delete the file.

### Collapsed rail composition (D-08 — the chevron and the stack disappear together)

**Before this phase:** `AppSidebar.tsx`'s `SidebarHeader` renders `flex items-center gap-2` (adds
`flex-col` when collapsed), containing either `<BrandLogo width={190}>` + spacer (expanded) or a
28×28 `<img src="/logo-mark.svg">` (collapsed) — **plus the hand-rolled chevron button in both
states**, which is what forces the collapsed case into a vertical stack (mark above chevron).

**After this phase:** the chevron is gone (moved to the header, D-07). With nothing left to
stack against, the collapsed `SidebarHeader` renders **the mark alone**:

```tsx
<div className={cn('flex items-center gap-2', collapsed && 'flex-col')}>
  {collapsed ? (
    <span className="flex size-8 items-center justify-center rounded-[9px] bg-sidebar-primary">
      {/* 18×18 glyph — reuse the existing mark asset scaled to 18px, or the
          product-icon-vocabulary equivalent if one exists; do NOT introduce a
          Hugeicons glyph here, this is product-level brand chrome, not
          primitive chrome (UIC-07). */}
      <img src="/logo-mark.svg" alt="" width={18} height={18} />
    </span>
  ) : (
    <BrandLogo width={120} alt={t('sidebar.brand', lang)} />
  )}
</div>
```

- **Structure copied from Colibris (D-09):** a 32×32 badge at **9px radius** holding an **18×18
  glyph** — up from the current bare 28×28 `<img>` with no badge container. `bg-sidebar-primary`
  (already `var(--brand-accent)` in both themes) is the badge fill — the one place this phase
  puts the Leasétic accent on the collapsed rail, matching the badge's role as the brand mark
  itself, not a competing accent use against UIC-03's budget (a logo mark is not counted the same
  way a CTA/status-chip/bullet/active-indicator is — it is the identity glyph, exempt from the
  interactive-element accent budget by the same logic Colibris's own badge is).
- **Centering fixed, not copied (D-09 — Leasétic must be *better* than Colibris here):**
  Colibris's own rail measures 68px wide with nav icons dead-centered at 33.5px but its logo mark
  centered at 26px — 8px off its own center line, confirmed by direct measurement. **Leasétic's
  implementation does not repeat this by construction, not by a pixel-offset patch:** both
  `SidebarHeader` (containing the mark) and `SidebarGroup` (containing the nav icons) already
  share the identical `p-2` (8px) horizontal inset within the same 68px collapsed rail
  (`SidebarHeader`: `flex flex-col gap-2 p-2`; `SidebarGroup`: `relative flex w-full min-w-0
  flex-col p-2` — confirmed in `sidebar.tsx`), and the collapsed header wrapper already carries
  `items-center` (present in the base class, not conditionally added), which horizontally centers
  its child within that shared inset. **The verification gate for the executor is not "measure
  and nudge" — it's "confirm the badge and the nav icons are rendered inside boxes with matching
  horizontal padding at the same nesting depth."** If a future change ever gives `SidebarHeader`
  and `SidebarGroup` different horizontal padding, this centering breaks — flag that as a
  regression against this contract, not a cosmetic nit.

### Expanded brand lockup (D-10)

`<BrandLogo width={190}>` → **`<BrandLogo width={120}>`** in `AppSidebar.tsx`'s expanded branch
only (the collapsed branch no longer calls `BrandLogo` at all — see above). `height` is not
passed — `BrandLogo`'s own aspect-derivation (`Math.round(width / LOCKUP_ASPECT)`, asset ratio
862:200) computes it automatically, exactly as the component's own header comment intends; **do
not pass a hardcoded height alongside the new width** — that is the exact mismatch
`BrandLogo.tsx`'s own comment warns caused letterboxing once before.

120px in a 252px sidebar = 47.6% — matches Colibris's measured 118px/252px (46.8%) within
rounding, and lands close to the v10 prototype's 130px (historical reference only, not a target).
Every other `BrandLogo` call site (public layout, login/invite/reset per Phase 15) is **untouched
— its `width` default stays 190**; this phase changes only the one explicit `width={120}` call
inside `AppSidebar.tsx`'s expanded sidebar branch.

### Nav group (D-12 — unchanged structure, new eyebrow styling only)

Single nav group stays single — no `PLATFORM`/`ENTITIES` sectioning. The one existing
`<SidebarGroupLabel>{t('sidebar.eyebrow.navigation', lang)}</SidebarGroupLabel>` gains Colibris's
measured eyebrow treatment: **11px, `uppercase`, `letter-spacing: 0.55px`**. Implementation is a
className addition on the existing element (`text-[11px] uppercase tracking-[0.55px]`) or,
if the repo's convention is to keep typography off ad-hoc classNames, a scoped rule on
`[data-slot="sidebar-group-label"]` — planner's call, not a new component either way.

   `{titleKey, activeNav}`; this contract assumes the planner adds a breadcrumb-segment field
   (or a sibling function sharing the same route-matching branches) rather than introducing a
   second lookup table. If the planner finds the existing `if (tail.startsWith(...))` chain too
   entangled to extend cleanly, a parallel table is an acceptable fallback **as long as both
   stay in the same file and the planner notes the duplication risk** — this document's hard
   requirement is "derives from route matching," not "reuses one specific function signature."

   newly commissioned asset. If that SVG doesn't crop cleanly to an 18px glyph inside a 9px-radius
   32px badge, sourcing a cropped variant is a one-file asset task, not a scope change to this
   contract.

   `--card`/`--sidebar`, `--border`/`--sidebar-border`, `--muted-foreground`). `--popover` and
   `--input` are deliberately left unchanged per the Unsampled gaps table — if the human-verify
   checkpoint finds a contrast problem on a dialog or form field in dark mode, that is new,
   separately-scoped work (get a second Colibris screenshot), not silently absorbed into this
   phase's edits.

   document assumes no call site outside the multiplier block itself reads them; the executor
   must verify this (`grep -rn "radius-3xl\|radius-4xl"`) before removing the declarations, and
   keep them (unused but harmless) if any real call site is found.

   `sidebar.eyebrow.navigation`'s existing FR/EN copy ("Navigation") is unchanged; only its
