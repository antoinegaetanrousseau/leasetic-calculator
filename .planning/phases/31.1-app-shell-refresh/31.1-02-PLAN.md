Build the data layer for the shell breadcrumb (D-06): extend `getRouteMeta` so the same

## Trail-depth decision (Claude's Discretion, exercised here)

`31.1-CONTEXT.md` § Claude's Discretion grants "breadcrumb segment labels and how deep the trail
goes on each route — as long as it derives from `getRouteMeta` and honours FR/EN."

`31.1-UI-SPEC.md` illustrates detail routes with a live entity name as the leaf
(`Clients → {company name}`). **This plan renders a dictionary label instead**, for three
reasons the executor should not relitigate: (a) `getRouteMeta` is a pure pathname function with
no data access, and `31.1-CONTEXT.md` § Phase Boundary forbids data work in this phase —
plumbing an entity name into the shell header would mean a new server→shell data path on every
authenticated page; (b) the shell header renders on every page, so an entity name there is a
persistent information-disclosure surface (screen shares, screenshots) that nobody scoped; (c)
the criterion the ROADMAP actually states is "derived from `getRouteMeta`, in the viewer's
language, with the current page as non-link text" — a dictionary leaf satisfies it exactly.
Record this divergence in the SUMMARY so the checker reads it as deliberate.

Ceiling is 2 segments, per the UI-SPEC.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| URL pathname (attacker-controllable) → `getRouteMeta` → breadcrumb hrefs rendered in the shell header of every authenticated page | The only untrusted input in this phase. |
| Admin URL segment (`ADMIN_URL_SEGMENT`) → breadcrumb href construction | The admin segment is a security-through-obscurity path element (AUTH-14/15); the shell must not widen its exposure. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31.1-02-01 | Information Disclosure | Breadcrumb hrefs on admin routes embed `adminSegment` | mitigate | Hrefs are built by string-concatenating the `adminSegment` the (admin) layout already resolved server-side for a URL the viewer is already on and which is already in their address bar. `adminSegment` is never rendered as label **text** — labels are dictionary keys only. Partner-side calls pass `adminSegment: undefined`, so no partner trail can contain an admin href |
| T-31.1-02-02 | Spoofing / open redirect | `BreadcrumbSegment.href` | mitigate | `href` is only ever assigned from a fixed set of literals (`/proposals`, `/clients`, `${adminPrefix}/partners`, `${adminPrefix}/companies`). The raw `pathname` argument is never echoed into an `href`. Test invariant "every non-last href starts with `/`" blocks a protocol-relative or absolute-URL injection |
| T-31.1-02-03 | Information Disclosure | Entity names in the shell header | mitigate | Deliberately not implemented — leaves are dictionary labels (see objective). No record data reaches the shell |
| T-31.1-02-04 | Tampering | A future route added to the app without a trail, silently falling through to the `/` fallback and mislabelling the page | mitigate | The fallback returns a valid 1-segment `header.home` trail rather than an empty array, so the header can never render an empty breadcrumb; the depth invariant test enforces non-emptiness |
| T-31.1-02-SC | Tampering | npm/pip/cargo installs | accept | No package-manager install in this plan or in Phase 31.1 |
</threat_model>
