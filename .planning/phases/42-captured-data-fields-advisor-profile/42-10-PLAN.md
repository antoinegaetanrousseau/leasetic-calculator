Enforce PROF-02 at the single server-side point D-17 chose — finalization — and give the two new
failure modes the client treatment D-18 and D-05 specify: a dialog naming the missing telephone
with a link to `/parametres`, and a toast plus redirect to step 1 for a draft that predates SIRET.

Purpose: `FinalizeButton` today never calls `res.json()` on the failure path at all — `!res.ok`
alone throws and every non-OK response collapses into one generic toast. Adding a bounded code on
the route side therefore looks complete while the dialog never appears (RESEARCH Pitfall 3). And
`finalizeWizard`'s `ZodError` catch would swallow a legacy draft's missing-SIRET failure into the
generic `ValidationFailed`, so the legacy check has to run as an independent pre-check before
`.parse()` is called at all (Pitfall 5, D-05).

Output: two new bounded codes, one server-side gate, one independent pre-check, and a client that
finally reads the failure body.
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-10-A | Tampering | finalize profile gate | mitigate | The gate lives inside `finalizeWizard`, which every finalize request passes through; the dialog is presentation only. A client that skips the UI still hits `if (!args.telephone) throw` on the server (D-17, ASVS V4). Asserted by a test that `renderProposalPdf` is never reached. |
| T-42-10-B | Information Disclosure | new bounded codes | mitigate | `MissingPartnerTelephone` and `LegacyDraftIncomplete` are bare string literals with no interpolated data, matching the four existing codes' shape exactly. A test asserts the response body's key set is exactly `['error']`, and `FinalizeButton` renders only dictionary strings — the ADMIN-09 no-payload-echo contract is preserved by construction, and `tests/admin-09-grep-contracts.test.ts` is re-run rather than assumed inert. |
| T-42-10-C | Information Disclosure | cross-user draft probing | mitigate | Unchanged by this plan. `getDraftById(args.draftId, args.userId)`'s `WHERE userId = $1` predicate is untouched, and the telephone gate reads `args.userId`'s own session-sourced value, never client input — so no new code can reveal another partner's data or the existence of their draft. |
| T-42-10-D | Elevation of Privilege | telephone provenance | mitigate | `telephone` is read from `session.user` inside the route's `requireUser()` block, never from the request body, so a partner cannot supply a telephone to satisfy the gate for an account that has none. |
| T-42-10-E | Denial of Service | legitimate partners blocked | mitigate | The gate's single condition is a missing partner telephone. The company telephone is explicitly not checked (D-13), and Plan 42-05's admin form plus Plan 42-04's `/parametres` field give both an admin path and a self-service path to clear the block. A test asserts an absent `partnerTel` still finalizes. |
| T-42-10-F | Denial of Service | unparseable error body | mitigate | `res.json().catch(() => null)` keeps a non-JSON failure response on the generic-toast path instead of producing an unhandled rejection that would leave the CTA spinning. |
| T-42-10-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; UI-SPEC § Registry Safety records that `Dialog` and `Button` are already vendored. |
</threat_model>
