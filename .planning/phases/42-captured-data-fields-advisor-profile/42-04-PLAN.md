| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-04-A | Elevation of Privilege | `companyTelephone` via `/api/auth/update-user` | mitigate | `input: false` on the additionalField definition — Better Auth rejects the field at the framework level, the same mechanism already protecting `partnerType` and `role`. This is structural, not a form-layer check. The acceptance criterion asserting no `companyTelephone` reaches `authClient.updateUser` is the code-side guard (ASVS V4). |
| T-42-04-B | Elevation of Privilege | fonction on `/parametres` | mitigate | Fonction is rendered as a `<p>`, never an input, and there is no write path for it on this surface — `partnerType` remains `input: false` and admin-only (D-14). A test asserts no editable control exists in that row. |
| T-42-04-C | Denial of Service | every authed route | mitigate | The registration is gated behind Plan 42-02's confirmed `MIGRATE PROD` run, and Task 3 re-verifies at runtime. This is the documented `partner_type` incident inverted. |
| T-42-04-D | Input Validation | `telephone` write | mitigate | `identitySchema` validates the value client-side through the shared `optionalPhoneSchema` rule; Better Auth stores it as a nullable text column with no interpolation into SQL (Drizzle parameterized). Value is free-text contact data, never rendered as HTML. |
| T-42-04-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; `42-RESEARCH.md` § Package Legitimacy Audit records the phase as install-free. |
