<objective>
Build the persistence and authorization layer for the single Leasetic advisor identity (PROF-03,
D-06, D-07, D-08, D-09 — the advisor is a Leasetic-side teammate supporting the partner's client
relationship, never the creating user): a fixed-id read/write pair over the `leasetic_advisor` singleton, a four-field
Zod contract, and an admin-only server action that writes it and records the change.

Purpose: D-08 puts this identity in its own table precisely so it stays out of `global_params`,
which is snapshotted verbatim into every proposal's `params_snapshot` — financial data that must
not carry contact details. D-09 makes it a live read at render time, so it must never be copied
into `proposals.inputs`. This plan is the layer that makes both of those structurally true before
any screen or PDF touches it.

Output: `getAdvisor` / `upsertAdvisor`, `advisorFormSchema`, `adminUpdateAdvisor`, all barrel-exported
and unit-tested.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `adminUpdateAdvisor` server action | A caller-supplied payload crosses into the singleton settings row |
| `leasetic_advisor` row → every generated PDF | One row's contents reach every partner-visible document once Phase 43 renders it |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-06-A | Elevation of Privilege | `adminUpdateAdvisor` | mitigate | `requireAdmin()` is the first statement in the action, before the payload is read and before any DB access — a server action is a public endpoint, so the page-level guard is not sufficient (ASVS V4, AUTH-15). A test asserts a rejecting `requireAdmin` leaves `upsertAdvisor` uncalled. |
| T-42-06-B | Tampering | `leasetic_advisor` row multiplicity | mitigate | Every write is a fixed-id `UPDATE`; no `INSERT` path and no "does a row exist" branch exist in application code, so two concurrent admin saves cannot produce competing singletons. Asserted by a test that `insert` is never called. |
| T-42-06-C | Input Validation | advisor payload | mitigate | `advisorFormSchema.parse` runs server-side inside the action regardless of client validation; all four fields are length-bounded and the email and phone shapes are refined (ASVS V5). Drizzle parameterizes the UPDATE. |
| T-42-06-D | Information Disclosure | `params_snapshot` / `proposals.inputs` | mitigate | The advisor lives in its own table, not `global_params`, so it cannot be captured by `buildParamsSnapshot`. `getAdvisor` is not imported by `finalize-wizard.ts` or `finalize-helpers.ts`, and this plan does not add such an import (D-08 / D-09). |
| T-42-06-E | Repudiation | advisor change history | mitigate | `updatedBy` on the row plus one `audit_log` entry per successful write identify who changed the identity that every PDF shows. |
| T-42-06-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; `42-RESEARCH.md` § Package Legitimacy Audit records the phase as install-free. |
</threat_model>
