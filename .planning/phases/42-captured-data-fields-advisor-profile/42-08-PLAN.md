<objective>
Put the client SIRET on wizard step 1 (FIELD-01): a new required field beside SIREN, prefilled from
the company registry when the SIREN resolves and always editable, falling back silently to manual
entry when it does not (D-01, D-03, D-04).

hand-typing. But a client's operating site is not always the siège, so the value stays editable,
and a third-party outage must never stop a partner finalizing — which is why D-03's fallback is
silent. The operator was offered the variant with an explanatory inline notice and did not take it.

Output: a `SiretInput` component, a registry-lookup server action, and the wired field.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `lookupSiretAction` | A partner-controlled SIREN string crosses into an outbound request to a third-party API |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-08-A | Elevation of Privilege | `lookupSiretAction` | mitigate | A Next.js server action is a public endpoint. `requireUser()` is the function's first statement, before the argument is inspected and before the outbound call, so an unauthenticated caller cannot use the app as a registry proxy (ASVS V4). |
| T-42-08-B | Information Disclosure | registry failure surface | mitigate | The action returns `{ ok: false }` with no reason field, so the client cannot distinguish "not found" from "upstream error" from "no siège SIRET". This is D-03's silent fallback and also removes an oracle that would let a caller probe which SIRENs the registry knows beyond what the existing CRM lookup already exposes. |
| T-42-08-C | Tampering | prefilled SIRET value | mitigate | The prefill is a convenience only: `requiredSiretSchema` and the cross-field refine (Plan 42-03) validate the value on both the client resolver and `finalizeWizard`'s server-side re-parse, so a manipulated or stale registry response still cannot produce a stored SIRET that disagrees with the SIREN. |
| T-42-08-D | Denial of Service | third-party dependency | mitigate | `lookupCompanyBySiren` returns its failures rather than raising them, and every failure maps to a no-op. A registry outage leaves the field blank and manually fillable — it can never block finalization (D-03). Asserted by the failure-path test. |
| T-42-08-E | Denial of Service | request amplification | mitigate | The malformed-SIREN short-circuit prevents a network call for junk input, and `useTransition` prevents overlapping in-flight lookups from a single blur sequence. |
| T-42-08-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; UI-SPEC § Registry Safety records zero new shadcn/ReUI blocks. |
</threat_model>
