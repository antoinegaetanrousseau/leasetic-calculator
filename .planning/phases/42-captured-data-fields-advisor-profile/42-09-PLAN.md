<objective>
Carry the partner company's telephone onto every proposal by session hydration rather than a typed
field (FIELD-02, D-11), and make the resume path repopulate the SIRET the partner already entered
(FIELD-01).

Purpose: D-11 rejects a wizard field because the telephone is a fact about the firm — retyping it
per proposal invites drift between proposals from the same partner. The established pattern is
already here: `partnerCo` and `partnerName` are resolved from the session server-side and written
into `draft.inputs`, never rendered as inputs and never read back from the form. This plan is that
pattern applied to one more field, plus the one-line resume-prefill addition the new SIRET field
needs.

Output: `draft.inputs.partnerTel` populated from `session.user.companyTelephone` on every draft
path, and `clientSiret` surviving a page reload.

**Pairs with Plan 42-08**, which renders the SIRET field itself. Both are wave 3 and land before
the phase closes; neither is complete without the other.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session → `draft.inputs` | An account-level fact is written into the proposal record that later becomes an immutable snapshot |
| stored draft / duplicated proposal → `draft.inputs` | Previously stored values are re-read and could carry another moment's (or another account's) attribution |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-09-A | Tampering | `draft.inputs.partnerTel` | mitigate | `partnerTel` is never rendered as an input and never read back from the form; it is resolved server-side from `session.user` on every render and re-asserted in both overlay writes, so a client-supplied value cannot survive. This is the existing D-07 lock extended by one field. |
| T-42-09-B | Information Disclosure | duplicate path | mitigate | The duplicate overlay already refuses to carry the source row's partner attribution and the source is fetched only when `source.userId === session.user.id`; adding `partnerTel` to the overlay keeps that property rather than widening it. A cross-user duplicate is silently skipped and never confirmed. |
| T-42-09-C | Denial of Service | partners with no company telephone | mitigate | An absent `companyTelephone` resolves to `''`, which `optionalPhoneSchema` accepts (Plan 42-03). No draft path can fail because the admin has not filled the field yet — D-13's explicit requirement. |
| T-42-09-D | Elevation of Privilege | company telephone provenance | mitigate | The value originates from `session.user.companyTelephone`, which Better Auth marks `input: false` (Plan 42-04), so a partner cannot set the value that lands on their own proposals. |
| T-42-09-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; `42-RESEARCH.md` § Package Legitimacy Audit records the phase as install-free. |
</threat_model>
