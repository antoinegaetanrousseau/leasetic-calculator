<objective>
Give the admin partner form a real persistence path for the two telephone values D-12 keeps
separate: the company telephone (D-13 — the existing `phone` field, which today writes only to an
audit trail nobody reads) and the partner's own telephone (D-19 — a genuinely new field), so an
operator can populate existing accounts before anyone meets the finalization gate.

Purpose: RESEARCH Pitfall 4 is the whole point of this plan. `phone` is already threaded through
`adminCreateInvitation`, but `buildProfilePayload()` is its only reader and its sole destination is
`audit_log.payload.profile` — write-only, never read back. Loosening the Zod constraint and
relabelling the field would leave it looking fixed while `session.user.companyTelephone` stayed
null forever. The `.update(schema.users).set({...})` call must be extended explicitly.

Output: both values persisted to real, queryable, session-readable `users` columns, with an admin
form that names them unambiguously.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin browser → `createPartnerInvitationAction` | Admin-supplied form values cross into a `users` UPDATE |
| server action → `users` table | Two new columns become writable from an admin-only path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-42-05-A | Elevation of Privilege | `createPartnerInvitationAction` | mitigate | The action re-validates with `createPartnerFormSchema.parse(data)` server-side before any write (defence-in-depth against tampered client state), and the surrounding admin route is `requireAdmin()`-gated. No new authorization path is introduced — the two new keys ride the existing single `users` UPDATE (ASVS V4). |
| T-42-05-B | Tampering | `users.company_telephone` / `users.telephone` | mitigate | Only this admin path and (for `telephone` only) the partner's own `/parametres` write may set these. `companyTelephone` is `input: false` in Better Auth, so no partner-facing endpoint can write it. Conditional spreads ensure an absent value never overwrites an existing one. |
| T-42-05-C | Input Validation | both telephone values | mitigate | Zod `/^[\d\s+()-]{6,20}$/` bounds the character set and length on both fields before the write; Drizzle parameterizes the UPDATE, so no string reaches SQL uninterpolated (ASVS V5). |
| T-42-05-D | Information Disclosure | `audit_log.payload.profile` | accept | Both telephones are recorded in the existing compliance trail. They are contact details, not commission or rate values, so ADMIN-09 is unaffected; the audit log is admin-only by its existing access path. |
| T-42-05-SC | Tampering | npm/pip/cargo installs | accept | No packages installed; `42-RESEARCH.md` § Package Legitimacy Audit records the phase as install-free. |
</threat_model>
