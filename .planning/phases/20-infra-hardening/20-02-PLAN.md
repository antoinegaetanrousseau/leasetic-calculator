<objective>
INFRA-02 — Add a CI db-smoke gate that catches schema-apply failures (missing
`_journal.json` entries, syntax errors, constraint violations on existing
data) BEFORE they reach production migration paths. Closes the recurring
"generator self-evaluation blind spot" class that bit v1.1 (correlated-subquery
SQL bug) and v1.2 Phase 12 (missing `_journal.json` entry → 24h prod un-applied).

Also extends the existing manual production migration workflow with a `branch`
selector (per D-01) so the same workflow can fan migrations across all 3 Neon
branches once 20-03 provisions them.

Per D-05 (PR `paths:` filter), D-06 (per-run ephemeral branch with always()
cleanup), D-07 (run migrations + assert apply succeeds), D-08 (required status
check via Pattern B from RESEARCH §5), and the RESEARCH §2 finding that Neon
publishes official GitHub Actions — NO raw curl/neonctl YAML.

Purpose: Pre-positions the safety net BEFORE INFRA-01's high-blast-radius
env-var changes ship (D-15 wave order). After 20-03 lands, every migration PR
(prod or preview or dev) will have been validated against an ephemeral schema
clone first.

Output:
- `.github/workflows/ci.yml` with a new `db-smoke` job appended after
  `build-test` (Pattern B from RESEARCH §5: job always runs, paths-filter
  gates internal steps).
- `.github/workflows/db-migrate.yml` with extended workflow_dispatch inputs
  (branch + confirm) and parameterized DATABASE_URL secret selection in the
  apply step.
- No app/source code changes; pure CI workflow plan.

the actual secret/variable provisioning is documented in `user_setup` for

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions runner → Neon API | The runner executes Neon's official Actions which embed a `NEON_API_KEY` to call the Neon REST control plane. Project-scoped key (not full-account) per `user_setup`. |
| PR author (untrusted) → CI workflow | A malicious PR could attempt to exfiltrate the NEON_API_KEY via the workflow. Mitigated by GitHub's "secrets are unavailable to forked-PR runs" default; the repository is public per STATE.md Phase 5 follow-up #2 but secrets policy still blocks fork access. |
| db-migrate.yml operator → production DB | Triggers from the Actions tab; the existing `production` GitHub Environment gates the apply job behind a required-reviewer. Now extended to all 3 branches. |
| Third-party action (Neon, dorny) → workflow | Supply-chain trust — actions can read env, exfiltrate via outbound HTTPS. Mitigated by major-version pinning + using only the official Neon publisher account. |
