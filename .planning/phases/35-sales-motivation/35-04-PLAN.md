<objective>
Prove — against a real Postgres, not a mocked driver — that the Phase 35
aggregate does not leak across partners, that its week window is half-open, and
that a move to Perdu does not extend a streak.

Purpose: every unit test in this repo mocks the database driver, so a mocked
test proves a WHERE clause was COMPOSED and can never prove it FILTERS. Two
production defects shipped this week through exactly that gap — both Drizzle
query builders that type-checked, passed 2200+ mocked tests, and mis-scoped on
every real call. Phase 35 adds a new owner-scoped aggregate over a week window
whose entire purpose is not to leak, which makes it the strongest candidate in
the repo for this treatment.

Output: one skip-by-default integration suite, plus recorded mutation evidence.
"The test passes" is not the deliverable. "Removing the owner predicate makes
exactly this test fail" is.

`DATABASE_URL_TEST` is not wired into CI, so this suite runs only when invoked
by hand. That is a known, accepted state — wiring CI is explicitly out of scope
for this phase and must not be attempted here.
</objective>

Assertions:
1. **Owner isolation, positive + negative (the headline claim).**
   `listWeeklyMovementsForOwner(A, win, 5)` returns only rows whose
   `relationshipId` belongs to A; and

   NEITHER A's `A-only` company name NOR A's `shared` relationship id NOR any of
   A's event ids. Assert on the serialized payload, not only on enumerated
   fields, so a leak through an unnamed field is still caught.
2. **The shared company does not bridge owners.** A's result for the `shared`
   company references A's relationship id; B's references B's. Neither contains
   the other's.
3. **Week boundary is half-open.** A's movements include the event at
   `win.start` and the event at `win.end - 1ms`, and EXCLUDE both the event at
   `win.start - 1ms` and the event at exactly `win.end`.
4. **`total` reports the full window, `rows` is capped.** Call with `limit: 2`
   and assert `rows.length === 2` while `total` equals the true number of
   in-window movement rows for A.
5. **D-11 behavioural proof.** The `perdu` row IS present in A's movements
   (closing a dead deal belongs in the record), and

   is decisive: assert that the week key produced by a Perdu-only week is
   absent. Seed one additional relationship for A whose ONLY event is a
   `negociation` → `perdu` move in the week `shiftWeekKey(win.key, -3)`, and
   assert that key is not in the returned array while `win.key` and
   `shiftWeekKey(win.key, -1)` are.
6. **D-01 vocabulary proof.** Neither the `note` nor the `next_action_set` event
   appears in A's movements, and neither contributes a week key.
7. **Badge counts are owner-scoped.** `getBadgeCountsForOwner(A)` counts A's
   distinct progress relationships and A's one won proposal;
   `getBadgeCountsForOwner(B)` returns strictly B's own smaller numbers and never
   a total that could only be reached by including A's rows.
8. **Indistinguishability (defensive D-15 cover).** Calling all three functions

   call should ever happen in production.
9. **No write side effects.** After the full suite, a raw

   returns the seeded count unchanged — the read layer wrote nothing (D-03).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| partner A ↔ partner B in real SQL | The boundary this plan exists to test. `relationship_events` has no owner column; ownership is one join away, and only a real round-trip proves the join filters. |
| test harness → the database it points at | The suite INSERTs and DELETEs. Pointed at production it is a data-integrity incident, not a failed test. |
| shared company → two owners | A company held by two partners is the sharpest leak shape: a join keyed on the company rather than the relationship returns both books while looking correct. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-35-04-01 | Information disclosure (cross-partner, direct) | `listWeeklyMovementsForOwner` | mitigate | Positive + negative assertion pair over the SERIALIZED result, plus a shared-company fixture, plus mutation M1 proving the assertion is load-bearing rather than incidental. |
